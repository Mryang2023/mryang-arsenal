## 一、为什么不是「再加一批规则」

69 条规则解的是「**这样写对不对**」。多人协作真正的四个痛点它一条都不管：

| 失效点 | 现象 | 69 条能不能管 |
|---|---|---|
| 没有仲裁 | 同一件事两种写法，吵完靠谁先提交谁说了算 | ✗ 规则不解决「两个人都违规时谁对」 |
| 规范不落盘 | 规范只在某人脑子里，人一走就失传 | ✗ 规则集是通用的，不含「本项目怎么定的」 |
| 没有例外通道 | 有人有正当理由破例，嘴上说破就破了，然后全队跟着破 | ✗ 规则只有 MUST/SHOULD，没有「合法例外」概念 |
| 查不出跨文件漂移 | 每个文件单独看都合规，合起来一套代码五种命名风格 | ✗ 现有引擎全是单文件判定，无跨文件视野 |

所以这一层要解决的不是「加规则」，是**治理机制**：谁说了算、怎么改、怎么破例、怎么自动查。

## 二、分层模型

```
L0 行业基线        arsenal-rules/**        69 条 · 跨项目复用 · 项目不可私改
      │ override（加严 / 放宽[须理由] / 替换）
      ▼
L1 项目章程        arsenal-charter/<id>.json  本次要建的 · 进 Git · 走 PR · MUST ≤ 15
      │ 条款 ID 走 PJX- 前缀，决策记录走 ADR-NNN，两族不混
      │ 继承 + 局部加严
      ▼
L2 目录级微约定    章程内的 pathGlob 作用域    模块自有 · 出了目录即失效
```

**override 三种动作**（这是 L0 与 L1 的唯一接口，不多不少）：

| 动作 | 语义 | 必填 |
|---|---|---|
| `tighten` | 项目比基线更严（SHOULD→MUST） | — |
| `relax` | 项目不比基线严（MUST→SHOULD） | `reason` + `approver` + `expiresAt` |
| `replace` | 换掉基线的检查方式（如项目用 MapStruct 不用手写拷贝） | `replacement` + `reason` |

> **`relax` 不允许永久。** 必须带 `expiresAt`。这是防止「当年的一次性例外变成十年传统」的唯一机械保障。

### 2.1 ID 命名空间：`PJX-` 而不是 `PJ-`（实测踩出来的）

`RULE_ID_PATTERN` 的第一段是 `[A-Z][A-Z0-9]{2,7}` —— **首字符 + 至少 2 个，即最少 3 字符**。
实测 69 条规则的段长分布只有 3（43 条）与 4（26 条）两种，**两字符前缀从未被使用过**。

| 候选 | 是否过契约 |
|---|---|
| `PJ-SVC-001` | ✗ **不过**（`PJ` 只有 2 字符） |
| `PJX-SVC-001` | ✓ 过 |

### 2.2 章程断言必须独立成一层（实现时推翻了自己）

初稿写的是「并入第十一层 `脚手架生成链路`，不加新层」（理由：加层要动五处 + README 两处）。
**实现时这条判断是错的**，真因不是成本：

`finish(layer)` 用 `layer` 字符串同时决定两件事 —— 状态文件名 `layer-<key>.json`，
以及 `declaredCount()` 去档案查表用的层名。两个脚本都 `finish('scaffold')` 时，
**后写的状态文件覆盖先写的**，先跑那 17 项被静默吞掉，报告上只看得见后跑的那层。

这正是本仓反复治的「静默丢失」，不能在自己新加的层上重犯一次。所以：
新增第 12 层 `charter`，`LAYER_NAMES` / `verify-all LAYERS` / `package.json` /
`arsenal.json verifyChain` / README 分项表 + 正文，六处同步 —— 与本仓硬约定第 7 条一致。

顺带修掉一处同类隐患：`meta-check` 的合计行原本写死「十层合计」，
现在从 `chainDeclared.length` **算出来**。层数是统计结果，写成字面量就一定会在
加一层那天过期，而当时没有任何东西会报错 —— 与「项数由实测得出」是同一条道理。

**为什么仍然要独立命名空间**（而不是把章程条款塞进 `COL-` 或 `WEB-`）：
章程条款与 L0 规则的**生命周期不同** —— L0 跨项目复用，章程条款随项目走、随项目废。
ID 不混是「一眼看出这条是哪个层级的东西」的最省事判据。


## 三、数据模型

### 3.1 章程文件外壳

`arsenal-charter/<projectId>.json`：

```jsonc
{
  "$schema": "./charter.schema.json",
  "id": "command-center",
  "name": "智能中枢 · 后端工程章程",
  "version": "1.2.0",
  "owner": "mryang",              // 章程本身的最终责任人
  "ratifiedAt": "2026-10-03",
  "team": ["mryang", "zhang", "li"],   // 出现过的开发者，用于例外登记簿的 assignee 校验
  "extends": "arsenal-rules@0.1.0",    // 钉死基线版本，升级基线要显式改这里

  "overrides": [ /* 见 2. 三种动作 */ ],
  "clauses":  [ /* 见 3.2 */ ],
  "exceptions": [ /* 见 3.3 */ ],
  "consistency": [ /* 见 3.4，一致性检查器配置 */ ]
}
```

### 3.2 条款（clause）—— 复用 Rule 契约 + 加四个字段

条款**必须**满足 `RULE_SPEC` 全部 12 项必填（id/title/severity/sources/rationale/bad/good/check/promptFragment/status/version），
在此之上**加四个**协作专用字段：

```jsonc
{
  "id": "PJX-SVC-001",                   // 独立命名空间，前缀 PJX-（3 字符，见 §2.1），不与 COL-/WEB- 混
  "title": "应用服务间调用必须走 Feign 声明式客户端，禁止裸 RestTemplate",
  "severity": "MUST",
  "sources": [{ "ref": "ADR-014", "type": "project-decision" }],
  "rationale": "裸 RestTemplate 的超时与重试各调用点各写一遍，线上出现过三个不同超时值的同类接口。",
  "bad": "restTemplate.getForObject(url + \"/x/\" + id, XxxDTO.class)",
  "good": "XxxClient.fetch(id);   // 声明式，超时/重试在 client 统一配置",
  "check": { "regex": { "pattern": "restTemplate\\.", "targetGlob": "**/*.java", "expect": "absent" } },
  "promptFragment": "服务间调用一律走 Feign 声明式客户端，禁止直接使用 RestTemplate。",
  "status": "active", "version": 1,

  "clauseOwner": "mryang",              // ① 这条归谁管 — 找谁问
  "decidedBy": "ADR-014",              // ② 依据哪次决策 — 可追溯
  "effectiveFrom": "2026-10-03",        // ③ 生效日 — 冻结线用
  "pathGlob": "src/main/java/**/service/**"  // ④ 作用域 — L2 微约定就靠它
}
```

四个字段是**硬要求**，构建期校验，缺一即失败：

- `clauseOwner` 不填 = 没人负责这条 = 三个月后没人知道为什么这么定
- `decidedBy` 不填 = 拍脑袋的规矩 = 下次有人来改
- `effectiveFrom` 不填 = **冻结线无法计算**（见 4.2）
- `pathGlob` 不填 = 无法生成 L2 微约定，也无法做 diff 门禁的路径裁剪

### 3.3 例外登记簿（exception）—— 最容易被省掉、但最要紧的一节

```jsonc
{
  "id": "EXC-0007",
  "clauseId": "PJX-DATA-002",          // 豁免哪条（PJX- 前缀，与 ADR 编号不同族）
  "pathGlob": "src/main/java/**/legacy/**",
  "reason": "历史模块，2026-Q4 排期重构，现阶段改造成本高于收益",
  "approver": "mryang",                // 谁批的
  "owner": "zhang",                    // 谁还债
  "grantedAt": "2026-08-15",
  "expiresAt": "2026-12-31",           // ★ 到期日，必填，无例外
  "ticket": "TASK-1830",               // 还债的工单号
  "status": "active"                    // active | expired | repaid | orphaned
}
```

构建期硬闸**五道**（对应本仓既有惯例「写不出反例的不收录」）：
1. `expiresAt` 必填 —— 「永久豁免」不接受
2. `owner` 必须在 `team` 里 —— 不能甩给不存在的人
3. `expiresAt` 已过期且 `status != repaid` → **构建失败**（债务到期不销账，红）
4. `reason` 长度 < 20 → 失败（「历史原因」不算理由）
5. **孤儿闸**：已过期、且 `owner` 已不在 `team` 里（离职/转项目）→ `status` 必须是 `orphaned`，
   此时**只进债务账高亮，不让构建失败**

> 第 5 条是自检时补的。原设计只有 1–4，漏了一个真实后果：**人走了，债务还在，
> 而债主已经不在团队里** —— 没人能销账，于是第 3 条会让全队构建永久红。
> 这不是「环境不满足」，是「决策者离职了」，两者的正确处置不同：
> 前者逼你干活，后者逼你补一个人。混在一道闸里，两个后果都出不来。
> `orphaned` 让这件事**必须被人看见但不会挡住别人干活**。

> 这五道闸门是这一层最值钱的东西。没有它们，例外登记簿三个月后就变成「全员豁免名册」。
> 五道里第 3 道最容易被嫌严（到期那天全队一起红），但它是唯一能让「例外到期必须销账」
> 不退化成口头承诺的机制 —— 顺带说明：第 5 道是**故意留的出口**，
> 否则「债主离职」这个最常见的情况会变成一个谁也解不开的死结。

### 3.4 一致性检查器（consistency）—— 现有引擎的第五层

前四层是 `regex → ast → llm → manual`，全都**单文件**。多人协作最痛的是跨文件漂移，所以加第五层 `consistency`：

```jsonc
{
  "id": "CONS-NAME-001",
  "concept": "订单",                   // 概念名
  "canonical": ["Order", "订单"],       // 唯一认可的写法
  "forbidden": ["Trade", "Purchase", "Bill", "OrderInfo"],  // 明令不许的同义写法
  "scope": "src/main/java/**/domain/**",
  "check": {
    "type": "identifier",              // identifier | package | table | interface
    "minVariants": 1,                  // 全仓出现 >1 种写法就报
    "report": "drift"                  // drift 只报不改，不阻断
  }
}
```

与前四层的**根本区别**：

| | regex/ast/llm | consistency |
|---|---|---|
| 判定对象 | 单个文件 | **全仓聚合** |
| 违规含义 | 这行代码错了 | **这个团队在漂移** |
| 处置 | 阻断（改了就过） | 默认只报（drift 不阻断） |
| 反例形态 | 一段 bad 代码 | **一组并排的命名变体** |

「写不出并排变体的检查项不是一致性检查」—— 沿用本仓第 3 条设计原则。

## 四、落地机制

### 4.1 三个出口（沿用「一份数据三种出口」）

| 出口 | 载体 | 谁消费 |
|---|---|---|
| 人查 | `/charter` 页面 + 按项目导规范书 | 新人、评审人、你三个月后 |
| 给 AI | MCP 新工具 `get_charter` / `check_clause` | 写代码时自己来查 |
| 拿代码验 | `/check?project=xxx` 项目模式 | 本地自检、CI |

MCP 工具扩三个（现有 4 个：search_rules / get_rule / lint_code / …）：

- `get_charter(scope)` —— 取本项目章程（含生效的 overrides）
- `list_exceptions(pathGlob)` —— **写代码前先看这里有没有合法豁免**（这条最容易被忘，但最重要）
- `check_clause(clauseId, files)` —— 单条条款定向校验

### 4.2 冻结线双门禁

存量代码不合规是必然的。**如果第一次跑就报 300 条红，没人愿意用第二次。** 所以：

| 门 | 范围 | 频率 | 处置 |
|---|---|---|---|
| **PR 门** | 本次 diff 触及的文件 × `effectiveFrom` ≤ 今天 的条款 | 每次 PR，秒级 | **阻断** |
| **存量门** | 全仓 | 定时（每晚 / 每周） | **不阻断**，出「债务账」页面 |

判据：`file.mtime >= clause.effectiveFrom` → 新代码；否则存量。
（更严谨的做法是用 `git log --diff-filter=A -- %f` 拿文件引入时间，mtime 只是近似 —— 实施时取 git 为准，mtime 兜底。）

> **实施取舍（2026-10-05 补记）**：实际没有按「文件引入时间」分新旧，
> 而是按**条款的 `effectiveFrom`** 划冻结线 —— 只看「这条规矩哪天生效」，不看「这个文件哪天写的」。
> 理由：前者在**章程数据里**，可评审、可回溯、换机器结论一致；
> 后者依赖 `git log` 与 mtime，**同一份代码在不同 clone 上结论可能不同**（浅克隆 / 重新检出都会改 mtime）。
> 「不许因为存量违规挡住今天的 PR」这个目标两者都能达成，而冻结线那个口径**不需要读 git**。
> 代价：一个在条款生效**之后**新建、但抄了老代码的文件，会被判为新代码 —— 这正是我们要的。

债务账页只列三列：条款 / 历史违规数 / 例外数。这页的 KPI 是**数字下降**，不是零。

### 4.3 CI 落地形态

导出的 CI 片段是 **PR 门模式**，不是全量门：

```yaml
- run: npx arsenal-lint --mode pr --base ${{ github.base_ref }}   # 只查 diff
- run: npx arsenal-lint --mode audit --report debt.md             # 旁路，不 exit 1
```

`--mode pr` 只对 `effectiveFrom` 之后的条款生效，存量违规不进 PR 门。
这与本仓 `export-lint` 的预检闸思路一致：**闸门只拦新增，存量走账**。

## 五、数据流与红线

```
arsenal-charter/<id>.json       source of truth，进 Git，**手写**（见下）
        │  node scripts/sync-content.mjs（校验 + 同步，P0 已接）
        ▼
src/generated/charter.json      编译期快照（gitignore）
        │
        ├─→ src/lib/charter.ts   纯函数层（合并 L0/L1、算冻结线、算一致性）
        ├─→ /charter 页面         人查
        ├─→ exporters.ts 扩 format 'charter-md'
        └─→ mcp-tools.json 扩 3 工具
```

### 5.1 为什么章程走**手写 JSON**，不进 `tools/content/*.py`（实现时定的，与规则集不同）

本仓硬约定第 1 条是「改内容改 `tools/content/*.py`」，但那条的适用范围是
**由生成器产出的三类数据**（规则/案例/选型）。章程不在其列：

| | 规则 / 案例 / 选型 | 项目章程 |
|---|---|---|
| 谁写 | 军火库维护者一人 | **各项目团队自己** |
| 变更频率 | 一次改动，全库受益 | 每个项目独立节奏 |
| 要不要构建期工具 | 要（跨文件交叉校验、锚点核对） | 不要（单文件自洽） |
| 手改成本 | 高（必须改 Python，改 JSON 会被生成覆盖） | **零**（JSON 就是源） |

若把章程塞进 Python，别的团队要用就得先装军火库的 Python 构建链 ——
而章程是「clone 项目即拿到」的东西（见待拍板 1，我倾向放业务仓）。
**让章程保持手写 JSON，反而是唯一让「工具可选」的形状。**
数据流因此比上图少一段，这是刻意的。

**沿用本仓硬约定**（自检后修订，带 ✅ 的是实测事实）：

1. 改内容改 `tools/content/charter/*.py` → `build-content.py` → `sync-content.mjs`
2. 条款 ID 必带 **`PJX-`** 前缀（**不是 `PJ-`**，见 §2.1 实测），**ID 不回收**。
   `RULE_ID_PATTERN` **实测无需改动** —— `[A-Z][A-Z0-9]{2,7}` 天然放行 3 字符前缀。
   要改的是 `RULE_REQUIRED`（12 项清单）**不加**条款的四字段：`clauseOwner/decidedBy/effectiveFrom/pathGlob`
   是**章程层附加**，不进 `RULE_REQUIRED`。理由：那 12 项守的是「L0 规则是完整可执行的」，
   章程层是「L0 之上的项目决策」，两者混进同一份必填清单会让 L0 也背上不该背的要求。
   → 章程自己的契约写在 `charter-contract.mjs`（**新文件，与 rule-contract 同构**），
   并**复用** `RULE_SPEC` 的字段定义对象而不是复制一份。
3. 章程的 MUST 条款数 **≤ 15**（人一次能记住的量）。超了构建失败 —— 与 `mustHardLimit: 50` 同一个思路。
   ✅ 口径参照 L0 实测 50/50 **已经打满**这个事实：上限必须硬，否则会被自然增长吃掉。
4. 例外**五**道闸门（§3.3）写进**新的** `validate-charter.mjs`（不改 `validate-rules.mjs` ——
   那个只管 L0 规则文件，塞进去等于让 L0 校验器知道「例外」这个它不认识的形状）。
   **不许只在 UI 提示**

### 页面结构：`/charter` 一个路由、三个页签 + 一块常驻

```
/charter
├─ 抬头        章程名 · id · 版本 · 批准日 · 负责人 · 基线 · 团队 · 快照时刻
```

**为什么政策条放首屏**：读条款的人必须先知道「例外到期会不会让构建红」，
才能理解那些徽标为什么是红的。政策藏进设置 = 徽标变成没有解释的颜色。

**为什么「偏离」与「一致性」不并进页签**：它们的读者不同 ——
偏离给「刚进项目的人」（我们和基线不一样在哪），一致性给「看到代码风格分裂的人」。
挤进页签会让三页签各有两种不相干的内容。

### 三条「不能假数字」的硬规矩（P1 最要紧的部分）

| 数字 | 不能怎么来 | 实际做法 | 断言 |
|---|---|---|---|
| `today` | 不能 `new Date()` —— 静态导出页面内容随构建时刻变，今天红了明天自己又绿 | **sync 链写进快照**，且同一个值喂给 `validateCharter(today)`，保证「构建期判的」与「页面显示的」是同一天 | ✓ 断言「快照 today == todayOf()」 |
| L0 MUST 实测 / 上限 | 页面静态导出**拿不到文件系统**；写成字面量则 L0 加一条时静默过期 | sync 链**逐文件重算**（不用 `meta.json#budget.mustCurrent` 那个声明值），写进快照 | ✓ 断言「快照数 == 现扫实测」 |
| shared 口径用量 | L0 数据拿不到时不能显示 0% | `budgetView` 显式返回「无法计算」 | ✓ 断言「缺数据时说明里含『无法计算』」 |

顺带：L0 声明值与实测值**漂移时页面上显式提示**（`l0DeclarationDrift`）——
不静默用其中一个，因为那会让「声明值已过期」这件事只有 CI 知道。

### `debtLedger` 为什么按条款聚合而不是罗列例外

例外几十条、条款十几条。按条款聚合才能看出**哪条规矩在持续吃豁免**：

> 一条条款吃 5 个豁免是**制度问题**（那条规矩定得不对，人不得不绕）；
> 5 条条款各吃 1 个是**执行问题**（人没守住）。
> 这两种问题的处置完全不同，所以按条款聚合。
> 页面正文里也把这句读法写给读者了 —— 一张表如果需要解释才能读，它就该被解释。

断言里守了**守恒**：各行 `openDebt` 之和 == 未销账例外总数（聚合类断言必须守恒，
否则「加错了行数」与「算错了数」都看不出来）。
