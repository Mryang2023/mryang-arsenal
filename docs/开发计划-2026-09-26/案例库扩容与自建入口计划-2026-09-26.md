# 最佳实践案例库（/blueprints）· 内容扩容 + 自建入口计划

> 日期：2026-09-26
> 承接：2026-09-24 三层结构重构、`docs/开发计划-2026-09-25/最佳实践案例库升级计划-2026-09-25.md`（C-1 AI 出口 / C-2 代码自证 / C-3 规则互链 / C-4 第二条主线）
> 本计划回答两个问题：**①除了虚拟线程还该写什么；②你自己（以及团队里其它人）怎么往里写**

## 0. 决策先行

| 问题 | 结论 |
|---|---|
| 现在缺什么 | 两样：**内容**（只有 1 条主线）和 **入口**（写入路径只有一条 —— 改 `tools/content/*.py` 再跑 build + sync，等于只有仓库作者能写） |
| 先做哪个 | **先做入口（W-0/W-3），再批量填内容**。理由：入口的内核是「把校验判据抽成一份共享清单」，抽出来之后每条新主线都从「盲写 ~900 行 Python」降级成「填空 ~300 行 + 看红绿」；反过来先写内容，入口落地时要返工全部已写主线 |
| 内容往哪写才不跑偏 | **按规则反推，不按技术热度推**。实测 69 条规则里 **61 条从未被任何案例引用**，其中 **42 条是 MUST/NEVER**。按这 42 条的密度聚类 ⇒ 自然得出 9 条主线，且能做到「每条主线都是被自己的强制级规范拽出来的」 |
| 用户录入的内容要不要进 Git | **两条车道**：`私有`（浏览器 / 本地目录，不进 Git、不进九层数字契约）/ `一等公民`（`tools/content/*.py`，过 build + verify）。两条车道之间有一部**电梯**：私有内容可一键导出成 `.py` 骨架升格。不留第三条模糊地带 |
| 用户录入要不要放宽校验 | **不放宽**。校验清单就是产品质量本身，录坏了比没录更糟。差别只在：私有车道**不阻塞构建**，但在录入界面里逐条告诉你「还差什么」 |
| 一眼看完的目标 | **10 条主线（1 现有 + 9 新增）吃掉全部 42 条未覆盖的 MUST/NEVER**，外加一套「你自己也能写」的录入通道 |
| 明确不做 | 不做在线写 Git（后端无写仓库权限，也不该有）、不做投稿/多租户/审核流（三原则里的上限：单人 + 小团队）、不绑某家 AI（导出 prompt 而不是调 API）、案例库不做 auto-fix |

### 2.2 两种主线规格（关键设计决策）

| 规格 | 适用 | 必含 | 可否无实验 | 预计体量 | 一棒能否做完 |
|---|---|---|---|---|---|
| **A 型 · 实操型** | 有运行时行为的技术（IO、并发、事务、校验） | L1/L2/L3 全套 + `flow` + `files[]`(≥2) + `checklist`(≥3) + `pitfalls`(≥2) + `playground`(≥1) + `lab` | **必须**有 ≥1 个自包含可跑实验 | 700–950 行 Python | 一棒一条（含真跑一次） |
| **B 型 · 契约型** | 只有「规定 + 反例」的主题（骨架 / 单测 / 代码纪律 / 命名） | 同上 **去掉 `playground` 与 `lab`**；改为必含 `performance`? 否 —— 改为必含 **`doAndDont`（≥3 组 bad↔good 对照，每组挂 `rule`）** | 允许 | 250–400 行 Python | 一棒可做两条 |

> B 型不是降质：它把「实验」换成「**可执行对照**」—— 每组 doAndDont 的 good 片段要能被 `cookbook-lint` 扫出零违规、bad 片段要能扫出至少 1 条（这本身就是可机检的，见 W-0 内核）。
> **代码层今天就已经允许 B 型**（`build_cookbook` 只在 `lab.kind` 有值时才校验），要改的是 09-25 那份门槛文档的 T-3。

### 2.3 每条主线的「能些什么」草案（写作时的起手提纲）

**① api-contract（A 型，P0）** —— `glyph: ⌸`
- S1 `request-validation` 入参校验收口：`@RequestBody` + `@Valid` + 专用 DTO + 字段约束注解
  - signals：DTO 里出现 `Map<String,Object>`；Controller 里手写 `if (x == null)`；实体直接进 `@RequestBody`
  - R1《DTO + Bean Validation + 全局 binding 结果适配》（files：`UserCreateRequest` / `GlobalExceptionHandler` / `UserController`）
- S2 `unified-response` 统一出口：所有接口同一响应体，业务异常走 `@RestControllerAdvice`
  - signals：不同 Controller 返回结构不一致；Controller 里 try-catch 业务异常；错误码各处硬编码
  - R1《Result 包装 + @RestControllerAdvice + ProblemDetail 兜底》
- S3 `pagination-limit` 分页与批量上限：`pageSize` 硬上限、游标法兜深翻
  - signals：导出接口一次拉全表；`pageSize` 由前端随意传；深翻页数越大越慢
  - R1《分页参数对象 + 上限截断 + 游标翻页》
- demo（纯 JDK）：起 `HttpServer` 当假 Controller，演示「裸返回 vs 统一包装 + 异常映射」的差异（`kind: mock-endpoint`）

**② error-and-log（A 型，P0）** —— `glyph: ⚠`
- S1 `swallowed-exception` 空 catch / printStackTrace 收口
- S2 `context-logging` 现场 + 堆栈、SLF4J 占位符、禁用 System.out
- S3 `resource-close` try-with-resources 替代裸 finally（含 finally return 陷阱）
- demo（纯 JDK）：同一个失败流程跑两遍，对比「吞掉异常」与「带 traceId 现场 + 完整堆栈」的可诊断性（`kind: mock-endpoint`，输出日志行）

**③ sql-baseline（A 型，P0）** —— `glyph: ▤`
- S1 `explicit-columns` 禁 `SELECT *`、显式列与别名
- S2 `bind-parameters` 占位符绑定（含 `IN` 的动态拼接陷阱、排序字段白名单）
- S3 `schema-convention` 表名/字段命名、`is_` 布尔、三件套必备字段
- demo：用 `HttpServer` 起一个假 DAO 层？—— 更合适的是 **新增 `lab.kind: 'sql-plan'`**：纯 JDK 无内嵌库，退一步做「**文本层对照**」：同一条查询的两种拼法 + 输出拼出来的最终 SQL（`kind: text-diff`，见 §3.1 的 kind 扩展提案）

**④ security-guard（A 型，P1，需新 family）** —— `glyph: ⛨`
- S1 `horizontal-authz` 资源归属校验（IDOR）
- S2 `data-masking` 敏感字段脱敏（手机号/身份证/银行卡）
- S3 `unsafe-input` 反序列化白名单（`ObjectInputFilter`，纯 JDK 自带）+ 排序/重定向参数白名单
- demo（纯 JDK）：`ObjectInputFilter` 拦住恶意 gadget 链 vs 不拦；`MessageDigest`/`PBKDF2` 存密码 vs 明文（`kind: self-contained`）

**⑤ tx-and-layering（A 型，P1）** —— `glyph: ⌗`
- S1 `transaction-boundary` `@Transactional` 落在 Service public 方法、显式 `rollbackFor`
- S2 `di-style` 构造器 + final 注入（含自调用导致事务失效）
- S3 `business-exception` 自定义业务异常替代裸 `RuntimeException`
- demo（纯 JDK）：用 JDK 自带的东西演示「自调用绕过代理」有点勉强 → 建议做成 **B/A 混合**：demo 用「手写代理 vs 自调用」的最小复现

**⑥ external-call（A 型，P1）** —— `glyph: ⇄`
- S1 `timeout-budget` 连接/读超时 + 全链路预算
- S2 `retry-backoff` 禁止 `Thread.sleep` 重试 → 退避 + 抖动 + 熔断
- S3 `idempotent-retry` 重试必须幂等（唯一键兜底）
- demo（纯 JDK）：`HttpServer` 起一个会随机慢/随机 500 的假下游（`kind: mock-endpoint`），对比无超时 vs 有超时+退避的 P99 —— 这条和 power/虚拟线程的 mock 写法几乎同源，**成本最低，建议当 A 型样板第一条**

**⑦ project-skeleton（B 型，P2）**：包结构 / 启动类位置 / BOM 管版本 / jakarta 命名空间 / 配置分环境
**⑧ unit-test-baseline（B 型，P2）**：AIR、必须断言、测试只进 `src/test/java`
**⑨ code-discipline（B 型，P2）**：`@Override`、常量命名、约定式提交、不提交密钥与产物

## 3. 自建入口：让你自己也能往里写

### 3.1 W-0 · 内核先行（**必须第一棒**）

把散在两处的校验判据抽成**一份清单**，三个消费方共用 —— 这就是项目第一条原则「一份数据三种出口」在校验上的落地。

```
tools/content/cookbook_contract.py      ← 唯一判据来源（Python，含每条的文案）
        │  导出
        ▼
arsenal-cookbook/_contract.json         ← 机器可读，进 Git
        ├── tools/build-content.py::build_cookbook      （构建期，拒绝非法内容写盘）
        ├── scripts/sync-content.mjs                    （同步期，去掉重复判据）
        └── src/generated/cookbook-contract.json
                └── src/lib/cookbook-contract.ts        （浏览器内实时校验）
```

- 判据清单至少包含现在双写的那些：`intent≥30`、`pickWhen≥2`、`limits≥2`、`references≥2`、`when≥30`、`signals≥2`、`notSuitable≥2`、`checklist≥3`、`pitfalls≥2`、`files.highlights≥2`、锚点必须命中、`relatedRules` 必须真实存在、`lab.kind` 与代码的对照（`mock-endpoint`→`HttpServer`）、**新增** `tier` 与 B 型的 `doAndDont≥3`、id 唯一性
- 新增闸门 **【22】共享判据三方一致**：①`_contract.json` 的条数 ≥ N；②build 与 sync 都不再内联出现这些阈值常量（grep 源码，出现即红）；③前端读到的是同一份（`generated/cookbook-contract.json` ↔ `arsenal-cookbook/_contract.json` 双向比）
- ⚠ 按本项目硬约定：**每条新断言必须反着验一次**（把阈值改坏 → 必须红 → 还原 → 必须绿），且新增/删除断言要同步四处数字（`arsenal-profiles/arsenal.json` 的 `project.verifyChain[*].count`、README 总数句、README 分项表、跑 sync）

### 3.2 W-1 · 浏览器内「我的案例」（`/blueprints/mine`）

| 项 | 设计 |
|---|---|
| 起步方式 | 三选一：**空白表单** / **粘贴 JSON** / **fork 一条现有主线**（详情页加「复制为我的案例」按钮） |
| 形态 | 表单 ⇄ JSON **双向绑定**：表单填就更新 JSON，粘 JSON 也回填表单。理由：新手用表单，批量用 JSON，两边不打架 |
| 存储 | `localStorage['arsenal-blueprints-v1']` —— 沿用 `src/app/stack/drafts.ts` 的写法；SSR 安全：**只在 `useEffect` 里读**（项目既定教训，避免首帧不一致） |
| 实时闸门 | 右侧常驻「过闸清单」：用 W-0 的 contract 逐条判定 ✅/❌，❌ 的那条写清「还差几个字 / 缺哪个字段」，而不是「校验失败」四个字 |
| 出口 | ①下载 `.json` ②复制到剪贴板 ③导出 Markdown（给 AI 用）④**导出 `tools/content/<id>.py`**（电梯：升格为一等公民，见 W-3） |
| 标识 | 私有内容一律带 `私有` 徽标；列表页入口在 `/blueprints` 顶部，与公有主线视觉分区 |
| **不入什么** | **不进九层 verify 的数字契约**（否则你每写一条就红一片）。这是刻意的：私有车道对自己的内容负责，不对仓库的契约负责 |

### 3.3 W-2 · 本地私有目录（换机器靠文件，不靠浏览器）

- 目录：`arsenal-cookbook-private/*.json`（`.gitignore` 加一行）**或** `~/.arsenal/blueprints/*.json`（完全在仓库外）—— 二者选一，见 §6 决策点 D-2
- `sync-content.mjs` 追加一步：扫描该目录 → 用同一份 `_contract.json` 校验 → 合并进 `src/generated/cookbook.json` 的 `privateTopics` 分支
- id 规则：必须 `private-` 前缀；与公有 id 冲突直接报错（防止你无意覆盖一条主线）
- 页面：同一套渲染器，顶部一条提示「这条不是仓库的一部分，不进 Git、不进校验」

### 3.4 W-3 · 脚手架生成器（`tools/new-blueprint.py`）

```bash
python tools/new-blueprint.py api-contract --tier A --family web
# → 生成 tools/content/api_contract.py（骨架，所有必填字段是 TODO + 文案要求）
# → 自动在 COOKBOOK_MODULES 里加一行
# → 立刻跑一次 build_cookbook 的校验，把「当前缺哪几条」打印出来
```

**「红着交给你」是特性而非缺陷**：骨架生成完必然不满足全部判据，打印出来的缺项就是写作清单。这样新主线的过程是「填空 → 看红 → 补全 → 变绿」，而不是「照着虚拟线程 946 行猜」。

### 3.5 W-4 · AI 草稿通道（P2，给 AI 用的一环）

- `ExportStudio` 增加一种导出：**案例库草稿 prompt**（含三层 schema + contract 全部判据 + 一条完整的一等公民主线当 few-shot）
- 你把这份 prompt 喂给任意 AI，产出 JSON，**粘回 W-1** —— 同一份判据立刻告诉你哪里不合格
- 为什么不直接调 API：**不绑某家 AI** 是三原则之一，也省掉密钥管理

## 6. 需要你拍板的三件事

| # | 决策 | 选项 | 我的建议 |
|---|---|---|---|
| **D-1** | 接不接受 **B 型（无实验）主线**为一等公民 | ①接受，配套 `doAndDont` 对照+机检 ②不接受，skeleton/test/collab 三类永不进案例库 | **①**。这三类恰是一个人最常丢分的日常规范；它们在正则引擎下其实**最好检**。现有代码本来就没拦 B 型，要改的只是门槛文档 |

## 7. 验收口径（照项目硬约定执行）

1. **每条新断言必须反着验**：故意改坏判据 → 断言必须红 → 还原 → 必须绿；注入后先确认「注入真的打中了」再跑检查。
2. **还原只认备份文件**：私有/调试产物用 `.verify/tmp/` 里的备份 `cp` 回来，不用 `git checkout --`（后者回到 HEAD，会把本棒未提交的改动一起抹掉）。
3. **数字四处同步**：`arsenal-profiles/arsenal.json` 的 `project.verifyChain[*].count`、README 总数句、README 分项表、跑一次 sync。漏了不静默（`finish()` 会「声明 X / 实测 Y」退出 1）。
4. **改 `.verify/**` 必须实跑** `npm run typecheck:verify`（它不在根 tsconfig 里）。
5. **同一文件多处改动必须串行**（并行 Edit 在本仓会静默丢改且 tsc 仍 0 错）。
6. 每条 A 型主线交付前：实验**必须在真 JDK 21 上跑通一次**，实测数字写进 `lab.baseline` —— 不许把会话里的数字当结论留在文档里。
7. **A 型的 `playground[]` 必须是纯 JDK**（无 classpath，见 N-8）；`files[]` 可以是 Spring 版。两者不一致时，要在 `note` 里写明「差异仅为框架写法，语义一致」。
8. `recipes[].files[].code` **只放 good 版**（既有硬约定），反例写进 `pitfalls` / B 型的 `doAndDont`。
