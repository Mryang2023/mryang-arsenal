## 3. 分类体系自检报告（回答「为什么分这几类、是否合理」）

### 3.1 正式结论：**现状 ABCD 不合理，必须重建**

三个维度搅在了一层：

| 维度 | 现状落在哪 | 问题 |
|---|---|---|
| **判据来源**（规则引擎 / LLM / 委员会） | A vs B 的分界线 | 这是「怎么检出来的」，用户不关心；他关心「要不要改、怎么改」 |
| **交付物**（优化方案 / 测试建议） | C vs D | 这是「给你什么」，和「问题是什么」不是一类东西，混在问题面板里让「四类问题」的错觉成立 |
| **严重度**（P0/P1/MAY） | 嵌套在 A 里面 | 语义 finding 的 MUST 徽标在 B 里、静态的 MUST 在 A 里——同一严重度被劈成两半 |

**您问「是问题的归属不同，还是严重度不同」——答案是：现在两个都不纯粹，是混的。** 而且 B 面板还同时兼任「问题清单」和「能力说明（三态披露）」两个角色，一个面板两种读法。

### 3.2 新体系：两个问题视图（正交）+ 两个交付面板 + 一张边界卡

```
┌─ ① 审查边界卡 ──────────── 这次查了什么 / 没查什么（全面性，回答意见 2）
├─ ② 问题区 ─────────────── 视图切换：[ 按严重度 ] [ 按规则 ]   ← 两个正交视图
│    ├ 按严重度：P0 必修 / P1 该改 / MAY 可选 → 档内按规则聚成组 → 组内逐条
│    └ 按规则：规则卡（标题 + 严重度 + 出处摘要 + 违反 N 处）→ 逐条 file:line
│    每条都可展开详情（问题 / 路径+复制 / 违反哪条 / 出处 / 后果 / 正例 / 规则页链接）
├─ ③ 审查能力与可信度区 ──── 语义层三态、实锤四档、委员会共识/孤证、LLM 记账
├─ ④ 怎么改（优化方案）──── 原 C 面板，移交即用
└─ ⑤ 怎么验（测试建议）──── 原 D 面板
```

**每个维度只回答一个问题，写进页面文案里**：

| 维度 | 回答的问题 | 分组依据 |
|---|---|---|
| 按严重度 | **先改谁** | MUST→P0 / SHOULD→P1 / MAY→可选（规则 severity 政策原文） |
| 按规则 | **怎么改省事** | ruleId 聚合——同规则违反 N 处，一次改一类 |
| 来源徽标（每条都带） | **这话可不可信** | 规则库（确定性）/ LLM（带置信度）/ 委员会（共识×N 或孤证）/ 实锤（跑红过） |
| 交付面板 | **改完怎么验** | 方案 + 测试建议 |

**两条纪律不动**：
1. 语义 finding **永不进 P0**、必带 confidence（既定纪律，P0 的可信度是解剖台立起来的，不能稀释）。语义 finding 在「按严重度」视图里按自己的 severity 徽标展示，但用「语义」徽标与静态档区分；实锤档（跑红过）给铜色徽标——那是「真的跑红了」，比置信度更硬。
2. 「没跑」「跑不完」「跑完没报」三态披露不变（`semanticStatus` / `reproTiers` / coverage 三态全部保留，只是从「一个面板」变成「一张说明区」）。

## 4. 数据契约变更（qaReport v1 → v2，向后兼容）

**原则：旧报告缺字段 → 前端 fallback 一句人话**（沿用 C1 实锤上线时的旧报告处理模式：「这份报告出在 XXX 之前」）。

### 4.1 finding 级新增（静态 + 语义统一形状）

```jsonc
"rule": {
  "id": "SEC-AUTH-001",
  "title": "涉及用户私有数据的接口必须校验资源归属，防水平越权",
  "severity": "MUST",
  "version": 1,
  "category": "security",
  "subcategory": "authorization",
  "sources": [
    { "ref": "阿里巴巴Java开发手册 安全规约 §1【强制】", "type": "industry-standard",
      "quote": "隶属于用户个人的页面或者功能必须进行权限控制校验…" },
    { "ref": "OWASP Top 10 · A01:2021 Broken Access Control", "type": "security-baseline" }
  ],
  "rationale": "登录校验只回答「你是谁」，不回答「这条数据是不是你的」…",
  "good": "@GetMapping(\"/order/{id}\")…"
},
"impact": "接口只要传对 ID 就能读到别人的数据——攻击成本是改一个数字。",
"impactSource": "rule-rationale"   // 或 "llm"（语义 finding 原话）
```

- `rule` 是**检查时点的规则快照**（join `RuleIndex`），不是前端现查——这样留档 JSON 自包含，且「当时的规则长什么样」可追溯（服务意见 9 的时序问题）。
- `impact`：静态档 = 规则 `rationale` 首句/全文派生，`impactSource: "rule-rationale"`，页面标注「出自规则制定理由」；语义档 = LLM 原话，`impactSource: "llm"`。**不编造**——规则没有 impact 字段，第一版就用 rationale 顶着，后续棒（Q4）给 69 条补真 impact。

### 4.2 报告级新增

```jsonc
"ruleset": {
  "version": "0.1.0", "releasedAt": "2026-09-11",
  "ruleCount": 69, "activeCount": 69, "llmLayerRules": 43,
  "loadedAt": "2026-10-16T22:30:00Z",     // 本次加载时间
  "filesNewestMtime": "2026-10-16T20:00:00Z"  // 规则库文件最新 mtime
},
"groupedByRule": [
  { "ruleId": "SEC-AUTH-001", "title": "…", "severity": "MUST",
    "tier": "static",                  // static | semantic —— 两个判据来源不混组
    "count": 3,
    "items": [ { "file": "src/main/java/…/OrderController.java", "line": 42, "finding": 0 } ] }
]
```

- `ruleset.filesNewestMtime > loadedAt` → 页面黄条：「规则库文件已变更但未重载，点此重载」——这把「明天用新规则」变成**用户可见、可一键执行**的动作，而不是一句承诺。
- `groupedByRule` **后端算**（拍板项 3，默认后端）：① 留档 JSON 直接可读聚合；② `collapsed`（引擎折叠计数）的语义只有后端知道；③ 前端少一套聚合逻辑就少一处口径打架。语义与静态分组不相混（`tier` 字段）。

## 11. 风险与提前说清

1. **B4 动共用出口**：`violationNode` 是 autopsy/qa 共用，加字段有响应体积与形状回归双重风险。缓解：默认 autopsy 一起吃（双赢），吃不下就降级为 qa 侧 join。**这是本计划唯一可能伤及现有功能的一步，排第一棒并先跑 autopsy 现有断言。**
2. **规则热加载的缓存死角**：LintEngine / CheckupEvaluator 若持有 `Rule` 对象或编译态跨 run 复用，refresh 后新旧规则会混。缓解：B3 先查证再改；查完在 `RuleIndex.refresh()` 里显式清空所有派生缓存；reload 端点返回「重载前规则数 → 重载后规则数」让变化可见。
3. **impact 派生自 rationale 是过渡**：rationale 是「为什么定这条规」，不总是「不修会怎样」。第一版页面标注 `impactSource`，不让派生内容伪装成真 impact——这是「诚实披露」纪律在内容层的落地。
4. **聚合视图与平铺视图的数字必须一致**：两个视图同源不同算法，count 打架就是 bug。验收写死：两视图逐档比对。
5. **`/qa` idle 页截图会变**（改名 + 文案）：视觉矩阵张数不变但内容变，`verify:visual` 必须重跑 + 人工看一眼，不许只信断言（断言只管几何，管不了「这个名字对不对」）。
