# 项目解剖台 · 升级计划书

**日期**：2026-10-11
**代号**：`/autopsy`（解剖台）
**一句话**：给一个项目地址（git / 本地目录 / zip），一键产出三样东西 —— **技术架构**、**不足清单**、**功能清单**；功能可单独剥离成能直接跑的新工程；每次分析存档，下次带着存档重跑只算变化的部分。

---

## 0. 先说结论：你要的四件事，有一件的后端已经是成品

调研完仓库现状，必须先纠正一个前提 —— **「一键分析技术架构」这件事，军火库后端已经做完了，而且是按你 SOUL.md 里那套「不许猜、命中必带证据」的标准做的。**

| 你想要的 | 现状 | 差距 |
|---|---|---|
| 给地址 → 分析技术架构 | ✅ **已完成**：`POST /api/scan/facts`（git / path）+ `/api/scan/upload`（zip），产出 `ProjectFacts` JSON | 前端**没有入口**把它变成一个能看的页面 |
| 分析哪些地方不足 | 🟡 **半成品**：69 条规则 + AST/正则双引擎 + `/api/lint` 已能判代码，但**只吃上传的源码**，且**判据是单条规则，不做「体检结论」** | 缺「体检层」：把 69 条判据汇总成一份体检报告 |
| 分析功能 | 🔴 **无**：`CodeScanner` 已抽出路由/分层/注解（`@Scheduled`/`@KafkaListener`/`@FeignClient` 等），但只当技术事实，没当**业务功能** | 全缺 |
| 功能单独剥离、随时可用 | 🔴 **无** | 全缺 |
| 分析结果存档 + 下次增量分析 | 🟡 **半成品**：`/arch` 的 `profile-store.ts` 有 localStorage 档案先例（且明确「别的项目的资料不进本仓」） | 缺「分析快照」这个概念本身 |

**所以这个计划的形状不是「造一个新功能」，是「把散在四个地方的成品收进一个台子，再补三块真缺的」。** 这是好消息 —— 风险最高的「解析任意项目代码」这一段，已经有 5 个 Scanner + 108 条依赖映射表在跑了。

**预计工作量**：6 棒，约 3400 行新增。P0 三棒（架构 + 体检 + 存档）就能让你用起来；功能分析 + 功能剥离是 P1，最大的一块。

## 1. 产品设计：解剖台是什么

### 1.1 一句话交互

```
填地址 / 选文件夹 / 传 zip  →  [一键分析]  →  三张结果页（架构 / 体检 / 功能）
                                    ↓ 每次点都留档
                        [历史] 列表  →  再分析 → 「与 10-09 那次相比：改了 3 处，多了 2 个功能」
```

### 1.2 四个面板

**面板 A · 架构解剖**
复用现有 `ProjectFacts` → `factsToPicks` → `buildTechArchSvg` / `buildLayeredSvg` 链路（`/archify` 已有完整实现 765 行）。
产出：技术栈部署图 + 应用分层图 + 跨带直连红线 + 未识别依赖清单。
**这就是现成的，只需要一个新页面把它接出来。**

**面板 B · 体检报告**（新，P0）
输入 `ProjectFacts` + 源码 → 输出三档结论，每条**必带证据**（文件+行号），没有证据的结论不许出现：

| 档 | 判据来源 | 例子 |
|---|---|---|
| **P0 必修** | 69 条规则里 severity=MUST/NEVER 的命中（50 条） | 跨带直连 Controller→Repository；无超时配置；事务内调远程 |
| **P1 该改** | SHOULD 命中（18 条） | 缺 `@Slf4j`；循环内查库 |
| **观察项** | facts 层推导（不是规则） | 单体但依赖 8 个外部服务；无 CI 配置；Dockerfile 无 healthcheck |

关键设计：**P0/P1 用规则引擎（复用 `/api/lint` + AST 层 42/69 覆盖），观察项用 facts 推导（不硬编码在 Java 里，写成 `arsenal-checkups/` 声明式 JSON）** —— 后者必须可扩展，否则「换个语言就得改 Java」。

**面板 C · 功能清单**（新，P1，最大）
把代码里的**技术单元**聚成**业务功能**。这一步最容易做成「假」，口径必须先定死：

```
一个功能 = 一组路由 + 它们调用的 service 方法 + 涉及的表 + 相关的前端路由
```

聚类的**唯一判据是调用闭包，不是命名相似**。理由：命名靠猜（`UserService` 里到底哪些是「用户管理」功能？），闭包是事实（这个路由的方法确实只调了这 5 个方法）。命名只能用来给功能起名字，不能用来划边界。

每个功能条目输出：

| 字段 | 内容 |
|---|---|
| 名称 / 一句话职责 | 起名字可以用命名推断，**但要标 `inferredBy: "name"`**，页面上显示为「据命名推断」 |
| 入口 | 路由列表（HTTP 方法 + 路径 + 文件:行） |
| 调用闭包 | service / repository / 外部客户端，文件:行 |
| 数据表 | 建表语句位置 |
| 依赖的功能 | 闭包相交时显式列出 |
| 完整度 | 是否有测试、是否有校验、有无异常处理、无入口的孤儿 |

**面板 D · 功能剥离**（新，P1，最难）
把选中的功能导出成**能直接跑的新工程**。

这是整个计划里唯一「输出物必须真能跑」的要求，判定标准借用装配台的 `export-lint` 五检查。剥离产物 = 一个 zip，内含：

```
<功能名>-standalone/
├── pom.xml          ← 只含这个功能真正用到的依赖（闭包推导，不是全量照抄）
├── src/…            ← 被闭包命中的类，去掉未命中的
├── application.yml  ← 只留用到的配置（按扫描到的配置 key 反查）
├── db/schema.sql    ← 涉及的表
└── README.md        ← 怎么跑 + 剥离时切断了什么（下面讲）
```

**剥离必须是诚实的**：功能 A 依赖功能 B 的一个工具方法，直接剥会崩。这份代码**不许假装能剥**，要输出「需要一起带走的 3 个外部依赖」清单，并给两个选项：连带剥离 / 替换为桩。**偷偷塞进半个 B 模块 = 产物编译不过 = 前面所有工作白做。**

## 2. 数据层：分析快照（这是「下次快」的关键）

### 2.1 快照存哪

**不进军火库仓库**（`profile-store.ts` 的注释已经立过这条规矩：别的项目的资料不该因为我们看一眼就被提交）。落 `arsenal-web/.data/autopsy/<projectId>/<snapshotId>.json`，加 `.gitignore`。

三档目录（沿用章程层已验证的三档模式）：

```
默认  arsenal-web/.data/autopsy/
覆盖  arsenal.json#project.autopsyDir
覆盖  env ARSENAL_AUTOPSY_DIR
```

### 2.2 快照长什么样

```json
{
  "schemaVersion": 1,
  "projectId": "d3f1…",          // 路径/git URL 的哈希
  "projectRef": "https://…/x.git",
  "snapshotId": "2026-10-11T20:10",
  "fingerprint": "sha256:…",     // 输入指纹，见下
  "facts": { …ProjectFacts 全文… },
  "verdict":  { "p0": 12, "p1": 31, "obs": 8 },
  "features": [ …功能清单… ],
  "summary":  { …人读的一页结论… },
  "toolVersion": "0.1.0"
}
```

### 2.3 「下次在原有基础上快速分析」怎么实现 —— 三级跳过

这是你明确要的，单独说：

| 级 | 判定 | 跳过什么 |
|---|---|---|
| L1 | 输入指纹**完全相同**（git HEAD + 未提交改动哈希 / 目录 mtime+size 树哈希） | 整个分析直接返回，秒回 |
| L2 | 指纹**部分相同**（只有 3 个文件改了） | 只重扫这 3 个文件；依赖图复用上次的；只有受影响的结论重算 |
| L3 | 指纹**完全不同** | 全量重扫，但拿旧快照做**对照**（下面） |

L2 的关键前提：**facts 与功能聚类必须能按文件粒度重算**。现在的 `ProjectScanner` 是整目录一把扫，`CodeScanner` 里的 `TreeMap` 聚合不支持增量 —— 这是 P1 要动的地方（聚类改成「每文件算局部贡献，再合并」，增量就是只重算变了的文件那部分贡献）。**这个改动不提前做，L2 就是假的。**

### 2.4 对照模式

每次分析自动和上一份快照比，输出四段变化：

```
技术栈  +Redis（pom.xml:58） -MyBatis（已删）
体检    P0 14 → 12   （修好 3 个，新增 1 个）    ← 每个都给出「哪一条、为什么算修好了」
功能    +「导出报表」  -「旧版导入」              ← 删除的功能要能看见
覆盖率  69 条规则覆盖 42 → 44
```

**「修好了」必须有依据**：靠 `violation` 集合的差集，并且要能点开看「上次命中在哪个文件第几行 → 这次那里没了」。否则「P0 少了 2 个」和「2 条规则今天没跑」在页面上长得一模一样（这是 10-04 踩过的坑）。

## 3. 实现计划（6 棒）

依赖关系：`棒1 → 棒2 → 棒3 → {棒4, 棒5} → 棒6`

---

### 棒 1 · P0 · 解剖台骨架 + 架构面板（复用为主）

**做什么**
1. 新路由 `/autopsy`，侧边栏「装配台」旁新增「解剖台」分组
2. 地址输入区（三种输入：git URL / 目录路径 / 拖 zip），复用 `arsenal-api.ts` 已有的 `scanFacts` / `scanUpload`
3. 架构面板：直接把 `ArchifyLab` 的 facts→IR→SVG 链路提出来接上（**不改它的算法**，ArchifyLab 765 行只做「拆出数据层 + 加壳」）
4. 未识别依赖清单（`unmatched` 直接展示，这是最有价值的「待补映射」入口）

**复用清单**（不新建的东西）
| 资产 | 位置 |
|---|---|
| 三种输入收敛 | `SourceResolver`（path/git/zip 一个接口） |
| 扫描编排 | `ProjectScanner` + 5 个 Scanner |
| 依赖映射 | `arsenal-scan/scan_rules.json`（108 条，47 条上画布） |
| 出图 | `arch-diagram.ts` / `arch-canvas.ts` / `archify-ir.ts` |
| 打包下载 | `zip-lite.ts` / `zip.ts` |

**验收**：填本仓地址 → 出技术栈图 + 分层图；填一个陌生 git 地址 → 不崩，未识别依赖列出来。

---

### 棒 2 · P0 · 体检报告

**做什么**
1. **源码通路**：新接口 `POST /api/autopsy/inspect`，把「本地/git 源码」喂给现有 `LintEngine`（现在只能传文件列表，要加「从 SourceResolver 读源码」这条路）
2. **声明式体检规则**：新建第 9 个事实源 `arsenal-checkups/*.json`，把「观察项」写成数据（`{when: {deps: {min: 8}}, then: {level: "obs", text: "…"}}`），Java 侧只写解释器
3. **三档报告页**：按档分组，每条带证据，点击跳到 `file:line`

**为什么检查器要数据化**：69 条规则是「写代码时的规矩」，体检结论是「这个项目整体健康度」，两者不是一回事，硬写进 Java 意味着换语言就重写。**数据化 = 加一条体检项不用重新编译。**

**验收**：拿军火库自己当被检对象跑一遍（自检是最好用的真实样本），出一份真报告；反着验：注入一条违规 → 报告红 → 还原 → 绿。

---

### 棒 3 · P0 · 快照 + 历史 + 增量 L1/L2

**做什么**
1. 快照读写层（三档目录）
2. 历史页：每个项目的快照列表，标注输入指纹、P0/P1/功能数
3. L1（指纹相同直接返回）+ L2（按文件粒度增量）
4. **对照模式**四段变化

**前置改造（必须做，否则 L2 是假的）**：`CodeScanner` 与功能聚类的聚合改成可按文件重算 —— 现在是 `TreeMap` 一把聚合，没法「只重算 3 个文件的贡献」。

**验收**：同一个地址点两次分析，第二次秒回且显示「无变化」；改一个文件再点，显示「只重扫 1 个文件」并给出该文件引起的变化。

---

### 棒 4 · P1 · 功能分析

**做什么**
1. 功能聚类器：**调用闭包**聚类（不是命名相似）
2. 功能清单页：入口 / 闭包 / 表 / 依赖 / 完整度
3. 孤儿检测：service 方法没有任何路由入口
4. 起名标 `inferredBy`

**风险（写明白）**：闭包推导靠的是正则抽调用（`CodeScanner` 现成），遇到反射、Spring 表达式、接口注入（`@Autowired` 字段拿不到调用点）会**漏边**。漏边 = 功能清单少算依赖 = 剥离产物编译不过。
**对策**：聚类结果里必须带一条 `unresolvedEdges`（找不到静态调用点的边），页面上显式列出「这条边靠猜/没解析到」。**宁可承认不完整，不要给一份看着完整其实漏了依赖的清单。**

---

### 棒 5 · P1 · 功能剥离（导出可运行工程）

**做什么**
1. 闭包 → 依赖裁剪（pom 只留真用到的；复用装配台已有的依赖推导思路）
2. 剥包器：类筛选 + 包名重写 + `application.yml` 按扫描到的 key 裁 + schema 抽取
3. **外部依赖诚实清单**（上面 1.3 讲的那条）
4. 复用 `export-lint.ts` 五检查当最后防线

**验收（硬标准）**：导出的 zip 解压后 `mvn -q compile` **真的能过**，启动能起来。这是唯一验收标准，「看着像能跑」不算。

---

### 棒 6 · P2 · MCP 工具 + CLI

1. `analyze_project`（给地址 → 三份结果）
2. `list_snapshots` / `diff_snapshot`
3. `extract_feature`（功能 → 可运行工程）
4. CLI：`arsenal-web/scripts/autopsy.mjs`，能进 CI 做「每次提交自动体检」

**为什么放 P2**：这套东西真正的长期价值在 CI（每次提交自动对比历史快照），但那要等棒 2/3 的判据稳定。先把交互跑顺。

## 4. 关键设计决策（怕以后忘了为什么这么定）

| 决策 | 理由 |
|---|---|
| 分析结果**不进 git** | 沿用 `profile-store` 已立的规矩；别的项目的资料不该进军火库 |
| 体检「观察项」**数据化**，规则判据**复用 69 条** | 两类判据性质不同，混在一起会让「加一条体检项」变成改代码 |
| 功能聚类用**调用闭包**不用命名 | 命名是猜，闭包是事实。命名只能用来起名字 |
| 剥离产物**必须报告切断了什么** | 偷偷塞半个依赖模块 = 编译不过 = 全白做 |
| 增量改造（棒3 里的聚类重构）**不能拖** | L2 依赖它，拖到最后 L2 就是个假的「快速」 |
| 「修好了」**必须能点开看依据** | 「P0 少了 2 个」和「2 条规则没跑」在页面上长得一样（10-04 踩过） |
| 每条结论**必带 file:line** | 仓库既有铁律：命中必带证据，没命中的进 unmatched，不许静默丢弃 |

## 5. 剩余工作量与风险

| 棒 | 估行 | 风险 |
|---|---|---|
| 1 架构面板 | ~700 | 低（复用为主） |
| 2 体检报告 | ~600 | 中（AST 层 42/69，27 条规则会 skipped，报告里必须显式写「27 条没跑」而不是省略） |
| 3 快照+增量 | ~800 | 中高（含聚类重构） |
| 4 功能分析 | ~700 | 高（反射/接口注入漏边） |
| 5 功能剥离 | ~900 | 高（产物必须真能编译） |
| 6 MCP/CLI | ~300 | 低 |

**总：约 4000 行（含测试与断言）。**

**三条我要提前说清的短板**
1. **功能剥离不可能 100% 自动**。反射、动态代理、配置驱动的调用链，静态分析就是看不见。设计上已经把「未解析的边」显式暴露出来了，但**首个版本的剥离成功率我估计 60-80%**，且失败是可解释的（告诉你缺哪个）。这是这个功能的天花板，不是实现质量问题。
2. **体检报告的「观察项」永远不完备**。69 条规则查的是「写法」，查不了「架构是否合理」「文档是否与代码一致」。观察项是补充，不是替代。
3. **P0 三棒做完你就能用**，但「随时可用的功能剥离」要等棒 5。如果现在就想要剥离，最省事的路径是：拿现成的 `arsenal-scaffold/*.tpl` + `arsenal-stacks` 按功能组一条装配台路线 —— 那是**已经能用**的东西。

## 6. 需要你拍板的三件事

1. **棒次优先级**：先做 P0 三棒（架构+体检+存档，够日常用），还是直接冲 P1 的功能剥离（你最想要但风险最大）？
2. **体检判据的严格度**：用军火库 69 条规则全套判（严格，但会挑出大量「项目本来就这么写」的项），还是先只判 MUST/NEVER 50 条？
3. **剥离的默认策略**：遇到外部依赖，默认「连带剥离」（更完整但可能拖出半个系统）还是默认「替换为桩」（干净但要手填）？
