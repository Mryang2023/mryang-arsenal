## 一、工作量裁定：**够，而且是过剩 —— 8 小时装不下，要砍**

这是最要紧的一句话：**问题从来不是"不够 8 小时"，而是"8 小时装不下"**。

| 计划 | 条数 | 单条估时 | 计划估时 |
|---|---|---|---|
| 1 · 验证体系 | 10 | 25–45 min | **5.5 – 7.0 h** |
| 2 · 引擎与 MCP | 10 | 25–50 min | **5.5 – 7.0 h** |
| 3 · 前端可达性 | 7 | 25–60 min | **3.0 – 4.0 h** |
| 4 · 事实一致性 | 7 | 20–45 min | **2.5 – 3.5 h** |
| 5 · 视觉与图形 | 6 | 25–60 min | **3.0 – 4.0 h** |
| **合计** | **40** | — | **19.5 – 25.5 h** |

**按章程公式倒着算**（公式与档位表见技能 `night-run` 的 `references/charter.md` §3.1/§3.2）：

```
可用窗口 525 min（23:10 → 07:55）
扣除     = 终检 40 + 交接 3×4=12 + 启动缓冲 10   →  463 min
单棒预算 = 463 / 4 工作棒 = 118 min
准入体量 = (118 − 20) / 1.5 ≈ 65 min 开发        ← 这才是「一棒装得下多少」的真实尺子
```

一棒 118 分钟里，**真实开发时间只有约 55 分钟**（一棒三段：开发 60% / 自检 20% / review 20%，收尾另算 20 分钟）。
→ **今晚的实际容量 ≈ 255 分钟开发 ≈ 7 条任务**（不是 17 条 —— 这是按公式倒算的结果，不是感觉）。
40 条后备按整棒口径折算 ≈ **30–38 h** → 8 小时能装下**不到四分之一**。

**所以排期的任务是「砍」，不是「凑」。今晚只装 7 条主任务 + 4 件备选。**

**这个数字不是估的**：2026-09-21 首次夜跑，四份「按一整晚设计」的方案塞进一个窗口，
每棒只分到约 2 小时（所需约 380 分钟的 1/3），结果**四条线全部只有半成品、无一条闭环**。
`NIGHT-RUN.md` 附表的原话是「排期必须倒着算，装不下就砍」。这次直接按 4 棒算。

**所以今晚的编排目标不是"多干"，是"每棒闭环一个能力"** —— 见 §二，五棒里没有一棒以"做了一半"收工。

> **并行的诱惑要顶住**：多开一条线看起来翻倍，实际会踩两处共享资源 ——
> `arsenal-web/.next` / `out/` / `.verify/tmp` 是同一份，两条线各跑一次 `next build` 会互相拆目录；
> `npm run verify` 八层也会抢同一批临时文件。**串行不是保守，是被文件系统逼的。**
> 唯一可行的并行形态：一条线只读已构建好的 `out/`（计划 5 的截图），另一条线改源码 ——
> 但两条都还要跑 `verify` 收尾，所以最多省半棒，风险却不小。**不建议。**

## 六、本次审查的补充发现（两份文档都漏了或排错了的）

1. **【真漏项】P0-3 的漂移 #3/#4 在两份文档里都只出现在 P0-3 正文，没有任何一行进入里程碑。**
   `engine.ts:105-107` 的 `normalizePath` 是单次 `replace(/^\.\//, '')`，而 `GlobMatcher.java:81-93` 用 `while` 去干净；
   glob 分支（`engine.ts:88-95`）不 `trim`，`GlobMatcher.java:68` 有 `.trim()`。已实测确认。→ 补为 **B-9**。
2. **【真漏项 · 最根的一处】JavaParser 纠偏清单漏了数据源本身。**
   实测：`arsenal-rules/**/*.json` 里 **20/20** 条 `check.ast.engine` 都写着 `"javaparser"`，
   而 `Rule.AstCheck.engineOrDefault()`（`Rule.java:84-86`）默认值也是 `"javaparser"`。
   两份文档只列了 README / UI / 注释，**没列规则数据**。
   只改 UI 不改数据 → 下一个人读规则 JSON 还是看到 javaparser。→ 补为 **D-3**（数据）+ **B-10**（默认值），**必须同批改**。
3. **【项数账目不一致】文件里同时存在 628 与 662。**
   `project-check.ts:512` 注释写「手写的 628」、`:517` 断言 `=== 662`；MEMORY.md 也记着 628。
   实测 `src/generated/profiles.json` 的 `verifyChain` 是 **35+59+406+33+17+12+31+69 = 662**，
   层序也与之不同（旧记录把「场景案例 33」排第 3、「代码扫描」记 35）。→ **以 662 为准**，628 与旧层序作废。
   A-4 做完后这两个数字都由实测得来，注释要一起清。
4. **【排错了】「删 `zip-lite.ts`」被放进里程碑 3（漂移），但它其实只能由验证层验收。**
   调用者是 `CaseLab.tsx` 与 `.verify/case-check.ts:30`，断言在 `case-check.ts` 里；
   要让 `case-check` 改测 `zip.ts`，必须同时改 `.verify/case-check.ts` 与 `src/lib/zip.ts` ——
   这两个文件分别落在计划 1（`.verify`）与计划 3（`src`）。→ 整条划给**计划 1**（所有权表已列例外白名单）。
5. **【口径冲突】5 条无检查器的 AST 规则，两份文档结论相反。**
   缺口清单排第 6「真实缺口」；体检文档里程碑 5 说「是刻意划出的边界，不是 bug」。
   → 统一为**待人工决策**（D-7），**不派 agent**。否则会有一个 agent 去硬做类型解析/符号表 —— 那是新增一个引擎。
6. **【漏了覆盖声明】`verify:scan` 有 2 项刻意未实跑**（500MB 总字节闸门、真等 180s 超时），
