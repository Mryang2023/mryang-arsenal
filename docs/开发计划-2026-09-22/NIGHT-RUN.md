## 一、性质与窗口

- 夜跑走 **23:00 → 次日 08:00** 这段夜间免费窗口。**硬停 07:55**。
- 这不是 N 条独立任务，是**一条接力链**。前一棒不交棒，后一棒不许开工。
- 窗口外的每一分钟都在扣积分。到硬线无论做到哪一步，立刻停止开新阶段，执行收尾并交棒。

**为什么必须串行**：多棒要改同一批文件（`sync-content.mjs` / `README.md` / verify 数字 / 共享类型）；
更要命的是 `.next` / `out/` / `.verify/tmp` 是**同一份构建产物**，两条线各跑一次 `next build` 会互拆目录。
两棒并行 = 互相踩烂，事后无法归因是谁改坏的。串行的代价是晚开工，并行的代价是静默损坏 —— 后者贵得多。

## 二、接力协议

### 开工（在读方案之前先做完）

1. 读 `night-chain\` 下已有的状态文件，先搞清现在到第几棒了。
2. **等前棒（最关键的一条）**：`<N-1>-done.json` 不存在 → **不许开工，不许碰仓库任何文件**，
   每 60 秒查一次，最多等到本棒硬线。
   - 等到了 → 正常开工。
   - 等不到 → 写 `<N>-blocked.json`（记录等了多久、前棒缺什么），
     然后**跳过本棒直接交棒**，把问题如实留给终检棒。
   > **绝不能和前棒并行改仓库。**
3. 建 `<N>-running.json`：`{ "棒次": N, "任务": "...", "开工": "<ISO>", "计划交棒": "<ISO>", "砍定范围": "..." }`
4. 第一棒不需要等待。

### 交棒

把下一棒的 `scheduledAt` 改成「现在 + 3 分钟」（用 `automation_update` 的 `mode="update"`，只传 `id` 与 `scheduledAt`）。
即使"现在 + 3 分钟"已经晚于下一棒的硬线，也照设 —— 让下一棒自己判断还来不来得及。
**下一棒的 automation id 写在各棒 prompt 的「第 7 步」里。**

## 三、一棒三段（缺一不可）

**一棒 = 开发 → 自检补漏 → Code Review。**
这不是"可选的最后两步"，这是**交付的定义** —— 没跑过自检和 review 的产出，不算这一棒做完了。

| 段 | 预算 | 对准 | 回答什么 |
|---|---|---|---|
| 开发 | 60% | 方案的实施计划 | 该做的做出来了吗？ |
| 自检补漏 | 20% | **方案**（要求） | 该做的都做了吗？有没有静默失败？ |
| Code Review | 20% | **代码**（实现） | 写得住吗？有隐患吗？和项目一致吗？ |

收尾另算（约 20 分钟），见 §四。**排期已把收尾算进单棒预算，不许把它当"可选的最后一步"。**

### 3.1 开发

- **开工先砍范围**，砍到开发预算内。方案原文按"一整晚"写，砍是正常操作，不是偷懒。
  砍完写进 `<N>-running.json`，收工时对照它交账。
- 前置依赖缺失 → **降级 + 如实记录，不许硬造**。
- 阶段化推进（数据 → 引擎 → 产物 → 页面 → 验证），每阶段做完立刻验收。
- **每棒 prompt 里写了「若提前完成的备选池」** —— 提前跑完就按序取**一件**，
  **不许自己找活干**（会撞文件所有权，见 §七）。

### 3.2 自检补漏（完整性）

**目标：找出"看起来完成、实际没完成"的地方。** 必做五件事：

1. **验收对照** —— 把方案/本棒 prompt 的「核心要求」逐条拉成表，标 ✅ / ⚠️部分 / ❌未做。
   **对照的是原文，不是自己的印象。**
2. **存在性核验** —— 声称新建的文件，`ls` / `grep` 逐个确认真的在。
3. **反着验 ≥2 处** —— 挑本次新写的闸门或断言，**故意注入错误**，确认真会红，然后还原。
   > 一条从没红过的断言，和摆设没有区别。
   > 首次夜跑只验了 2 组，闸门 ⑥⑦、断言【11】【15】、`verify:cases` 25 项、
   > `verify:scan` 恶意输入 7 项至今**未被证伪**。
4. **静默失败排查** —— 找"断言通过但样本量为 0"的检查（例：体积断言在文件数为 0 时"通过"）。
5. **引用核实** —— prompt 里引用的规则 id / 路径 / 依赖，去仓库查是否真实存在。

未完成项**先补**；补不完的写进清单，具体到文件 / 阶段 / 断言编号。

### 3.3 Code Review（质量）

审**本次改动的代码**（不审全仓），五个维度：

| 维度 | 查什么 |
|---|---|
| 正确性 | 边界值、空值、并发、错误路径、类型、异步时序 |
| 安全 | 注入、路径逃逸、敏感信息硬编码、权限、对外部输入的信任 |
| 性能 | 循环内 IO、N+1、无界集合、重复计算、不必要的同步 |
| 可维护性 | 重复代码、魔法数、命名、死代码、**残留调试代码** |
| 一致性 | 与项目既有范式 / 类型体系是否一致；有没有留下"功能等价但形态不同"的平行通道 |

每条按 `[P0/P1/P2] file:line —— 问题 → 根因 → 处置` 记录。
**P0 与便宜的 P1 当场修**，修完重跑验证；其余进清单并写明为什么没修。
不许把 P2 包装成 P1 凑数，也不许漏报。

### 3.4 段间门禁

| 关卡 | 规则 |
|---|---|
| 开发 → 自检 | `node node_modules/typescript/bin/tsc --noEmit` 或 `npm run build` 能过 |
| 自检 → Review | 无未修的 P0 完整性缺陷 |
| Review → 收尾 | 无未修的 P0 代码缺陷 |

> **不许带着已知的重病往下走。** 轻问题可以记账前行，重问题不行。

## 四、收尾清单（每棒必做，顺序不能反）

1. **跑全量验证**（`npm run verify` 八层，不是只跑自己改的那一层），记录真实数字与跳过的层。
   **没跑过就不能说它是绿的。**
   > 已知现象：单次会话内累计删除操作达阈值后，`build` 与 `parity` 的清理步骤会被沙箱守卫拦截。
   > **那是环境问题不是代码问题**，报告里要写清"哪一层被拦"。
2. **同步所有派生数字**（见 §六 铁律 3，四处），改完复跑一次确认生效。
3. **git commit** —— 本棒产出必须在收工前形成一次提交，message 用 `feat(scope): ...` 格式，
   确认没夹带调试产物。**一夜不提交 = 没有版本快照。**
4. **清理调试产物** —— `.workbuddy\_*` / `arsenal-web\.workbuddy\_*` / `.verify\tmp-*` 全删。
5. **追加 memory 日志** —— `.workbuddy\memory\<今天>.md`（append，不覆盖）。
6. **回滚判断** —— `build` 或 `verify` 比开工前更红且修不了 → **回滚到开工前状态**并在报告里说明。
   留一个坏状态比少做一个功能严重得多。
7. **写 `<N>-done.json`**（schema 见 §九）—— 必含 `开发` / `自检` / `review` / `验证` / `数字同步` / `提交` / `清理` 七组字段。
   `开发.未做完的` 不许写"部分未完成"，必须具体到**文件 / 阶段 / 断言编号**，能被一条命令核对。

## 五、终检棒

**唯一不写新功能的一棒。产出是「真相」+ 把摊子收拾干净。**

1. **等（但绝不并行）** —— 最后一棒没交棒就等到硬线，等待期间不碰任何文件。
2. **收集** —— 读 `night-chain\` 全部状态文件与各棒报告。
3. **独立验证（核心动作，不许只信状态文件）**：
   真跑 `npm run build` + `npm run verify`；声称新建的文件逐个确认；
   **闸门 / 断言故意写坏一次，确认真会红**（优先验从未红过的）；
   页面真挂上导航；四处数字真同步；memory 真写了；**git 真提交了、工作区干净**。
4. **补漏**（按优先级）：仓库不可运行 > verify 挂红 > 数字不同步 > 文档缺失 > 状态文件缺失。
   **不补**需要 30 分钟以上的新功能。
   **绝对不许**为了让报告好看而改结论、把"没做"写成"做了"、删掉挂红的断言。
5. **产出 `REVIEW.md`** —— 逐棒记「自述 vs 独立验证」+ **差异清单（逐条点名）** +
   补了什么 + 剩余工作量（**按离闭环的距离**排 P0/P1/P2，这份是下一晚的输入）。
   清理一次性状态文件，只留 `0N-done.json` 与 `REVIEW.md`。用 present_files 呈现。
6. **硬停** —— 到点无条件停止动手。窗口外每分钟都在扣积分。

## 九、`<N>-done.json` schema（棒与棒之间唯一的交接凭证）

字段**不许省略**，尤其 `自检` 与 `review` 两段。

