### 本次体检当场修掉的两个真问题

**（1）`topology.ts` 的 `void` 传参 —— 已修**

```
src/lib/topology.ts:619  o.push(row(['A', 'B', 'C'], cy - 6));    ← row() 返回 void
src/lib/topology.ts:664  o.push(row(['T', 'T', 'T'], cy - 14));
```

`row()` 自己往 `o` 里塞方块与连线、**没有返回值**，外面再套一层 `o.push()` 只会塞进一个 `undefined`。

它唯一的探测器是 `tsc`：

```
$ npx tsc --noEmit
src/lib/topology.ts(619,14): error TS2345: Argument of type 'void' is not assignable to parameter of type 'string'.
src/lib/topology.ts(664,14): error TS2345: ...
```

而 **`npm run verify` 全程不跑 `tsc`**（`package.json:24` 八层都是 `tsx`）——
只有 `next build` 会校验类型。已修，`tsc --noEmit` 现退出 0，`next build` 86 页全绿。

**（2）`src/generated/icons.json` 的陈旧快照 —— 已修**

首次跑 `verify:project` 报「孤儿: 18 个位图」。真相是 `arsenal-rules` 侧的同步产物过期：
事实源 `arsenal-icons/icons.json` 有 18 条 `bitmap`，而 `arsenal-web/src/generated/icons.json` 是 `bitmapCount: 0`。
跑一次 `npm run sync` 即对齐 —— **不是代码 bug，是「改了事实源忘了同步」**，也说明这套自检确实在干活。

### 结构性缺陷：八层里有三层在 Windows 上失效

实测 `bash` 解析到 `C:\Windows\System32\bash.exe`（WSL 桩），
`spawnSync('bash', ['--version'])` 返回 `status=1, error=undefined`，报 `execvpe(/bin/bash) failed`。
于是：

- `scan-check.ts:66` 的 `hasBash = bash.status === 0` → **判定为「没装 bash」并整层跳过**（`scan-check.ts:70,479-480`）；
- `parity-check.ts:137-142` 对同类缺件走 `check(..., false)` → fail → **退出 1**。

也就是说本机 `npm run verify` 的因果是：

```
verify:arch → graph → cases → project → engine → parity ✗(exit 1)
                                                       │
                        && 短路，后面两层根本不启动 ────┘
```

**1 层硬报错（parity），2 层静默空转（archify / scan）** —— 而 parity 恰好排在它们前面，把两个静默层遮住了。
只有单独跑 `npm run verify:scan` 才会看到它打印「0 项通过、0 项失败」然后**退出码 0**（已实测）。

装 Git Bash 并把 `C:\Program Files\Git\bin` 放进 PATH 后，八层全部可跑、全绿（本次体检即如此完成）。
但**「能不能验证」取决于 PATH 里哪个 bash 在前面**，这不该是自检的前提。

## 三、P0：验证体系在说谎（先修这三条）

### P0-1　两层自检「整层跳过」却退出码 0，且无 CI

**证据**

```
scan-check.ts:478-481    if (skipAll) { console.log('verify:scan —— 跳过…0 项通过、0 项失败。'); process.exit(0); }
archify-check.ts:92-98   if (!cli) { …'通过 0 项，失败 0 项，跳过 1 层（九项构图检查**未执行**）'; process.exit(0); }
archify-check.ts:445-446 if (!p.available) { check(`后端出图服务：跳过（${p.code}）…`, true, …); }   ← 跳过被计入 pass
```

实测退出码：**两层都是 0**（各自 0 条断言）。
全仓**无 `.github/`、无任何 CI**，唯一闸门就是开发者手跑。
仓库自己知道正确的跳过怎么写 —— `scan-check.ts:273` 的软链用例、`parity-check.ts:345-347` 的活服务体检、
`ArchifyProbe.java:114-118` 的 `guards.put("skipped", true)` 都**不把跳过算通过**，只有这两处例外。

**修法**
1. 跳过用**独立退出码**（建议 `2`），或必须显式 `--allow-skip` 才放行；`&&` 链上把「跳过」与「通过」分开表达。
2. 禁止 `check(..., true)` 表示跳过 —— 加一个 `skip(name, reason)` 单独计数（`archify-check.ts:446` 改用它）。
3. **把 parity 从 `&&` 链里解耦**，否则链子永远停在第 6 层，后面两层修了也跑不到。
4. 补最小 CI（GitHub Actions 或等价物），至少跑 `sync → tsc --noEmit → verify`。

**工作量 S + M　收益：验证体系的「绿」重新变得可信。**

### P0-2　AST 层解析失败静默空转，却仍计入「已执行」→ 报假的 100 分「合规」

**证据**

```java
AstEngine.java:129-132   Parsed parsed = parse(filename, content);
                         if (parsed == null) { return List.of(); }        // 失败与「没命中」不可区分
AstEngine.java:137-140   /** …解析失败（非 Java / 语法不完整）时整体返回空 ——
                          *   交还 LintEngine 如实归入 skipped，绝不伪造判定。 */   ← 调用方并未这么做
LintEngine.java:161      if (!astRules.isEmpty() && name.endsWith(".java")) { … }   // 非 .java 整层不跑
LintEngine.java:237      … compiled.size() + astRules.size() …                      // 却算进 executableRules
```

三种情况（提交 `.ts`、提交有语法错的 `.java`、`AstEngine` 解析失败）都是**无 finding、无 `SkippedRule`、无 note**，
而 `executableRules` 照样把它们算作「已执行」→ `POST /api/lint` 返回 `score 100 / 合规`。
**前端做法相反**（`engine.ts:174-187` 把非正则规则全塞进 `skipped`）—— 两端对同一规则池给出矛盾结论。

**修法**
- `parse()` 返回**带状态**的结果（成功 / 非 Java / 语法错 / 编译器缺失），`lintFile` 回传失败原因；
- `LintEngine` 为「因解析失败而未跑」的 AST 规则补 `SkippedRule(layer="ast", reason=…)`；
- `executableRules` **只算真的跑过的**；
- 把 `run.ts:130-134` 的「执行 + 披露 == 池子」守恒律**补到后端**（现在只断言了前端）。

**工作量 M　收益：`/api/lint` 的分数重新可信。**

  这本来就是「一份数据，三种出口」原则该有的样子。

**所以 README:377 的「MCP Server 适配层 · 项目成败关键 · 未完成」是过期结论。** 真正的问题有三个：
