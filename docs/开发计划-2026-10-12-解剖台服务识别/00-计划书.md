# 解剖台 · 服务识别升级计划书

**日期**：2026-10-12
**代号**：`/autopsy` 服务拓扑（services-topo）
**一句话**：让解剖台回答「这个项目有几个服务」—— 不是猜一个数字，而是把**每条服务声明连同它的出处**列出来，能合并的精确合并，合并不了的并排说清。

---

## 0. 结论先行：为什么现在剖不出服务数

用户原话：「连微服务有几个服务都没解剖出来」。读完扫描器全链路，确认这不是「精度不够」，是**四个断点**，每一个都有源码位置：

| # | 断点 | 证据（源码位置） | 后果 |
|---|---|---|---|
| 1 | **facts 里没有「服务」这个单位** | `ProjectScanner.java:21` 类注释「一个目录 → 一份 ProjectFacts」；`scan()` 产出 build/config/deploy/code/frontend/techStack 六段全是**跨目录扁平聚合** | 一个 8 服务的仓库和一份单体扫出来形状一样，只是数字大点 |
| 2 | **代码侧没有「可运行入口」概念** | `CodeScanner.java:31-35` 的 `WATCHED` 18 个注解里**没有 `@SpringBootApplication`**；全类无 `public static void main` 识别 | 连「有几个 Spring Boot 应用」都数不出来 —— 这是服务计数最硬的信号，却完全没读 |
| 3 | **部署侧读了却不关联** | `DeployScanner.java:92-120` `scanCompose` 只取服务名（且要求缩进**恰好** `servicesIndent + 2`，4 空格缩进的 compose 直接得到空数组）；`scanK8s:122-150` 每个文件**只取第一个 `kind`**，多文档 YAML（`---` 分隔，微服务仓库最常见写法）扫出 1 条而非 N 条 | compose/k8s 的服务声明明明就在文件里，读出来的永远是残缺的一份，且不与代码、构建、端口互相引用 |
| 4 | **代码事实无归属** | `CodeScanner.java:61-162` routes/clients/directCalls/packages 全部 TreeMap 扁平聚合，`routes[].file` 是唯一能回溯的字段，但**没有任何东西回答「这条路由属于哪个服务」** | 就算知道了有 4 个服务，也说不清每个服务的入口有哪些、调用了谁 |

另外两个既有缺陷是本计划的**顺带修复项**（不是新功能，是正确性）：

- `DeployScanner.scanK8s` 多文档 YAML 只认第一文档（断点 3 已述）—— 这是「剖不出服务数」的**直接成因之一**：服务都写在同一个 `all-in-one.yml` 里。
- `scanCompose` 的 `indent == servicesIndent + 2` 写死 2 空格 —— 扫不出服务时返回**空数组**，与「compose 里确实没有服务」在输出上长得一模一样（10-04 踩过的坑的同款：静默的 0）。

**好消息**：10-11 计划里「面板 A 架构解剖」的地基（5 个 Scanner + 事实 JSON + 前端纯函数派生层）是现成的，本计划**不新建扫描器、不改编排结构**，只做三件事：补信号、做关联、上面板。

## 1. 设计原则：诚实性落在这五个决定上

军火库的既有哲学（四种结局不许合并、命中必带证据、0 也是结论）落到「服务识别」上，就是这五条：

| # | 决定 | 反面写法（明确不做） |
|---|---|---|
| 1 | **服务数永远带出处**：「compose 声明 4 个 · k8s 声明 4 个 · 代码入口 3 个」三个数分开报，合并后的「识别为 4 个服务」单独报 | 只报一个「4」—— 那和猜没有区别 |
| 2 | **只精确匹配，不做名称归一化**。`order-service` 与 `order-svc`、`order` 并排展示，标 `matchedOn` | 模糊匹配/去后缀归一化 —— 猜错会把两个服务并成一个，**比不合并危险得多**（静默合并 > 显式冲突） |
| 3 | **模块 ≠ 服务**。Maven `<modules>` 是构建单元，k8s `kind: Service` 是网络声明，Dockerfile 是镜像构建单元，Helm chart 是打包单元 —— 四类都报告，都**不计入服务数** | 把 modules 数当服务数 —— 多模块单体直接虚报 5 倍 |
| 4 | **归属不了的如实进「未归属」桶**。路由/客户端/Dockerfile 匹配不到任何服务单元时，显式列出「N 条路由无法归属」，不静默丢弃 | 强行归给「最近的一个」—— 编出来的归属会一路传到交付文档 |
| 5 | **0 和 1 也是结论**。没有任何信号 → 「未发现服务边界信号（列清检查过哪些）」；只有 1 个 → 「单体：1 个运行单元」 | 没信号时报错、或画一个空图让人以为「没扫出来」 |

## 2. 信号清单：什么算「服务声明」

按证据强度分三级。**只有第一级进服务数**，第二三级是支撑证据：

### 第一级 · 运行单元声明（进 `services.declarations`）

| 信号 | 读取处 | 产出字段 |
|---|---|---|
| compose `services:` 每个键 | `DeployScanner.scanCompose`（扩展） | name / path / line / image / build / port（容器端口）/ dependsOn[] |
| k8s 工作负载条目 | `DeployScanner.scanK8s`（扩展：多文档拆分） | name / path / line / kind / replicas（`kind: Service` 等非工作负载条目也记录，由派生层按封闭 kind 集合区分） |
| 代码可运行入口 | `CodeScanner`（扩展，新数组 `code.entryPoints`） | className / package / file / line / runtime（`spring-boot` = 有 `@SpringBootApplication`；`main` = 仅 `public static void main`；`node-start` = package.json 有 `scripts.start`） |

### 第二级 · 支撑证据（不进服务数，用于关联与展示）

| 信号 | 现状 | 用途 |
|---|---|---|
| Dockerfile + EXPOSE | `deploy.dockerfiles[]` 已有 | 路径目录前缀与服务名精确相等时，挂为该服务的镜像/端口证据 |
| pom/gradle 构建单元 | `build.artifacts[]` 已有（artifactId + path） | 同上；`<modules>` 名字补记（现在只数个数，`BuildScanner.java:136`） |
| nginx upstream / proxy_pass | `deploy.nginx[].upstreams` 已有 | 提取 host token 与服务名精确匹配 → 「nginx → 该服务」边 |
| `server.port` | `config[].values` 已有（按文件） | 配置文件路径归属到服务后，作为该服务端口佐证 |

### 第三级 · 服务间调用边（进调用图，目标可空）

| 信号 | 现状 | 边类型 |
|---|---|---|
| `@FeignClient(name=…)` | `code.clients[]` 已有 target | feign 边；target 与服务名精确匹配 → 服务间；匹配不上 → 外部 |
| compose `depends_on` | 本计划补读 | depends_on 边（两端都是声明，最强） |
| nginx proxy_pass host | 见上 | ingress 边 |
| RestTemplate / WebClient | `code.clients[]` 有记录但 **target 恒 null** | 进「目标未解析」桶，如实计数，不猜 |

## 3. 数据契约（Java 只读事实，判断全在 TS 纯函数）

### 3.1 facts 新增一段（additive，不动现有字段）

```json
"services": {
  "declarations": [
    { "source": "compose", "name": "order-service", "path": "deploy/docker-compose.yml", "line": 8,
      "kind": null, "port": 8080, "replicas": null,
      "image": "acme/order:1.4", "build": "./order-service", "dependsOn": ["mysql"] },
    { "source": "k8s", "name": "order-service", "path": "deploy/k8s/order.yml", "line": 1,
      "kind": "Deployment", "port": null, "replicas": 3,
      "image": null, "build": null, "dependsOn": [] },
    { "source": "k8s", "name": "order-svc", "path": "deploy/k8s/network.yml", "line": 14,
      "kind": "Service", "port": null, "replicas": null, "image": null, "build": null, "dependsOn": [] }
  ]
}
```

`code.entryPoints[]`（新数组， additive）：

```json
{ "file": "order-service/src/main/java/com/acme/order/OrderApplication.java", "line": 9,
  "package": "com.acme.order", "className": "OrderApplication", "runtime": "spring-boot" }
```

**三条硬规矩**：
1. Java **不做任何跨源关联、不做 kind 过滤**（`kind: Service` 也如实记录，区分是派生层的事）—— 关联逻辑只有一个实现（TS），规避 10-04「判定逻辑两份实现」事故。
2. 读不到的值写 `null` 或留空数组，**不许兜底**（与 `replicaFact` 同款纪律：不默认 1、不默认 3）。
3. `deploy.compose[].services`（名字数组）**原样保留不动** —— 部署视角与服务视角两段并存，同一次 `scanCompose` 单一代码路径写出，无漂移；现有消费方（`facts-arch.ts:196`、`profile-draft.ts:176` 只用 length）零影响。

### 3.2 派生层 `buildServiceTopo(facts)`（TS 纯函数，唯一关联实现）

放在 `arsenal-web/src/lib/service-topo.ts`，与 `arch-layered.ts` 同款性质（零依赖、可单测、渲染器只读它的输出）：

1. **分组**：declarations + entryPoints 按 `name` 精确相等分组 → 服务单元（`sources[]` 带上每条声明，端口/副本多源冲突时两个值都列出、注明「图上取 X 因为 Y」，与 `applyReplicaFacts` 同款）。
2. **kind 过滤**：k8s 条目按封闭集合 `WORKLOAD_KINDS = {Deployment, StatefulSet, DaemonSet, Job, CronJob}` 区分工作负载/网络/其它（这是 K8s API 的封闭集合，不是本项目的「知识」，与 `arch-layered.ts` 的 `DATA_DIMS` 同性质）。
3. **路由归属**（两条精确前缀规则，标 `matchedOn`）：
   - `dir`：某声明的 path 目录是路由文件路径的前缀（`order-service/docker-compose.yml` ↔ `order-service/src/…/OrderController.java`）；
   - `package`：入口类的 package 点分前缀匹配路由文件路径中的包段（`com.acme.order` ↔ `…/com/acme/order/…`）。
   - 两条都不中 → 未归属桶，计数 + 列出。
4. **调用边**：feign/depends_on/nginx 三类，目标名精确匹配服务单元；匹配不上进「外部/未匹配」；target=null 的客户端进「目标未解析」桶。**没有证据不画边**。
5. **一致性结论**：各源数量并列 + 冲突清单（「compose 声明 4 个，代码入口只有 3 个 —— 第 4 个在仓库里找不到对应代码」），逐条带两侧证据。**这正是「4 vs 3」必须分开说的 10-04 教训。**

## 5. 明确不做（以及为什么）

| 不做 | 理由 |
|---|---|
| 名称归一化 / 模糊匹配（`order-service` ≈ `order-svc` ≈ `order`） | 归一化是猜；猜错把两个服务并成一个，比不合并危险得多。要合并，让用户在面板上手确认（未来项） |
| modules / k8s Service / Dockerfile / Helm chart 计入服务数 | 构建单元、网络声明、镜像单元、打包单位是四件不同的事。虚报一次，后面所有结论都不可信 |
| 解析 RestTemplate/WebClient 的目标 URL（常在 `${order.url}` 配置里） | 需要跨文件符号解析，单独立项；现在 target=null 进「未解析」桶，如实计数 |
| 猜网关 / 注册中心 / 配置中心角色 | 除非 `SpringCloudGateway`/`@EnableEurekaServer` 等注解真读到（增量项，不在本计划） |
| 服务**内部**的功能聚类 | 那是 10-11 棒 4（调用闭包聚类），仍未做，与本计划解耦：本计划到「服务单元 + 归属 + 调用边」为止 |
| L2 增量重扫 | 仍未实现；`buildServiceTopo` 是纯函数，将来增量天然可复用，但本计划不承诺 |
| Quarkus / Micronaut / NestJS 入口识别 | 首版覆盖 `@SpringBootApplication`/`main`/`node-start` 三种；其余信号加一行 WATCHED 式的识别即可，但不伪装「已覆盖」 |
| MCP 工具 `scan_services` | P2。fact 契约稳定、面板跑顺之后再出口子（MCP 工具数从 `arsenal-rules/mcp-tools.json` 现读，不写死） |
