# 解剖台 · 项目结构面板计划书

**日期**：2026-10-16
**代号**：`/autopsy` 架构面板第三卡（code-structure）
**一句话**：让架构面板在「技术栈部署图 + 应用分层图」之外回答第三问 —— **这个项目的代码是怎么摆的**：每个目录/包是干什么的、每个类是哪一层、每一层级的作用是什么。每条角色判定都带依据，判不出的老实说「未分类」。

---

## 0. 结论先行：为什么现在剖不出「项目结构」

用户原话：「架构面板里能看到技术栈部署图、应用分层图，我还需要一个项目结构 —— 每一块代码是做什么的，是工具类的还是系统服务，每一层级的作用是什么，按代码的结构展示。」

读完扫描器与派生层全链路，确认这不是「精度不够」，是**五个断点**，每一个都有源码位置：

| # | 断点 | 证据（源码位置） | 后果 |
|---|---|---|---|
| 1 | **facts 里没有「目录树」这个单位** | `CodeScanner.java:173-183` 只有 `packages[]`（包名前 3 段 + 文件计数）；`ProjectScanner.scan()` 的 `stats` 只有文件总数/字节总数/耗时 | 页面拿不到「arsenal-server/ 是干什么的、tools/ 是干什么的」—— 项目结构完全看不见 |
| 2 | **没有「哪个类是哪层」的记录** | `CodeScanner.java:150-151` classify() 逐文件算出 layer，但只 `merge` 进计数 Map，类名/文件/行号全部丢弃 | 分层图只会说「9 个 Service」，不会说「这 9 个是哪 9 个、分别在哪个包」 |
| 3 | **没有「工具类」这个概念** | `CodeScanner.java:262-281` classify() 的封闭分支只有 controller/service/repository/config/domain；类名后缀表里没有 Utils/Util/Helper/Tools | 「这块代码是工具类还是系统服务」答不出来 —— 这正是你要的 |
| 4 | **非 Java 文件只计数、不露面** | `CodeScanner.java:65` `if (!rel.endsWith(".java")) continue;`；`ScanGuard.TEXT_EXT` 白名单里 ts/tsx/js/py/md 都读内容，但没有任何结构产出 | 全栈项目（军火库自身就是）的前端/脚本/文档目录在 facts 里不存在，「项目结构」缺一半 |
| 5 | **层级释义没有唯一出处** | `arch-layered.ts` 的 `BAND_ORDER` / `BAND_NAME`（客户端/接入层/应用层/领域层/数据层）只服务于分层图 | 项目结构面板若自己写一套「层级作用」文案，就会出现「分层图说五带、结构图说六层」 |

**三个既有近似能力，都不是这个，别改用途**：

| 能力 | 答什么 | 为什么替代不了 |
|---|---|---|
| 功能视图（`call-closure.ts`） | 哪些类是一条功能链 | 类全集来自调用边，**没有调用边的类不在图里**；不答「这块代码是什么角色」 |
| 应用分层图（`arch-layered.ts`） | 有几层、每层几个类 | 聚合口径，**不落类名**；没有目录维度 |
| 服务拓扑（`service-topo.ts`） | 有几个服务 | 运行单元视角，与代码结构正交 |

**好消息**：分类机、五带词汇、产物挂载点、卡片骨架全是现成的 —— 本计划**不新建扫描器文件、不新建路由、不引新依赖**，只做三件事：补信号（Java 两条新数组 + 一个 util 桶）、做派生（TS 纯函数）、上面板（架构面板第三张卡）。

## 1. 设计原则：诚实性落在这五条上

军火库既有哲学（命中必带证据、四种结局不许合并、0 也是结论、判定逻辑只许一份实现）落到「项目结构」上，就是这五条：

| # | 决定 | 反面写法（明确不做） |
|---|---|---|
| 1 | **角色判定必须带依据**：注解（硬事实，`layerBy: "annotation"`）/ 类名后缀（推断，`layerBy: "name"`）/ 目录约定（推断，`layerBy: "convention"`）三种出处分开显示 | 只画一个「工具类」徽标 —— 误判了无从知道是猜的 |
| 2 | **分类机只有一份**：扩展现有 `classify()`（Java），派生层只做分组与展示，不 second-guess | TS 再写一个分类器 —— 10-04「判定逻辑两份实现」事故 |
| 3 | **层级释义复用 `arch-layered.ts` 的 `BAND_ORDER` / `BAND_NAME`**，不造第二套文案；加一条断言守「五带名逐字相等」 | 结构图自己写「控制层/业务层/数据层」—— 与分层图对不上，而两边都全绿 |
| 4 | **判不出的就是「未分类」**：注解、类名后缀、包名都对不上的类（含 `@Component` 杂项），单独一桶，计数 + 列出 | 把 `@Component` 类硬塞「应用层」—— 看着完整其实是编的 |
| 5 | **0 和空也是结论**：没扫到 Java 类（纯前端项目）→ 明说「未扫到 Java 类，以下为目录计数」；被闸门跳过的目录 → 树顶亮条说明跳过了什么 | 画一棵只有目录没有类的空树，让人以为「这个项目没有类」 |

## 2. 这个面板答什么（三问）

| 问 | 答 | 形态 |
|---|---|---|
| Q1 代码是怎么摆的？ | 一棵目录/包树，每个节点带文件计数；Java 目录下再列出类 | 可折叠树（HTML） |
| Q2 每一块代码是做什么的？ | 角色徽标：控制器 / 服务 / 仓储 / 配置 / 领域 / **工具** / 未分类，每个徽标带依据角标 | 徽章 + 依据小字 |
| Q3 每一层级的作用是什么？ | 层级释义条：复用五带词汇（+ 工具横切 + 未分类），每层一句「是什么」+ 这一层有哪些包 | 释义条 + 包列表 |

外加：**导出 Markdown**（tree 形态 + 徽标 + stats 头部），可留档、可贴文档 —— 与既有的「下载事实 JSON / 下载 SVG」同款出口。

## 3. 数据契约（Java 只读事实，派生全在 TS）

### 3.1 facts 新增两段（additive，不动现有字段）

**`code.classes[]`** —— 每个 `.java` 文件一条（既定口径：取文件中第一个类声明；同文件后续类不单列，扫描器本来就只认第一个）：

```jsonc
{
  "name": "StringUtils",                                    // 第一个类声明的类名
  "file": "src/main/java/com/arsenal/util/StringUtils.java",// 仓库相对路径
  "line": 12,                                               // 类声明所在行
  "package": "com.arsenal.util",
  "layer": "util",                                          // 封闭集：controller|service|repository|config|domain|util|null
  "layerBy": "name",                                        // annotation|name|package|null —— classify() 三档判据的出处，原样带出
  "annotations": ["@Component"]                             // 只收 WATCHED 里真出现的，与全局 annotations 计数同源
}
```

**`code.dirs[]`** —— 全量文件的目录计数（含非 Java，这是全栈项目「项目结构」的另外一半）：

```jsonc
{ "path": "arsenal-server/src/main/java/com/arsenal/scan", "files": 11 }
```

- 来自 `ProjectScanner.collect()` 已收集的 `ctx.files()`，一次 group by 父目录，**零新增 IO**；
- 被 `ScanGuard.skipDir` 跳过的目录（`.git` / `node_modules` / `target` / `build` / `dist` / `out` / `.next` / `bin` / `vendor` / `__pycache__` 等，见 `ScanGuard.java` SKIP_DIRS）**不在树里** —— 树是「读过的文件」，不是磁盘全貌，页面上必须这么说。

### 3.2 classify() 扩展（唯一改动点）

- 类名后缀表加封闭集 `Utils` / `Util` / `Helper` / `Tools` → `layer: "util"`。与既有 `Service`/`Repository`/`Controller`/`Config` 后缀同款性质：命名推断，`layerBy: "name"`，不是新发明一种猜。
- ⚠️ **行为变更**：`layers` 聚合会多出 `util` 键（仓库里真有这类文件时）→ `scan-check.ts:260-261` 既有期望值要同步；提交信息必须写明「layers 聚合新增 util 键」。
- **不加** `@Component` → layer 的映射：`@Component` 类是杂项，塞进任何一层都是猜 → 落到「未分类」，诚实。

### 3.3 三条硬规矩

1. **Java 只记录与分类，不关联、不过滤、不兜底** —— 读不到 layer 就是 `null`；`classes` / `dirs` 与 `layers` / `packages` 同一次 scan 单一代码路径产出，无漂移。
2. **派生层 `code-structure.ts`（新，纯函数）**：组树、上徽标、写释义、序列化 markdown。与 `service-topo.ts` / `call-closure.ts` 同款性质（零依赖、可单测、渲染器只读它的输出）。
3. **一致性由断言守**：`Σ classes[].layer` 按层逐键 === `layers` 聚合各键计数（同一函数同一趟的输出，不等就是漂移）。

### 3.4 形状同步清单（改 facts 必做，漏一处就漂移）

| 文件 | 要改什么 |
|---|---|

## 4. 派生层设计（`code-structure.ts`）

1. **组树**：`dirs[]` 为骨架（字典序，确定性），`classes[]` 按 `file` 挂到所在目录节点；目录节点带 `files` 计数 + `java` 类数。
2. **徽标**：`layer` → 中文名 + 依据（`layerBy`）；`util` 徽标固定带「据类名推断」角标；未分类单列一桶。
3. **层级释义**：复用 `BAND_ORDER` / `BAND_NAME` 五带 + `util`（横切：工具类，不属于某一业务层）+ 未分类；每带列出「这一层有哪些包」—— 按 `classes[].package` 前三段聚合，与 `packages[]` 同口径，不造新聚合。
4. **Markdown 导出**：tree 缩进 + 每节点一行（角色/计数），头部带 stats（文件总数 / 目录数 / 类数 / 截断亮条）。
5. **确定性**：所有集合排序固定，「同一份 facts 跑两次逐字段相等」进断言（与 `buildServiceTopo` 同款）。

**挂载点**：`autopsy-data.ts` 的 `buildAutopsy()`（L102）加第四个产物 `structure`，与 `built` / `layered` / `topo` 同款 —— 面板只画，不重算。

## 6. 判据（写死，自检时逐条核对）

1. `classes` 与 `layers` 聚合逐键相等（demo-repo + 军火库自身）
2. 三种依据（annotation / name / package）在徽标上分开可见；util 必带「据类名推断」
3. 未分类桶存在且计数正确；**不存在「所有类都分了层」的伪装**
4. 空 classes → 页面说「未扫到 Java 类」；目录被闸门跳过 → 树顶亮条列出跳过规则
5. 层级释义五带名与 `arch-layered.ts` 逐字相等（单一词汇表）
6. 纯函数确定性：同 facts 两跑逐字段相等
7. `npm run typecheck` 过 + `npm run verify` 全量绿（不是只跑自己那层）；视觉零溢出零 console 错误
8. 反着验 ≥2 处

## 7. 明确不做（以及为什么）

| 不做 | 理由 |
|---|---|
| 猜业务语义（「这是订单模块」） | 那是功能视图（调用闭包）与项目档案的职责；命名推断只能用来起名，不能划边界 —— 10-11 总纲已定 |
| 前端 ts/tsx 逐文件角色分类 | v1 前端只进目录计数；要分类是拍板项 1，且必须标 `inferredBy: "convention"` |
| 类 → 路由 / 调用联动 | 功能视图已有；v1 解耦，避免两个面板争着答同一个问题 |
| 逐文件代码行数（LOC） | 扫描器既定口径是「统计与位置」不是「度量」；要 LOC 是另一个议题 |
| UML / C4 类图 | 另一个量级；本面板到「树 + 徽标 + 层级释义」为止 |
| 新增 Java 文件 / 新路由 / 新依赖 | 扩展 `CodeScanner` + `ArchPanel` 内第三张卡，不新建（project-check 包齐备断言零改） |
| 补扫 node_modules 等被跳过的目录 | 闸门既定跳过；补扫等于把几万个依赖文件塞进事实 JSON |

## 8. 风险与前置债

| 风险 | 等级 | 对策 |
|---|---|---|
| `classify()` 加 util 改变 `layers` 聚合 → 既有断言红 | 中 | 棒 1 先 grep `scan-check.ts:260-261`；行为变更，提交信息写明「layers 聚合新增 util 键」 |
| `classes` / `dirs` 让 facts JSON 变大（2 万文件仓库最坏 ~数千目录 + ~万类） | 中 | `dirs` 只存目录计数（最小形态）；`classes` 每文件一条（既定口径）；UI 默认折叠深层；若实测超限再议「>10 层目录合并计数」并在页面明说 |
| 类名后缀误判（`UserUtils` 其实是业务类） | 中 | 徽标必带 `layerBy: "name"` + 「据类名推断」角标；误判可见可改，比没有徽标安全 |
| 目录约定表是「知识」，会过期 | 低 | 只收封闭知名约定（Maven 标准布局 `src/main/java` / `src/test/java` / `src/main/resources`），每行能指出处；不认识的目录只计数不标角色 |
| java 常驻不了 / spawn EBUSY | 低 | 真扫单条命令内完成；看到 EBUSY 先重试再判（硬约定 22），不写「沙箱限制」这类推断 |
| 与功能视图表面重叠（都列类） | 低 | 分工写进页面文案：功能视图答「哪些类是一条功能链」，本面板答「每块代码是什么角色」 |

**前置债确认**：本计划不触发 L2 增量所需的「按文件重算」改造 —— `classes` / `dirs` 天然按文件产出，将来自增可复用，但本计划不承诺。

---

## 9. 拍板三件事

1. **覆盖范围**：v1 只给 Java 类上角色、其余文件只进目录计数（推荐，与「工具类 / 系统服务」的原始诉求一致，风险最小）vs 前端目录也按约定上角色（`src/lib` = 纯函数库 等，标 `inferredBy: "convention"`）。
2. **交互形态**：架构面板内第三张卡 + HTML 可折叠树（推荐，信息密度高、可逐层展开）vs SVG 树图（可下载，与另两张图同形态，但交互差）。
3. **联动范围**：v1 不做类 ↔ 功能联动（推荐，与功能视图解耦）vs v1 就做（点开类看它参与的功能链，要动 `call-closure` 的消费方）。
