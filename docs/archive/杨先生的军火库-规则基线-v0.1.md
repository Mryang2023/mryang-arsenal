# 杨先生的军火库 · 规则基线 v0.1

> 2026-09-11 ｜ 62 条规则 · MUST 37 + NEVER 13 = 50 条强制级 · 9 大类 · 全部条目可溯源

---

## 0. 本次最重要的变更

**种子数据来源从「既有项目代码反推」改为「行业基准提炼」。**

原方案的问题：command-center 里大量代码本身就是 AI 生成的。用它反推，等于**把 AI 的毛病固化成我的规范**——我想要的恰恰是纠正它们，而不是复制它们。

新方案的逻辑：

```
行业基准（外部、经过时间检验的共识）
        │  提炼
        ▼
  候选规则池（约 200+ 条）
        │  四道闸门筛选
        ▼
  军火库规则（62 条）—— 这才配叫「我的规范」
```

**既有项目的代码不参与规则生成，只作为「合规度对照样本」。** 它的作用从「来源」降级为「靶子」。

## 2. 筛选方法论：四道闸门

候选池约 200+ 条，最终只留 62 条。每条都必须连过四关：

| 闸门 | 判据 | 淘汰示例 |
|---|---|---|
| **① 可判定** | 能写出明确的通过/违规判断逻辑 | 「代码要健壮」「注意性能」「命名要有意义」→ 淘汰 |
| **② 有示例** | 能写出具体的 bad / good 代码片段 | 「避免过度设计」→ 写不出统一反例 → 淘汰 |
| **③ 有可执行检查** | 能落到 regex / AST / LLM 判定三者之一 | 「架构要合理」→ 无法检查 → 淘汰 |
| **④ 与本项目相关** | 影响 Java 17 + Spring Boot 3 后端服务的实际代码 | 阿里手册中偏前端、偏 DBA 运维、偏分库分表的条目 → 第一期不收 |

**外加一条总量约束：MUST + NEVER 级总数硬上限 50 条。**
当前正好 50 条，已满。**后续新增强制级条目，必须先降级或删除一条。**

这条约束是刻意的，理由：规范超出人能记住的量就会变成没人遵守的摆设。你打开这个系统的目的不是「查手册」，而是「记住该怎么做」。

## 4. 既有项目的定位变更：从「来源」到「靶子」

原方案里对 command-center 的勘察数据，现在不再用于生成规则，而是作为**第一条基线**——用来测量「AI 写出来的代码距离规范有多远」。

由于规则来源已经外置为行业基准，这批数据现在有了一个更干净的用途：**它是规则的验收样本**。

| 规则 ID | 对应现状（2026-09-11 勘察） | 预期检出 |
|---|---|---|
| `WEB-CTRL-002` @Valid | 仅 5 / 54 个 Controller | 应检出约 49 处违规 |
| `SVC-TX-002` rollbackFor | 仅 3 个文件使用 @Transactional | 应检出事务缺失与参数缺失 |
| `REL-LOG-002/003` 日志 | LoggerFactory 仅 31 / 207 个文件 | 应检出无日志类 |
| `REL-EXCP-001` 空 catch | `catch (Exception` 出现在 76 个文件 | 应检出大量吞异常 |
| `CONC-POOL-001/002` 线程池 | `@Async` 0 处，线程池相关仅 2 处 | 并发体系基本空白 |
| `CONC-THRD-001` SimpleDateFormat | 需实测 | — |
| `DATA-SQL-001` 拼接 SQL | 需实测 | — |

**校验引擎的第一项验收标准就是：能不能把这张表里的已知违规全部找出来。** 找不出来说明规则写得不合格，而不是代码合格。
