## 三、一棒三段（缺一不可）

**一棒 = 开发 → 自检补漏 → Code Review。**
这不是"可选的最后两步"，这是**交付的定义** —— 没跑过自检和 review 的产出，不算这一棒做完了。

| 段 | 预算 | 对准 | 回答什么 |
|---|---|---|---|
| 开发 | 60% | 方案的实施计划 | 该做的做出来了吗？ |
| 自检补漏 | 20% | **方案**（要求） | 该做的都做了吗？有没有静默失败？ |
| Code Review | 20% | **代码**（实现） | 写得住吗？有隐患吗？和项目一致吗？ |

收尾另算（约 20–30 分钟，本仓库全量 verify 就要 7–15 分钟），见 §四。

### 3.1 开发

- **开工先砍范围**，砍到开发预算内。方案原文按"一整晚"写，砍是正常操作，不是偷懒。
  砍完写进 `<N>-running.json`，收工时对照它交账。
- 前置依赖缺失 → **降级 + 如实记录，不许硬造**。
- 阶段化推进，每阶段做完立刻验收。

### 3.2 自检补漏（完整性）

**目标：找出"看起来完成、实际没完成"的地方。** 必做五件事：

1. **验收对照** —— 把方案的「分阶段实施 / 验收标准」逐条拉成表，标 ✅ / ⚠️部分 / ❌未做。
   **对照的是方案原文，不是自己的印象。**
2. **存在性核验** —— 声称新建的文件，`ls` / `grep` 逐个确认真的在。
3. **反着验 ≥2 处** —— 挑本次新写的闸门或断言，**故意注入错误**，确认真会红，然后还原。
   > 一条从没红过的断言，和摆设没有区别。
   > 还原必须用 `git checkout -- <file>` 或写文件时带 `newline=''` ——
   > 用 Python 文本模式写回会把 `\n` 翻成 `\r\n`，内容一字未错但行尾变了（已踩过）。
4. **静默失败排查** —— 找"断言通过但样本量为 0"的检查（空跑通过）。必须点名。
5. **引用核实** —— 方案里引用的 id / 路径 / 依赖，去仓库查是否真实存在。

未完成项**先补**；补不完的写进清单，具体到文件 / 阶段 / 断言编号。

### 3.3 Code Review（质量）

审**本次改动的代码**（不审全仓），五个维度：

| 维度 | 查什么 |
|---|---|
| 正确性 | 边界值、空值、并发、错误路径、类型、异步时序 |
| 安全 | 注入、路径逃逸、敏感信息硬编码、权限、对外部输入的信任 |
| 性能 | 循环内 IO、N+1、无界集合、重复计算、不必要的同步 |
| 可维护性 | 重复代码、魔法数、命名、死代码、**残留调试代码** |
| 一致性 | 与项目既有范式 / 类型体系是否一致；有没有留下"功能等价但形态不同"的平行通道 |

每条按 `[P0/P1/P2] file:line —— 问题 → 根因 → 处置` 记录。
**P0 与便宜的 P1 当场修**，修完重跑验证；其余进清单并写明为什么没修。
不许把 P2 包装成 P1 凑数，也不许漏报。

### 3.4 段间门禁

| 关卡 | 规则 |
|---|---|
| 开发 → 自检 | 代码能编译 / 能构建通过（`node scripts/next-run.mjs build` + `npm run typecheck`） |
| 自检 → Review | 无未修的 P0 完整性缺陷 |
| Review → 收尾 | 无未修的 P0 代码缺陷 |
