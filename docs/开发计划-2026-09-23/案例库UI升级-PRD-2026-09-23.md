**原始需求复述**：把「最佳实践案例库」和「场景案例库」两个模块的 UI 大幅升级——**UI 多一些**。用户明确拒绝纯列表 / 纯文本流的页面，要求进阶的、非平凡的可视化（SVG 关系图、架构画布这个量级），但每一个新增图形都必须真的让人看清原本看不清的东西，不许为了画图而画图。

## 1. 产品目标

> **一句话**：cookbook 现在是一份「写得很好的文档」，cases 现在是一台「能算但没有仪表盘的机器」。这次升级把 cookbook 变成**可导航的结构图**（让人一眼看清一条垂直切片从入口到 SQL 怎么走、哪份代码在哪一层、哪条规则有代码证据），把 cases 变成**可解释的参数仪表**（让人在调参数之前就知道会牵动哪些切片、架构会怎么变、哪些参数组合根本不可行）。

拆成三个可判定的目标：

| # | 目标 | 现状（为什么要做） | 达标判据 |
|---|---|---|---|
| G1 | **让结构可见**：cookbook 详情页从「文档流」变成「一张图 + 按需展开的代码」 | 详情页 493 行，除列表页一条 `client → web → service → repo → sql` 标签链外**全程零图形**；包结构是等宽字符串数组，代码块按文件顺序罗列，要点是编号备注 | 详情页首屏出现至少 2 张由事实源数据算出的图（链路图、规则锚点矩阵），且图上的节点可点、可跳到对应代码 |
| G2 | **让参数空间可见**：cases 的参数与切片之间的因果关系从「黑盒」变成「可预判」 | 6 个 driver × 若干 level（hotspot-cache 参数空间 4×3×3×3×3×3 = 972 组合）与 8 个切片的命中关系**完全不可见**；用户只能逐个调参数、凭记忆对比 | 用户在不切换参数的情况下，能看到「哪些参数是我这个场景的真正分水岭」，以及「切到某个值会 +N/-M 个切片」 |
| G3 | **让不可行的也可见**（延续产品的「可信」灵魂） | 未命中切片虽有折叠区和 `notSuitable` 文本，但**为什么**不适用要逐个展开才知道；cross-driver 冲突只在命中后弹一条告警 | 任何「没有命中 / 没有代码证据 / 没有对比数据」的位置，UI 显式显示空态与原因，不静默省略、不装饰性补全 |

**明确的反目标**：本次不做「更漂亮的排版」。所有新增图形必须能追溯到具体字段（`flow[]` / `files[].layer` / `files[].highlights[].mark` / `relatedRules[]` / `drivers[].levels[]` / `slices[].when` / `slices[].decision`），追溯不到的图形一律砍掉（见第 6 节）。

## 3. 需求池

### 3.0 读前必读：两个「坑」，前端不要踩

这两条是从事实源里读出来的硬事实，会直接决定图怎么画：

1. **`flow[].layer` 与 `files[].layer` 是两套不同的词表**，不要当成同一套"层"去映射：
   - `flow[].layer`（**调用层**）：`client` / `web` / `service` / `repo` / `sql` / `concurrency`
   - `files[].layer`（**构件层**）：`web` / `dto-in` / `dto-out` / `service` / `repo` / `domain` / `exception` / `common` / `sql` / `config` / `integration` / `structure` / `test`
   - 且 **flow 不是单向链**：`crud-basic` 末步是 `web`（GlobalExceptionHandler，旁路回程），`async-transaction` 末步是 `client`（异步闭环）。**链路图必须支持回程边，不能只画一条直线。**
2. **`slices[].when` 可以是 `{}`**（如 hotspot-cache 的「缓存可观测与降级兜底」切片 `when: {}` = 无条件命中）。命中矩阵必须区分三种状态：**无条件命中 / 条件命中 / 未命中**，不能把 `{}` 当成"未命中"或"永远命中但未说明原因"。

## 4. UI 设计稿（P0 逐条）

> 统一约束：深色主题；容器用 `.panel`；图区底纹用 `.grid-bg`（34px 网格）；数字用 `.stat-num`；入场用 `animate-fade-up`；所有面板一律 `hairline-b` 分隔。**所有 SVG 一律手写（纯函数出字符串），不引图表引擎**（理由见 Q1）。

### 4.1 P0-1 · 垂直切片链路图（SliceFlow）

**位置**：cookbook 详情页，hero 之下、包结构之上的新区块，标题 `端到端链路`。宽度占满主栏（≥ 860px 时全宽；窄屏时图区横向滚动，不压缩字号）。

**布局**：纵向泳道 + 横向时间步。泳道由 `flow[].layer` 去重保序生成（crud-basic → `client / web / service / repo / sql`，5 条；`web` 在末步复用，不新增泳道）。


## 5. 非目标（本轮明确不做）

| 不做 | 原因 |
|---|---|
| 修改事实源内容（不改文案、不加 feature/case 条目、不重写 DDL/Java） | 内容链路独立，本次是 UI 增量 |
| 新增任何**评分 / 雷达图 / 健康度 / 推荐指数** | 无真值来源，编出来的分数违反「不伪造可信感」 |
| auto-fix / 代码自动修复、规则市场、多租户、后端、账号、埋点 | 产品明确不做的范围；纯静态导出 |
| 引入图表运行时依赖（D2 / Mermaid / Graphviz / ECharts / d3-force） | 见 Q1；且静态导出产物要小、SVG 要可选中可进 zip |
| 发明新颜色 / 加浅色主题 | 全站深色，token 已给定 |
| 把 cookbook 与 cases 数据合并，或统一两者的"层"词表 | 两个库分工不同（`flow` 调用层 vs `files` 构件层），强行统一会失真 |
| 移动端深度适配 | 桌面优先；窄屏只保证「图区横向滚动 + 面板折叠」可用 |
| 用动画/微交互博眼球（粒子、3D、视差） | 与「可信」的产品气质冲突，且遮挡信息 |
| 对 `performance` 参照表里的数值做二次推导/换算/图表化 | 只展示事实源原文数值，UI 不做插值或估算 |

## 6. 被砍掉或降级的方向（以及为什么）

| 方向 | 处置 | 理由 |
|---|---|---|
| 方案评分卡 / 雷达图（"这个方案 87 分"） | **砍** | 分数没有任何数据支撑，是本产品最不能碰的一类假可信感 |
| 力导向关系图（cookbook 的文件依赖图） | **降级：用 P0-2 的确定性文件树替代** | 依赖方向没有数据字段（`files[]` 无 imports/depends），只能靠猜包名猜依赖 → 图会撒谎。等事实源真有依赖字段再说 |
| 全参数空间三维立方体 | **降级到 P2-2** | 972 格在桌面屏上不可读；先上 P0-4 的二维矩阵看效果 |
| 场景间的统一评分对比 | **降级为 P1-1 的索引表** | 6 个场景 driver 语义不通用，强行归一就是伪造可比性 |
| 装饰性插画 / 大面积渐变 | **砍** | 用户要的是"看清原本看不清的东西"，不是"好看" |
| 自动推断切片↔架构节点的映射 | **改为显式数据字段**（见 Q2） | 推断结果无法验证，错了就是假证据 |

## 8. 与现有三原则的一致性检查

### 8.1 一份数据三种出口（给人查 / 给 AI 用 / 拿代码去验）

| 检查项 | 结论 | 具体保障 |
|---|---|---|
| 新增图形是否会制造「第二套数据」 | **否** | 每张图的数据源在 PRD 里写死：P0-1 ← `flow[]`；P0-2 ← `files[].path` + `highlights.length`；P0-3 ← `relatedRules[]` × `files[].highlights[].rule`；P0-4 ← `drivers[].levels[]` × `slices[].when`；P0-5 ← 现有 `case-synth` 输出 + `slices[].decision`。**禁止在前端组件里重排或补写任何业务数据** |
| 图形出口会不会吃掉文本出口 | **不会** | **P1-7 是硬配套**：每张图必须带「复制为表格」按钮，输出 Markdown 表格文本；SVG 源码并入 `zip-lite` 导出。原则：**没有文本出口的图不许上线** |
| 图的绘制逻辑是否可复用、可校验 | **是** | 与 `arch-diagram.ts` 同风格：纯函数 + 版式常量导出（供几何校验复用，避免"两份几何"漂移）。页面与导出器共用同一份真相 |
| 是否影响「拿代码去验」 | **不影响** | 本次不改规则数据、不改 `relatedRules` 语义；P0-3 只是把已有的 `highlights[].rule` 证据聚合可视化 |

### 8.2 Rule as Data

| 检查项 | 结论 | 说明 |
|---|---|---|
| 新增 UI 是否把规则逻辑写进代码 | **否** | 链路图层名来自 `flow[].layer`、文件层色来自 `files[].layer`、命中判定来自 `slices[].when`、冲突来自 `conflicts[].when` —— 全部读数据 |
| 唯一需要新增的"知识"是什么 | **两处映射** | ① `files[].layer`（构件层）→ `flow[].layer`（调用层）的关联；② 架构节点 ↔ 切片。这两处**必须声明为数据常量或数据字段**（见 Q2），**不许硬编码在 JSX 里或用正则猜** |
| 若加字段是否走完整链路 | **走** | 见 Q2 的四处清单：事实源 JSON → `tools/build-content.py` → `scripts/sync-content.mjs` → 前端类型定义 |

### 8.3 不伪造可信感（最关键）

| 风险点 | 处置 |
|---|---|
| **装饰性数字**：覆盖率 / 敏感度 / 命中数做成"看起来很专业"的数字 | 三个数字全部是**算出来的真值**：P0-3 覆盖数 = `highlights[].rule ∩ relatedRules` 去重计数，且 `X + Z = Y` 自洽校验失败时**红字报"数据不自洽"**而不是硬凑；P0-4 敏感度 = 真跑一遍 `when` 求值；P0-5 `命中 N` = 引用该节点的命中切片计数 |
| **静默省略**：为了让图好看而隐藏空白 | 反向要求：P0-3 的空格是**核心信息**（"这条规则声明了但没有代码证据"），必须可见；P0-4 的 `fgFaint` 斜纹明确区分"无关"与"不满足"，不合并成一种灰；`when:{}` 显式标 `无条件命中` |
| **编造解释**：架构节点 hover 出"为什么" | 理由**只引用 `decision.chosen` / `why` 原文**；拿不到时显示 `未标注原因`，**不生成看似合理的解释** |
| **假的可比性**：跨场景统一评分 | P1-1 明令不做评分，表头常驻声明"仅作索引，不构成可比评分" |
| **动画制造确定感**：diff 动画让人以为"系统会平滑演进" | diff 只展示**真实的节点集合差**，不插值、不预测；不显示任何"预计性能提升 X%" |
| **匹配失败时假装成功** | P0-1 节点匹配不到 `files[]` 时标 `fgFaint` 且**不可点**，浮层首行写 `无对应代码文件`；P0-5 面板无理由时写 `未标注原因` |
| **性能数值被图形化放大** | 非目标明令：`performance` 参照表数值不做二次推导、不插值、不图表化，只展示原文 |
| **数据异常被吞掉** | P1-5 若出现 `when` 为空却未命中，显示 `数据异常：无命中条件却未命中` 且不隐藏该切片 |
