# 解剖台 × 测试工程师 · 跃迁计划

**日期**：2026-10-13
**代号**：`/autopsy` × `/qa` 双台跃迁
**一句话**：这两个功能现在都是「读代码 → 出文字报告」的单向静态流水线；下一步不是补完旧计划的剩余棒次，是**换个物种** —— 从「代码阅读器」长成「项目的活体监护 + 改造工坊」。

---

## 0. 结论先行：先算旧账，再谈跃迁

### 0.1 现状核实（2026-10-13，以源码为准）

| 功能 | 已落地 | 未做（旧计划的剩余） |
|---|---|---|
| 解剖台 `/autopsy` | 架构面板 / 体检报告 / 服务拓扑 / 历史四页签；快照 + `diffSnapshots` 对照 + 指纹 L1 复用；服务拓扑 5 棒全完（`verify:scan` 112 项实测绿） | ① L2 按文件增量（CodeScanner 聚合重构，棒 3 前置债）② 功能分析（调用闭包聚类，棒 4）③ 功能剥离（可运行工程导出，棒 5）④ MCP/CLI（棒 6） |
| 测试工程师 `/qa` | M1 骨架（Job 状态机 + scope review/focus + 四面板）、M2 LLM 层（LlmClient 三档配置）、M3 语义深检（triage + 三态披露 + llmUsage 记账）、M4 大半（方案聚合） | ① `draftCases` 仍是 `putNull` 占位（QaService.java:557/582）—— 用例草案没生成 ② P2：MCP/CLI、Markdown 导出、PR 评论格式 |

### 0.2 一句话诊断

**这两个功能是同一个灵魂的两个出口。** 共用同一条「摄取 → 静态判定 → 报告」管道，差别只在 qa 多了 LLM 可选层和异步 Job。它们都停在 10-11/10-12 计划书的初始定义里 —— 一个**静态代码阅读器**。

### 0.3 所以这份计划的形状

不是「把旧棒次做完」（那是 L1 补课，见 §5 怎么消化旧账），是三个跃迁 + 一个合体：

| 跃迁 | 加什么维度 | 一句话 |
|---|---|---|
| **A · 活体解剖** | **运行时** | 不止扫代码，把项目**跑起来**，运行时事实与静态结论对账 |
| **B · 生命体征** | **时间** | 快照已有、diff 已有 —— 缺的是定时重扫、健康度曲线、断崖归因 |
| **C · 会动手** | **行动** | qa 从「说得对」到「做得到」：复现测试实锤、自动改造、PR 机器人 |
| **合体 · 数字孪生** | 全部汇成一个**可对话的活档案** | 「这个项目最大的债是什么」「和上月比烂在哪」 |

每条跃迁都写四件事：**是什么**（具体到对账表/界面）、**为什么现在敢想**（仓库里已有什么资产）、**最小第一步**（≤1 棒能验证的）、**诚实边界**（做不到的说清，不伪装）。

## 1. 跃迁 A · 活体解剖 —— 从「剖尸体」到「接活人」

### 1.1 是什么

解剖台现在扫的是**躺着的代码**。跃迁 A 让项目**站起来跑**，再把「声明」与「现实」逐条对账：

| 静态结论（现有） | 运行时采集（新增） | 对不上 = 什么 |
|---|---|---|
| 服务拓扑：3 个可运行入口 | `jps`/进程树：4 个 java 进程 | **幽灵进程** —— 有个没人声明的运行单元 |
| 单体：1 个入口 | 线程 dump：6 个线程池 / 3 个定时任务 | `@Scheduled` 僵尸任务在裸奔 |
| 配置 `server.port=8080` | `ss -ltn`：8080 真的在听 | 端口冲突/没起来 |
| `/actuator/health` 存在 | GET 它：DOWN | 声明了健康检查，现实是红的 |
| qa 判「事务内调远程」 | 日志里有远程超时堆栈 | finding 从「读代码猜的」变「**日志实锤的**」 |
| 说接口快 | 压一轮：P99 1.2s | 性能结论有了真人测 |

**产物**：`/autopsy` 新增第五页签「运行时」—— 上半页「声明 vs 现实」对照表（每行带两侧证据：静态 file:line + 运行日志行号），下半页真实进程/端口/定时任务清单。

### 1.2 为什么现在敢想（资产盘点）

| 资产 | 位置 | 用它干什么 |
|---|---|---|
| 可运行工程导出 | 装配台⑥交付，`mvn compile` 真过 | 「生成一个能跑的壳」这条路**已经通** —— 沙箱起进程的输入现成 |
| 可运行实验 | `arsenal-cases` 10 个实验，真起 HttpServer 假下游，不用 sleep 假装 IO | 运行时采集器的**范式**现成（起进程、探活、收证据、杀进程） |
| 纯 JDK 编译运行 | playground 纪律 | 不引外部依赖的沙箱执行能力 |
| 异步 Job 状态机 | qa 的 PENDING→…→DONE | 跑项目要分钟级，**同步接口撑不住**——qa 已经替活体解剖趟过这条路 |
| 规模闸门 | scan 的四闸门（单文件/深度/文件数/超时） | 沙箱执行同款：CPU/内存/墙钟上限，防失控 |

### 1.3 最小第一步（1 棒）

**「冒烟解剖」**：选一个 `runtime: spring-boot` 入口 → 沙箱起进程（JDK/mvn，带墙钟上限）→ 采三样：启动日志错误行 / 监听端口 / `/actuator/health` 状态 → 与 facts 对账，出一页「声明 vs 现实」对照面板。不追求通用，**先只支持 Spring Boot 入口一种**；其余入口类型如实标「该类型的运行时采集未实现」。

### 1.4 诚实边界

- **本机没有 Docker**：需要容器的项目跑不了，面板如实说「需要容器化沙箱，当前环境不支持」，不画饼。
- **需要 DB/Redis 的项目只能起一半**：能起进程、能采启动日志，但连不上依赖时的报错堆栈**本身就是证据**（「起不来是因为缺 mysql」也是结论）。
- **运行时采集器按入口类型分叉**：spring-boot / node-start 先做，Quarkus/NestJS 如实标未覆盖 —— 与入口识别的既有纪律一致，不伪装全语言。
- **执行不可信代码的安全模型是 P0 前置，不是可选项**：跑的是用户提交的源码。无网络、只读文件系统（除工作副本）、墙钟+内存双上限、采完即杀。这套没建好之前，活体解剖不上线。

## 2. 跃迁 B · 生命体征 —— 从「拍 X 光」到「戴监护仪」

### 2.1 是什么

快照有了、`diffSnapshots` 有了、指纹 L1 复用有了 —— **缺的只是「定时再拍一次」和「把多次连成线」**：

- **Watch 模式**：登记一个项目 → 每日/每周定时增量重扫（或 git push 触发）→ 什么都不用干，健康度自己长出来。
- **健康度曲线**：P0 数 / 服务数 / 覆盖率 / 技术债分量，四条可解释的时间序列。**算法必须可解释** —— 用四档计数拼，不许一个黑箱分数。
- **断崖归因**：「健康度 10-08 断崖」→ 自动定位到那天前后的提交 diff → 关联 qa 报告「那天起 P0 +3」。git bisect 式归因，全自动。
- **舰队视图**：多项目一屏排行榜 —— 哪条产品线在烂、谁在进步。**这正是你自己的痛点**：command-center、ProtoAI、arsenal 自身、auto_bm……一个人盯四条线。
- **预警**：跌破基线 → 亮红 + 通知（WorkBuddy 自动化体系现成，邮箱/IM 都能接）。

**产物**：`/autopsy` 第六页签「生命体征」—— 曲线 + 断崖标注 + 归因链接；舰队视图独立子页 `/autopsy/fleet`（舰队数据只在本机 `.data/`，不进 git 的纪律不变）。

### 2.2 为什么现在敢想

| 资产 | 状态 |
|---|---|
| `diffSnapshots` + fingerprint | 已实现，L1 复用已工作 |
| 三档目录配置模式（默认 < arsenal.json < env） | 章程层已验证成熟 |
| 定时自动化 | WorkBuddy automation 工具 + night-run skill 现成 |
| 断崖归因的数据前提（按文件粒度重算） | 正是旧计划「L2 增量」的前置改造 —— **旧债变成新计划的地基**（见 §5） |

### 2.3 最小第一步（1 棒）

**CLI 先行**：`arsenal autopsy watch <path> --every 24h`（Node 侧，复用 autopsy-fingerprint + autopsy-store）→ 每次重扫落一条序列点 → 一条 P0 曲线渲染。先 CLI 后 UI：夜跑里就能验证「定时增量真的只重扫变了的文件」，不用等页面。

### 2.4 诚实边界

- **时间序列存哪**：`.data/autopsy/` 不进 git 是既有纪律，舰队视图跨项目的数据同样只在本机 —— 「换电脑失忆」是已知代价，页面写明。
- **健康度指数不许黑箱**：四个分量（P0/P1 计数、覆盖率、服务稳定性、未归属比例）全部可解释，公式写在页面上。
- **断崖归因的上限是 git 粒度**：没进 git 的改动归不了因，如实标「该区间无版本控制证据」。

## 3. 跃迁 C · 会动手的测试工程师 —— 从「说得对」到「做得到」

qa 现在给的是**文字**：before/after 方案、测试建议。跃迁 C 让结论**可执行、可验证、可交付**。

### C1 · Bug 实锤化 —— 从「我猜这里有 bug」到「我复现了它」

- finding → LLM 生成 JUnit 复现测试 → 沙箱编译运行 → **测试红 = 实锤**（附失败堆栈作证据）。
- 语义 finding 从此分两档：**「有复现」**与**「待确认」**。置信度从「模型嘴里的 0.8」变成「我真的跑红了」—— 这是语义层可信度的质变。
- `draftCases` 占位（QaService.java:557/582）在这里被**消化**：用例草案从「文字建议」升级为「可运行复现」。
- **边界**：并发 bug 的复现测试本身可能 flaky —— 如实标「复现率 3/10」，不假装稳定；复现不了的 finding 留在「待确认」，不进实锤档。

### C2 · 改造工坊 —— 代码时光机

- 选一个改造目标（「升 Spring Boot 3」「上虚拟线程」「切走 MyBatis」）→ qa 逐点方案 → LLM 在 git worktree 里应用 → **前后各跑一次审查 + 全套测试** → 「P0 14→2、测试 47 绿」才交付一个 diff/分支。
- 改造过程像游戏进度条：每一步前后对照、可单步回滚。**每一步给人确认** —— 全自动改造是危险机器，首版是「人踩油门、机器干活」。
- **边界**：首版只自动应用「规则 good 片段可机械替换的项」（有 before/after 的才自动改）；需要设计决策的项只出方案不动手。与「剥离」的关系见 §5。

### C3 · PR 机器人 —— 审查员进 CI

- 两步走：**先 CLI 进 CI**（push 后 CI 调 `qa.mjs`，只审 diff，报告贴进流水线产物）→ 再 webhook 形态（Gitee/GitHub PR 评论 + 门禁）。
- 第一个客户就是你自己：ProtoAI 就在 Gitee 上。
- **边界**：webhook 要公网入口，先做 CI 形态（无公网依赖）；「只审 diff」需要行级映射（diff 行 → findings），复用 scope 的 glob 匹配器，不新建第二套。

### C4 · 审查员委员会 —— 三个审查员交叉审

- 安全审查员 / 性能审查员 / 并发审查员，三个 prompt 并行审同一批 triage 文件 → **交叉验证**：只有 1 个报的标「孤证」，2+ 个报的标「共识」。
- 孤证 ≠ 误报，只是置信标注 —— 与「语义 finding 必带 confidence、不进 P0」的既有纪律一致。
- **边界**：token 成本 ×3，预算闸门必须先于功能上线（复用 qa 已有的预算记账，扩成三份账）。

## 4. 合体 · 项目数字孪生

```
   静态层（facts + 69 规则 + checkups）────────── 现有
   语义层（LLM findings + 复现实锤）────────── C1
   运行时层（进程/端口/日志/health 对账）──── A
   时间层（快照序列/健康度曲线/断崖归因）──── B
   行动层（改造 diff / PR / CI 门禁）─────── C2/C3
                    ↓
        ┌─────── 数字孪生档案（一个项目的活档案）───────┐
        │  对话问诊：「最大的债是什么」「和上月比烂在哪」  │
        │  「剥一个服务要动多少类」                        │
        └──────────────────────────────────────────────┘
```

- **对话问诊**：对着档案问自然语言。资产：LLM 层已在 qa 落地、档案结构（快照 JSON）现成、军火库自己的规则/案例/checkups 就是最好的 RAG 语料。
- **军火库 dogfooding**：把「军火库健康仪表盘」做成 `/autopsy` 默认页 —— 自身 + command-center + ProtoAI 三项目常驻监护。**工具有了自己的生命体征，「杨先生的军火库」才真的活了。**
- 功能视图（「剥一个服务要动多少类」）依赖调用闭包聚类 —— 又一处旧债被消化（见 §5）。

## 5. 旧账怎么消化（不扔、不重复造）

| 旧计划的剩余 | 去哪了 | 关系 |
|---|---|---|
| 解剖台 L2 按文件增量 | **并入 B（生命体征）** | watch 模式的前置正是按文件重算 —— 旧债是地基 |
| 功能分析（调用闭包聚类） | **并入数字孪生 + C3** | 孪生的「功能视图」要它；PR 机器人审 diff 也要「这个改动影响了哪些功能」 |
| 功能剥离（可运行工程导出） | **并入 C2（改造工坊）** | 剥离 = 改造的特例（「把所有外部依赖切掉的改造」）；harvest 清单复用「外部依赖诚实清单」设计 |
| MCP/CLI 出口 | **每个跃迁各带自己的出口** | 不再单列一棒；`watch` 先 CLI，`qa` 审查进 CI 先 CLI，MCP 等 fact 契约稳定后再出 |
| qa `draftCases` 占位 | **并入 C1（复现测试）** | 用例草案从文字建议升级为可运行实锤 |

**这份计划最诚实的地方**：不吹「全新的」。五个旧债一笔都没扔，每一笔都找到了更高的去处 —— 补完旧棒次是 L1，把旧棒次消化进新物种是 L2，我们做后者。

## 6. 建议顺序（按「最小第一步」逐个验证，不排夜跑）

| 波次 | 内容 | 依赖 | 为什么这个顺序 |
|---|---|---|---|
| 第 1 波 | **B 的 CLI 先行**（watch + 曲线 + L2 增量改造） | 无（diff/fingerprint 已工作） | 最稳、天天可用、顺带把旧债 L2 做掉；CLI 在夜跑里就能验证 |
| 第 2 波 | **A 的冒烟解剖**（spring-boot 入口 + 沙箱安全模型） | 沙箱安全模型先于功能 | 最炫但受环境限制；安全模型（无网/只读/双上限/采完即杀）是 P0 前置 |
| 第 3 波 | **C1 复现实锤**（draftCases 消化） | LLM 层已通 + JDK 沙箱（A 的副产物） | 语义层可信度质变，且依赖已就绪 |
| 第 4 波 | **C3 PR 机器人（CI 形态）** | 闭包聚类（孪生前置） | 有了实锤 + 归因，CI 门禁才有人信 |
| 第 5 波 | **C2 改造工坊 + C4 委员会 + 孪生对话** | 前三波的地基 | 最贪心的一波，放最后；每项都可独立裁剪 |

---

## 7. 需要你拍板的四件事

1. **优先级**：第 1 波先走 B（稳、可用、消化旧债）还是直接冲 A（炫、受沙箱限制）？我的建议：B 先行，A 并行备料。
2. **沙箱安全模型的尺度**：允许在军火库服务器上编译运行**用户提交的代码**（一次性、无网、只读、双上限、采完即杀）—— 这是 C1 和 A 的共同地基，尺度定多大决定这两个跃迁的天花板。
3. **舰队视图的范围**：只监护军火库自己，还是把 command-center / ProtoAI 也拉进来当常驻样本（数据只在本机 `.data/`，不进 git）？
4. **数字孪生对话的 LLM 预算**：复用 qa 三档配置即可，还是单独预算闸门（C4 委员会 ×3 成本）？

## 8. 风险（说在最前）

| 风险 | 等级 | 对策 |
|---|---|---|
| **java 在本 harness 常驻不了**（run.sh 约 35s 静默死、start-server.mjs 没能救活） | 高 | 活体解剖的沙箱先解决「起进程」再排功能；已有可用的探活姿势（启动+sleep 13+探活+kill 同一条命令）先复用验证 |
| **跑用户代码 = 执行不可信输入** | 高 | 安全模型是 P0 前置不是可选项（§1.4）；没建好不上线 |
| **LLM 成本**（C1/C2/C4 都是 token 大户） | 中 | 预算闸门先于功能（复用 qa 已有记账扩份）；超限记 skipped 并披露，不静默丢 |
| **范围贪婪**（四个跃迁一夜做完=四个都半吊） | 中 | 每个跃迁只认「最小第一步」；第一步 ≤1 棒，验证了再展开 |
| **健康度曲线误导**（指数设计不好比没有还糟） | 中 | 四分量全可解释、公式上页；先看曲线再谈预警 |
| **改造工坊的安全感**（自动改代码吓到人） | 中 | 每步人确认 + git worktree 隔离 + 单步回滚；首版只机械应用有 before/after 的项 |

---

## 9. 一句话收尾

这两个功能已经证明了「军火库能诚实地说出一个项目哪里不好」。跃迁之后要证明的是另一半：**军火库能盯着一个项目变好，并能动手让它变好。** 前者是 X 光机，后者是监护仪 + 手术台 —— 计划书写的是怎么从前者长成后者。
