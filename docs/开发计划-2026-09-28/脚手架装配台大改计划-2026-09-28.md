## 0. 决策先行

| 项 | 结论 |
|---|---|
| 定位 | 菜单「装配台」改名**「脚手架装配台」**，定位从「选型 → 导出后端脚手架」升级为「选型 → 填环境 → 挑模块 → 导出**前后端两个可直接启动的项目包**」。 |
| 真问题 | 导出包起不来的根因不是玄学，是**主 `application.yml` 里根本没有 `spring.datasource` 配置**（证据 E-1/E-2/E-3），加上 schema.sql 不会被自动执行（E-4）、UI 没有让用户填数据库连接的地方（E-3）。「开箱即跑」目前是 README 里的口号，不是事实。 |

| 前端基底 | 新增前端技术栈维度：**Vue 3 + Vite + TS + Element Plus + Pinia + Axios 为 v1 完整交付**；React + Ant Design 在选择器中**预留位（灰显标「规划中」）**，v2 落地。选「无前端」则纯后端包。 |
| 环境配置 | 新增「环境与连接」步骤：选了数据库就**必填**地址/端口/库名/账号/密码，Redis/MQ/Nacos 按选型出现对应表单；值**烘焙进生成物**（dev/local profile），prod 仍走 `${ENV_VAR}`。另有**「演示模式（H2 内存库）」开关**：啥都不填也能启动。 |
| 功能模块 | 新增「功能模块」步骤：**用户管理、角色权限（RBAC）、菜单管理**三个模块 v1 交付（对应点名的用户/系统/菜单模块），每个模块 = 后端接口 + 前端页面 + 建表 SQL + 菜单种子数据，导出即可用。操作日志/字典管理入 backlog。 |
| 菜单导航 | **仍走单一菜单入口**「脚手架装配台」（向导是线性流程，拆菜单会打断上下文），靠 StepRail 步骤条承担导航；「模块库」独立浏览页入 backlog。 |
| 生成位置 | **继续前端生成**（离线优先是仓库刻意设计），后端只做两个可选增强：测试数据库连接、导出包编译冒烟（都走 arsenal-server，服务离线则优雅降级）。 |
| 分期 | **阶段 0 止血（让现有包先能跑）→ 1 环境配置+双包 → 2 前端模板+模块体系（最大块）→ 3 质量链路 → 4 backlog**。总计约 9–13 个工作日。 |

## 1. 本次实测证据

| # | 现象 | 证据位置 | 影响 |
|---|---|---|---|
| E-1 | **主 `application.yml` 无任何数据源配置**：`renderYaml()` 的 head 只有 `server` / `spring.application.name` / `lifecycle` / `logging`；`stack.json` 里 `database`（mysql/postgres）、`persistence`（jdbc/mybatisplus/jpa）、`migration`（flyway/liquibase/none）、`cache`（redis）**全部选项的 `yamlBlocks` 实测均为 0** | `lib/stack.ts:330-367`；`arsenal-stacks/stack.json`（python 解析实测） | 本地 `mvn spring-boot:run` 时 Spring Boot 自动装配 DataSource，classpath 上既无 URL 也无内嵌库 → **启动直接失败**。这就是「导出之后不能正常启动」的第一根因。 |
| E-2 | **`application-dev.yml` 同样没有 datasource**，只有日志级别、mybatis-plus SQL 日志、springdoc 开关 | `lib/project.ts:566-592` | 就算用户想本地跑，dev 配置也帮不上忙。 |
| E-3 | **唯一有 datasource 的是 `application-prod.yml`，值全是 `${DB_URL}` / `${DB_USERNAME}` / `${DB_PASSWORD}` 环境变量占位**；README 启动指引让用户自己 `export` 这三个变量；而装配台 UI **没有任何填写连接信息的界面**（七步向导无 Env 步骤） | `lib/project.ts:504-565`；`arsenal-stacks/project.json → files.readmeStartMaven`；`StackComposer.tsx` 全文 | 连接信息要么起不来、要么靠用户手敲环境变量，「填写的信息很少就能用」不成立。 |
| E-4 | **`migration=none` 时 `schema.sql` 落在 `src/main/resources/db/schema.sql`**，而 Spring Boot `spring.sql.init` 默认只认 classpath 根的 `schema.sql`；生成物里也没有 `spring.sql.init.mode` 配置 | `project.json → scaffold`（db/schema.sql）；`lib/project.ts` | 不执行 → user 表不存在 → 示例接口全部 500。选了 Flyway 且数据库没起时，迁移失败同样挡启动。 |
| E-5 | **导出只有单包**：`handleExport()` 打 `${name}-${kind}.zip` 一个包，包内只有 Spring Boot 工程；**没有前端工程**，README 所谓「接着写业务」对前端开发者是断头的 | `StackComposer.tsx:727-732`；`lib/project.ts buildExportPlan` | 与「导出前后端两个包」的目标差一个完整维度。 |
| E-6 | **业务代码固定不可选**：`scaffold` 是 30 个文件的固定清单，只有 user 示例六件套（README 自己说「新领域照它抄」）；没有模块勾选，没有角色/菜单/RBAC | `arsenal-stacks/project.json`（30 项实测） | 「搭建时就把用户模块/菜单模块设置好」无承载点。 |
| E-7 | **verify 体系不验证可启动性**：`verify:project` 做树↔zip↔configClasses 三方一致 + 悬空 import 归零，但没有编译、没有启动冒烟 | `arsenal-web/scripts/`、`.verify/` | 「一致」≠「能跑」，绿灯给了虚假的安全感。 |
| E-8 | 基线干净：`git status` clean @ `ace40eb`，可放心开改 | git 实测 | 无落袋负担，直接进阶段 0。 |

> 排查记录：曾怀疑 E-1 是 `yamlBlocks` 字段名不对导致的解析误报，已用三种读取方式复核实测为 0，**证据成立**。

## 2. 目标（完成定义见 §6）

1. **双包导出**：选完直接下载 backend.zip / frontend.zip / all.zip，前端工程是完整可跑的 admin（登录、布局、动态菜单、CRUD 页）。
2. **开箱即跑三档**：
   - 填了数据库连接 → `mvn spring-boot:run` 直接起；
   - 什么都不填 → 勾选「演示模式（H2）」也能启动登录；
   - `all.zip` → `docker compose up -d` 起 DB + 后端 + 前端全套。
3. **环境配置前移**：数据库/Redis/MQ/Nacos 的连接信息在装配台里填，烘进生成物；prod 保持 `${ENV_VAR}` 注入。
4. **模块可选、导出即用**：用户管理 / 角色权限 / 菜单管理勾选后，导出包含可用接口 + 前端页面 + **建表与种子 SQL**（admin 账号、菜单树）。
5. **前端技术可选**：Vue3（v1 完备）/ React（预留位）/ 无前端。
6. **绿灯即事实**：新增 `verify:scaffold`，把「能跑」变成机器断言。

## 3. 总体设计

### 3.1 目录与数据层：新增 `arsenal-scaffold/`（模板文件化）

现状把 30 份脚手架代码以字符串塞在 `project.json` 里。前端工程模板 50+ 文件、模块体系再乘 3，继续塞 JSON 不可维护。**改为真实文件目录 + 同步脚本打进 bundle**，沿袭 `sync-content.mjs` → `src/generated/` 的既有管道，保持静态导出（`next export`）离线优先：

```
arsenal-scaffold/
  backend/                    # 后端模板（按需引用，from project.json 逐步迁移）
  frontend/
    vue3-vite/                # v1 唯一完备基底，完整 admin 工程
      package.json.tpl  vite.config.ts.tpl  tsconfig.json.tpl
      src/main.ts.tpl  src/router/index.ts.tpl  src/stores/auth.ts.tpl
      src/api/{http,auth,user,role,menu}.ts.tpl
      src/layout/{AdminLayout,SideMenu,HeaderBar}.vue.tpl
      src/views/{login,home,user,role,menu}/*.vue.tpl
      src/utils/permission.ts.tpl  .env.tpl  README.md.tpl
    react-antd/               # v2 预留目录，先不建文件
  modules/                    # 功能模块清单（每个模块一个 json/目录）
    user/  role/  menu/       # backend/*.java.tpl + frontend/*.ts|vue.tpl + sql/*.sql.tpl
  shared/
    sql/V1__init.sql.tpl  V2__seed.sql.tpl   # DDL 与种子分离，种子含 admin/菜单树
    scripts/start-dev.bat.tpl  start-dev.sh.tpl
    compose/docker-compose.yml.tpl  compose/frontend-nginx.conf.tpl
```

- `scripts/build-scaffold-templates.mjs`：把上述目录编译成 `src/generated/scaffold-templates.ts`（路径 → 内容字符串的 Map + 模块清单 JSON），`sync-content.mjs` 链路里同步调用。
- 占位符：`{{basePackage}}` `{{artifactId}}` `{{appName}}` `{{dbUrl}}` `{{dbUsername}}` `{{backendBaseUrl}}` 等，渲染走一个极小的 `renderTemplate()`（正则替换即可，不引模板库）。
- `arsenal-stacks/stack.json` 扩展（走 `tools/content/stack_*.py` 数据管道，禁止直接改 JSON）：
  - 新增维度组 `fe`：`fe.base`（vue3-vite / react-vite(规划中) / none）、`fe.uilib`（element-plus 完备；ant-design-vue、naive-ui 随 react/后续）、`fe.lang`（ts/js）、`fe.state`（pinia）、`fe.http`（axios）；
  - 新增顶层 `envForms`：声明「选了什么 → 出现什么表单」的 schema（字段、默认值、必填、烘焙目标 profile）。
- `project.json` 里的 30 份后端模板在阶段 2 迁入 `arsenal-scaffold/backend/`（迁移动作由脚本搬运 + `verify:scaffold` 守护，不手抄）。

### 3.5 模块体系（v1 三模块 + 内置基础设施）

| 模块 | 后端交付物 | 前端交付物 | 表与种子 |
|---|---|---|---|
| 内置基础设施（必含） | 认证（按 `auth` 选型分叉：securityjwt/satoken/custom）、登录/登出/当前用户接口、common 五件（已有）、全局异常 | 登录页、AdminLayout、路由守卫、Axios 拦截器（token 注入/401 跳转）、权限指令 | `sys_user`（无 mod-user 时仅作登录账号表，最小字段） |
| mod-user 用户管理 | 分页/条件查、增删改、重置密码、改个人信息（repository 按持久层分叉，复用现有分叉机制） | 用户列表页（搜索/表格/弹窗表单/启停用） | `sys_user` 全量 + 种子 admin（BCrypt('admin123')） |
| mod-role 角色权限 | 角色 CRUD、权限码分配、用户-角色绑定；接口按权限码拦截 | 角色列表页 + 权限树选择 + 按钮级显隐 | `sys_role` `sys_permission` `sys_user_role` `sys_role_permission` + 种子 ADMIN |
| mod-menu 菜单管理 | 菜单树 CRUD（目录/菜单/按钮三类）、按角色出菜单树接口 | **登录后拉 `/api/auth/menus` 动态渲染侧边栏与路由**；菜单管理页 | `sys_menu` + 种子三条演示菜单 |
| mod-auditlog 操作日志（backlog） | AOP 切面落库 | 日志查询页 | `sys_operation_log` |
| mod-dict 字典管理（backlog） | 字典/字典项 CRUD | 字典页 + 表单枚举联动 | `sys_dict` `sys_dict_item` |

- **依赖规则**：mod-role、mod-menu → 依赖 mod-user；全部模块 → 依赖认证基础设施（自动满足）。`module-registry` 校验，UI 标黄一键补。
- **菜单模块未选时**：前端用静态路由表渲染侧边栏（模板内置），导出包依然完整可用；选了 mod-menu 才切动态菜单。两条路径都真实可用，不出现「选了才断」的悬崖。
- **兼容性**：模块对持久层/前端基底的硬要求进 registry（如 mod-menu 树形查询在 jdbc 直写 SQL 分叉）；不满足的组合走 `auditArchitecture` 同款提示，不静默生成坏代码。

### 3.6 环境值的安全边界

| 位置 | 规则 |
|---|---|
| `application-local.yml` | 用户填的连接信息烘焙处，**写入 .gitignore**；文件头注释「本机私有配置，勿提交」 |
| `application-prod.yml` | 一律 `${ENV_VAR}`，与现状一致 |
| docker-compose | 值注入容器环境变量；compose 里含密码属用户本机文件，README 提醒勿公开分发 |
| localStorage（picks-store） | 主机/端口/库名/用户名持久化；**密码默认不持久化**，勾选「记住到本机」才存 |
| 上传 | 无任何上传。离线优先不变。 |

### 3.7 前端基底的版本策略

- 模板 `package.json` 锁精确版本（如 vue `3.4.x`、vite `5.x`、element-plus `2.x`），升级走单独任务，不在功能迭代里顺手升。
- `.env.example` 与 `.env` 双文件：`.env` 烘焙用户填的值，`.env.example` 留占位（便于换机器分发）。

## 5. 关键技术决策记录

| 决策 | 理由 |
|---|---|
| 继续前端生成，不把生成逻辑搬后端 | 离线优先是仓库刻意设计（`docs/功能缺口清单-2026-09-22.md` 明示「非阻塞」）；纯前端零上传、零服务依赖；后端只做「测连接/编译冒烟」两个可选增强，离线时优雅降级。 |
| 模板文件化（`arsenal-scaffold/`）而非继续塞 JSON | 前端工程 50+ 文件，JSON 里写转义字符串不可维护、不可 diff；真实文件目录可被 IDE 校验、可逐文件评审；同步脚本打进 bundle 保持静态导出。 |
| 三包而非两包 | 用户要的是「两个包」，但「两个包怎么一起跑」是真问题 —— all.zip 用 compose 给出答案；单包各自独立分发场景也保留。 |
| 演示模式（H2）作为兜底 | 「开箱即跑」的最大敌人是环境依赖。H2 `MODE=MySQL` 内存库让零配置可启动，真库信息填好则自动优先；两档共存不冲突。 |
| 菜单模块未选 → 静态路由兜底 | 避免出现「不勾菜单模块前端就没菜单」的悬崖；动态菜单是增强，不是前提。 |
| 密码默认不进 localStorage | 军火库自身是本地工具，但导出配置里含真实密码，持久化扩散面最小化；需要便利的用户显式勾选。 |
| zip 保持 store 模式、纯文本 | `lib/zip.ts` 头注释已论证过成本收益；模板全文本，SVG favicon 即可满足图标需求，不引入二进制。 |
| 菜单仍单一入口 | 向导是线性流程，拆多菜单打断上下文；StepRail 已是合格的步骤导航。「随你自己安排」的答案就是：不拆。 |

## 6. 总体验收标准（完成定义）

1. **后端包**：全新目录解压 → `mvn spring-boot:run`（连接信息已在装配台填好）→ `/actuator/health` UP。
2. **前端包**：`npm install && npm run dev` → 登录页 → `admin / admin123` 登录成功 → 侧边栏渲染（动态或静态）→ 用户/角色/菜单三个管理页 CRUD 全可用且数据落库。
3. **all 包**：`docker compose up -d` → DB + 后端 + 前端全通，同 2。
4. **演示模式**：不填任何数据库信息（勾演示模式）→ 后端可启动可登录。
5. `npm run verify:all` 全绿，含新增 `verify:scaffold`；既有九层 verify 无回归。
6. README（导出包内）每条命令都真跑过一次，无「文档里的命令」。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 33 维 × 前端基底 × 模块的组合爆炸，无法逐组合真机验证 | 模块只承诺「标准组合」全通（P3-4 抽样矩阵）；其余组合靠 `auditArchitecture` 缺口提示 + `verify:scaffold` 静态断言兜底；组合不承诺处 UI 明示。 |
| 前端模板体量大（50+ 文件），一次写完容易夹带坏 import | 模板文件化 + P2 分模块提交 + P3-1 悬空断言先于 P2-3/P2-4 的模块扩张就位（调整执行顺序：P2-1 完成即插 P3-1）。 |
| H2 MODE=MySQL 与真 MySQL 方言差异（如 `datetime(6)`、外键行为） | 种子/DDL 只用双方言安全子集（写一条「H2 兼容写法」约束进模板注释）；演示模式仅承诺登录与 CRUD 演示，不承诺生产语义。 |
| 用户把含密码的 compose/local.yml 分享出去 | 文件头注释警告 + README 明示 + prod 恒走环境变量；不上传任何值，责任边界写清楚。 |
| React 基底排期挤占 | React 只占 schema 预留位与灰显 UI，零实现成本；v2 单独立项。 |
| 迁移 project.json 模板时引入漂移 | P2-5 用「迁移前后 zip 逐字节对拍」守护，不一致即红，禁止手抄。 |
