# 工程规范 × 智慧中枢 · 联动设计（2026-10-05）

> 目标：让「工程规范」这一层**接上中枢的团队事实源**——不再靠章程里手写的名单，
> 而是用中枢的「谁还在这个团队里」当真值。
>
> 状态：**B 方向已交付**（MCP 工具，中枢零改造即可消费）；A 方向契约已定、待改中枢；
> C 方向押后。逐项进度见 §6。

## 一、为什么要联（问题是真的，不是「要整合」这种空话）

军火库现在的「债主离队」判据是章程 JSON 里**手写的 `team` 名单**：

```jsonc
"team": ["mryang", "someone"]     // ← 手写、必然过期、忘了更新就永远发现不了孤儿债
```

而中枢里 `team_members` 删掉记录 = 人离开团队。**离队在中枢是可查询的真值**，
在手写名单里是一个需要人去记得更新的字符串。这就是联动的全部价值。

顺带解决的第二个问题：治理动作（谁欠着例外、什么到期了）现在只存在于军火库一个页面上。
中枢是「每天要看的地方」，所以待办应该出现在那里。

## 二、中枢现状（2026-10-05 实测，不是推测）

| 事实 | 证据 |
|---|---|
| 团队名册可读 | `GET /api/teams/{teamId}/members` → `[{id, team_id, user_id, role, joined_at, user_name, user_email, user_avatar}]` |
| 角色枚举 | `owner` / `manager` / `member`（排序时 owner → manager → member） |
| **没有「离职 / inactive」字段** | `OrgService.removeMember` 是**删记录**；`team_members` 无 status 列 |
| 全部端点走 JWT | `JwtAuthenticationFilter`（`OncePerRequestFilter`） |
| 免登录只有四处 | `PUBLIC_PATHS`（注册/登录/健康检查）、微信扫码三个端点、`/api/share/` 前缀。**没有配置化白名单** |
| 限流与菜单权限 | `RateLimitInterceptor` + `MenuAccessInterceptor` 都挂在 `/api/**`（除 `/api/files/**`） |
| 响应外壳 | `ApiResponse.ok(data)` → `{code, message, data}`，前端判 `code === 0` |

**结论**：中枢没有「集成专用只读口」，也没有 API Key 机制。要联，必须加 —— 这正是
下面 A 方向要做的事，而且它需要**改中枢代码**（不是配置）。

先造一个没人看的数字不如不做。真正想做时先回答「谁会看它」。

## 四、B 方向已交付的部分（可直接用）

### 4.1 第 8 个 MCP 工具：`list_governance_actions`

中枢（或任何 MCP 客户端）现在可以直接问军火库「现在该干什么」：

```
tools/call  name=list_governance_actions
            arguments={ "level": "P0", "owner": "mryang" }
```

返回示例（本仓当前真实数据）：

```
# 治理待办（判定日 2026-10-05｜生成于 2026-10-05 10:23:41）

## 军火库自身 · 工程章程（arsenal-self）—— 共 0 件：P0 0 / P1 0 / P2 0
  当前没有待办：例外都销了账、没人离队、条款都在机器能判的层上。
```

三条设计纪律：

1. **读构建期产物，不现场算。** 聚合逻辑在 `src/lib/standards.ts`（TypeScript），
   MCP 是 `.mjs`，跑在 AI 客户端进程里 import 不了 `.ts`。在 `.mjs` 里重写一遍就是
   「同一规矩两份实现」——本仓已经栽过三次（sync 的 cookbook 段、project-check【13】、
   CI 判定口径）。所以：逻辑一份，构建期算一次，页面 / MCP / CI 读同一份。
2. **产物过期会自己说。** 输出带判定日与生成时间；`staleAfterDays`（默认 7）超了会
   提醒重跑 `npm run sync:governance`。**不假装实时** —— 没有数据来源时画 0 是本仓最反感的形态。
3. **过滤无结果要明说。** 按不存在的 owner 过滤会返回「没有匹配 level/owner 的待办」，
   而不是空串 —— 空串会被中枢当成「没事」。

### 4.2 构建期产物链

```
npm run sync
  ├─ sync-rules.mjs
  ├─ sync-content.mjs          写 src/generated/charter.json
  ├─ build-scaffold-templates.mjs
  └─ calc-governance.ts        写 src/generated/governance.json   ← 新增（tsx 跑）
```

`prebuild` / `predev` 都会先跑 `npm run sync`，所以**改了章程不重跑就不会更新**。
能这样挂在 npm 链里（而不是在 sync-content.mjs 里 spawn tsx）是因为
本环境 `spawnSync(process.execPath, …)` 会被沙箱拦成 EBUSY（Archify 那 3 项红就是这个原因）。

## 五、A 方向的契约（待实现，两端都要改）

### 5.1 中枢侧：加一个只读集成口

```
GET /api/integrations/teams/{teamId}/roster
Header: X-API-Key: <integrations.roster.api-key>

200 → { code: 0, data: {
  source: "command-center",
  teamId: 123,
  teamName: "平台组",
  fetchedAt: "2026-10-05T10:00:00Z",
  members: [ { userId: 7, name: "张三", role: "member", joinedAt: "2026-03-01" } ]
}}
```

**最小暴露**：只给 `userId / name / role / joinedAt`。**不给** `email`、不给 `avatar`
—— 名册同步只需要「谁在、叫什么、什么角色」。

安全要求（一条都不能少）：

| 要求 | 理由 |
|---|---|
| `integrations.roster.api-key` **为空时端点返回 503 并说明未配置** | 绝不能出现「没配 key 就放行」 |
| 常量时间比较（`MessageDigest.isEqual`） | 防时序攻击逐字节猜 key |
| `JwtAuthenticationFilter` 放行 `"/api/integrations/"` **前缀**，且注释写明「该前缀靠 X-API-Key 自行鉴权，不是免鉴权」 | 放行的是「JWT 这一层」，不是「鉴权」 |
| 每次调用记审计日志（谁、何时、哪个团队、结果） | 名册是组织信息，泄露了要能追 |
| 继续挂现有限流拦截器 | 端点在 `/api/**` 下，自动覆盖 |

要改的中枢文件（三个，都很小）：

| 文件 | 改什么 |
|---|---|
| `controller/IntegrationRosterController.java` | **新增**，一个 GET + 常量时间比较的 key 校验 |
| `filter/JwtAuthenticationFilter.java` | 放行条件加一个**精确前缀** `/api/integrations/` |
| `application.properties` | 加 `integrations.roster.api-key=${INTEGRATIONS_ROSTER_API_KEY:}`（空即未配置） |

**未验证项**：`MenuAccessInterceptor` 对「无登录态的请求」的行为我还没核实，
端点可能被它拦。改完必须在 IntelliJ 里重启后端实测（记忆：本机无 mvn、DB 在远程，
`javac` 只能过静态编译，**端点无法运行时验证**）。

### 5.2 军火库侧：拉名册 + 交叉校验（构建期）

配置（环境变量，不进 Git）：

| 变量 | 含义 |
|---|---|
| `ARSENAL_CC_BASE_URL` | 中枢后端地址，如 `http://127.0.0.1:3001` |
| `ARSENAL_CC_API_KEY` | 与中枢的 `integrations.roster.api-key` 一致 |
| `ARSENAL_CC_TEAM_ID` | 要同步哪个团队 |

`sync-content.mjs` 拉一次，写 `src/generated/roster.json`：

```jsonc
{
  "schema": "arsenal-roster/1",
  "status": "ok",              // ok | unavailable | not-configured
  "source": "command-center",
  "teamId": 123,
  "fetchedAt": "2026-10-05T10:00:00Z",
  "members": [ { "name": "张三", "role": "member" } ],
  "error": null                 // status != ok 时写清原因（连不上 / 401 / 未配置）
}
```

**处置按拍板结果：构建照过，页面提示差异。** 具体：

| 情况 | 构建 | 页面 |
|---|---|---|
| 名册拉到且与章程 `team` 一致 | 照过 | 显示「中枢名册一致（N 人）」 |
| 拉到但**有差异**（有人不在中枢 / 中枢有人不在章程） | **照过** | 列出差异，并点名「按中枢口径这几位已离队，孤儿债判定以此为准」 |
| 中枢不可达 / 401 / 未配置 | **照过** | 显示「本次未校验名册」+ 原因 + 怎么配 |

差异怎么用：**离队判定优先取中枢口径**，中枢不可用时回落到章程手写名单，
并在页面上标明当前用的是哪一份 —— 与「两套判定口径不许混」是同一条纪律
（`gateReadiness` 拆 ciRunnable/astOnly/manualOnly 就是这个教训）。

## 七、实测步骤（中枢重启后端后跑这三段）

改完中枢三个文件并**在 IntelliJ 里重启后端**（本机无 mvn、DB 在远程，
`javac` 只能过静态编译，端点必须靠这一步验证）：

```bash
# ① 未配置 key → 必须 503，且**不能**返回名册
curl -i http://127.0.0.1:3001/api/integrations/teams/1/roster

# ② key 正确 → 200，名册只含 4 个字段（无 email / 无 avatar）
curl -s -H "X-API-Key: $YOUR_KEY" http://127.0.0.1:3001/api/integrations/teams/1/roster

# ③ key 错误 → 401，且错误信息不区分「没传」与「传错」
curl -i -H "X-API-Key: wrong" http://127.0.0.1:3001/api/integrations/teams/1/roster
```

配好 key 之后，军火库侧拉一次。三个环境变量（bash 版；PowerShell 用 `$env:名` 同义）：

| 变量 | 值 |
|---|---|
| `ARSENAL_CC_BASE_URL` | `http://127.0.0.1:3001` |
| `ARSENAL_CC_API_KEY` | 与中枢 `integrations.roster.api-key` 同一份 |
| `ARSENAL_CC_TEAM_ID` | 要同步的团队 id |

```bash
cd arsenal-web
node scripts/sync-roster.mjs     # 单独跑，看清各分支各打印什么
npm run sync                     # 走完整链（含 calc-governance）
```

期望输出（**本机已用假中枢实跑过全部五个分支，全部 exit 0**）：

| 场景 | 产物 status | 打印 |
|---|---|---|
| 三件变量没配 | `not-configured` | `未配置 ARSENAL_CC_BASE_URL / … —— 离队判定本次仍用章程手写的 team 名单` |
| key 不对 | `unavailable` | `X-API-Key 无效（401）—— 核对两侧是否同一份 key` |
| 中枢没配 key | `unavailable` | `中枢报「集成口未配置」→ …` |
| 连不上 | `unavailable` | `拉不到中枢名册：fetch failed —— …` |
| 正常 | `ok` | `名册已同步 · 团队「X」· N 人 · 角色分布 {…}` |

然后打开 `/standards` 看「团队名册一致性」那块：它会写明**当前判定用的是哪一份**
（中枢名册 / 章程手写名单），以及两侧的差异名单。
