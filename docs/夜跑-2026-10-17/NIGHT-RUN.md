## 二、接力协议

### 开工（在读方案之前先做完）

0. **环境探活（≤3 分钟）**——方案里的环境假设可能是过期的，别照抄：
   node / JDK / 后端 :3011 / dev :3010 / 方案的命令与日志格式，逐项实测（命令见 §七）。
   写进 running.json 的「探活结论」。⚠️ **前棒"起不来"的结论不可继承**——必须自己探一遍。

1. 读状态目录，先搞清现在到第几棒了。

2. **等前棒 = 接管，不是干等**：

   | 前棒状态 | 你的动作 |
   |---|---|
   | `0<N-1>-done.json` **存在** | 正常开工 |
   | 无 done，但有 `0<N-1>-running.json` | **走接管协议**（§2.1） |
   | 无 done，**也无** running | 真没开工 → 写 `<N>-blocked.json`，跳过本棒，如实留给终检棒 |
   | running 存在但 mtime 不到 30 分钟 | 前棒还在跑 → 每 60 秒查一次，最多等到本棒硬线 |

   > **绝不能和前棒并行改仓库。** 两棒同时改同步脚本 / README / 验证数字会互相踩烂，而且很难查。
   > 但**干等到硬线同样不可接受**——窗口在空转，积分在白烧。

3. 建 `<N>-running.json`：`{ "棒次": N, "任务": "...", "开工": "<ISO>", "计划交棒": "<ISO>", "探活结论": {...}, "砍定范围": {...} }`

4. 第一棒不需要等待。

### 2.1 接管协议

**前棒死了，但它的工作区里往往躺着已经写好的代码。**

| 步 | 动作 | 要点 |
|---|---|---|
| 1 | 读 `<N-1>-running.json` 的「砍定范围」 | 那是前棒承诺的范围，接管的第一依据 |
| 2 | 盘点工作区 `git status` + `git diff --stat` | 前棒未提交的改动**全部保留** |
| 3 | 决定**救还是弃** | 属前棒声明的范围 → 救；垃圾/脏改动 → 弃，**但必须先记下丢了什么** |
| 4 | 补最小收尾（≤10 min） | commit + 写 `<N-1>-done.json`（`状态: "被接管"`）+ 点明哪部分是你的 |

**接管时的诚实义务**：在自己 done.json 写一条 `踩的坑` 点明接管事实；给下一棒的话里说明**哪些产出是前棒的、哪些是自己的**；**接管 ≠ 继承自检与 review 的结论**（前棒没做的自检你没资格替它签字，但可替它做存在性核验 + 一次反着验）。

### 交棒（v2.0 强化）

把下一棒的 `scheduledAt` 改成「现在 + 3 分钟」。即使已晚于下一棒硬线也照设——让下一棒自己判断。

**交棒后自查三项（30 秒），缺任一立刻补**：
- [ ] 下一棒的 `scheduledAt` 真的改成功了（automation list 里能看到新时间）
- [ ] 自己的 `done.json` 已落盘
- [ ] `git log -1` 是自己的 message

⚠️ **不许虚报收工时间。** 落盘即交棒。虚报会让下一棒一直等到兜底时间——昨夜因此空转了 3 小时（10-13 实证）。
