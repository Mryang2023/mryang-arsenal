# 测试工程师 · 升级计划书

**日期**：2026-10-12
**代号**：`/qa`（测试工程师）
**一句话**：给一个项目地址（git / 本地目录），**可以整仓检，也可以只圈一部分代码检**（目录/文件/模块多选）；解剖台先跑规则找硬伤，然后**像真测试工程师一样**做语义深检 —— 发现规则之外的 bug（边界、并发、时序），针对每一处给出**带 before/after 的优化方案**，并列出该补哪些测试用例。未配置 LLM 时优雅降级为纯静态深度审查，离线优先原则不破。

---

## 0. 先说结论：这不是「再造一个解剖台」，是给它装大脑

调研完仓库现状，先把和 `/autopsy` 的分工说死：

| | 解剖台 `/autopsy` | 测试工程师 `/qa` |
|---|---|---|
| 回答的问题 | 「违反了 69 条规则里的哪几条」 | 「哪里会出事、该怎么改、该补什么测试」 |
| 判据 | 规则驱动（regex + AST + checkups） | 规则 + **LLM 语义**（可选层） |
| 输出 | 三档违规清单，每条带 file:line | 违规清单 + **语义 finding** + **逐点优化方案** + **测试建议** |
| 执行模型 | 同步（单请求，clone 60s / Lint 2MB 上限） | **异步 Job**（提交→轮询→结果），大项目不撞超时 |
| 定位 | 快速静态体检 | 深度审查，解剖台的下游深化 |

现状盘点（2026-10-12 核实）：

| 需要的件 | 现状 | 差距 |
|---|---|---|
| git/path/zip 三输入 | ✅ `SourceResolver.fromPath/fromZip/fromGit`（SourceResolver.java:66/95/186），`AutopsyController` 已接 git | 直接复用 |
| 规则引擎 + 覆盖率 + 三态披露 | ✅ `ProjectScanner` + `LintEngine` + `CheckupEvaluator`，autopsy 报告已带 `skipped/undecidability` | 直接复用 |
| 异步作业 | 🔴 **无**：全仓所有端点同步跑在服务线程 | 新建 Job 状态机 |
| LLM 层 | 🔴 **0 行代码**：`check.llm` 只是提示字符串，`LintEngine.java:399` 占位归 skipped | 新建（本计划核心增量） |
| 逐点优化方案 | 🔴 报告只有「违反了什么 + 规则自带 good 片段」，没有「这一处具体怎么改」 | 新建生成器 |
| 语义 bug 发现 | 🔴 AST 层刻意不覆盖（反射/并发/边界查不了） | 由 LLM 层填 |

**所以这个功能的形状是：一条已跑通的静态链路（复用）+ 三块真缺的件（Job 状态机、LlmClient、方案聚合器）。** 风险最高的「解析任意项目」解剖台已经替你扛过了。

**已拍板的设计决策**（2026-10-12，与杨先生确认）：
1. **LLM 作为可选增强**，OpenAI-compatible 接口，未配置 key 时全链路降级可用 —— 这是仓库第一个碰外网的层，做成可选是为了守住离线优先。
2. **独立新入口** `/qa` + `/api/qa/*`，不在 autopsy 上加深度模式开关（两档混一页会失焦，且同步请求撑不住 LLM 分钟级耗时）。
3. **交付物 = 结构化报告**（四面板在线看），Markdown 导出 / PR 评论格式留到 P2。
4. **支持圈定范围检测**（2026-10-12 补充）：提交时可带 `scope` 选择器（目录/文件 glob/模块），只对选中范围出结论；不选 = 整仓。

**预计工作量**：4 棒（M1–M4），约 3000 行新增。M1 不依赖 LLM、可独立跑通验收；M2 起才需要 key。

## 1. 产品设计：测试工程师是什么

### 1.1 一句话交互

```
填 git 地址 / 本地路径 + [圈定范围：整仓 | 选目录/文件/模块] + [语义深检开关]
        →  [开始审查]  →  拿到 jobId，页面显示 5 阶段进度
                              ↓ 完成后
        四面板报告：A 硬伤 / B 语义深检 / C 优化方案 / D 测试建议
                              ↓ 每次审查自动留档
        [历史] .data/qa/<projectId>/ 快照列表
```

### 1.1.1 检测范围（scope）怎么选

三种圈定方式，最终收敛为一个 `scope` 匹配器（glob 集合 + 模式）：

| 方式 | 交互 | 说明 |
|---|---|---|
| 整仓（默认） | 不选 | `scope.mode = "full"` |
| 目录/文件 | 拉取后返回目录树，勾选节点 | 前端提交 `include: ["src/main/java/com/x/order/**", "…/OrderService.java"]` |
| 模块 | Maven 多模块项目按 `<module>` 整选 | 复用 BuildScanner 已解析出的模块清单，勾模块 = 勾该模块根目录 glob |

**两种执行语义（关键，防「假局部」）**：
- `scope.mode = "review"`（默认，**严格局部**）：规则引擎、triage、报告 findings 都只落在圈内文件。适合「我就想知道这个模块现在有没有问题」。
- `scope.mode = "focus"`（**全量扫描 + 聚焦呈现**）：ProjectScanner/LintEngine 仍跑整仓（技术栈 facts、分层、调用闭包是全局事实，砍掉会让语义深检缺上下文、圈外调用圈内时报不出），但报告的 staticFindings 只列圈内命中，圈外命中折叠进 `outOfScopeSummary`（只给计数不给明细）。适合「重点测这块，但顺便别把跨模块影响漏了」，也更适合喂 LLM（上下文完整、token 只花在圈内文件的深检上）。

**诚实披露**：报告头部横幅写死「本次范围：3 个目录 / 42 个文件（占全仓 18%）」+ 模式标注；`review` 模式明确提示「圈外文件未检查」。范围历史随快照记录，同一项目不同 scope 的报告并存、可对比。

### 1.2 流水线（5 个 Phase，对应 Job 状态机）

```
输入 ──▶ ①摄取 ──▶ ②静态确定性审查 ──▶ ③LLM语义深检(可选) ──▶ ④方案聚合 ──▶ ⑤报告
   PENDING→CLONING→SCANNING→ANALYZING→AGGREGATING→DONE / FAILED
```

**① 摄取**：`POST /api/qa/submit` 立即返回 `jobId`（不等 clone）。clone/扫描在工作线程跑；`GET /api/qa/jobs/{id}` 轮询进度（phases 已完成/当前/失败原因）。Job 状态落 `.data/qa/jobs/<jobId>.json`（报告快照在 `.data/qa/<projectId>/`，两者分开目录避免布局互踩），服务重启后历史可查。提交体含 `scope`：`{ mode: "full"|"review"|"focus", include: [glob…], exclude: [glob…] }`；`review/focus` 时 include 至少一项，glob 在拉取的**工作副本内**解析（防路径穿越，规范化后必须仍在仓库根内）。局部检测复用同一个 Job 通道，只是各 phase 按 scope 过滤（见 1.1.1 两种语义）。git 地址的目录树要 clone 完才有：`GET /api/qa/tree?projectId=` 从快照缓存/上次工作副本返回目录树供勾选，同一 `projectId` 的 clone 结果按 HEAD 指纹缓存复用 —— 选完范围再提交是**第二个 Job 但不再重新 clone**（整仓首次提交顺带当探路）。

**② 静态确定性审查（离线全跑）**：复用 `LintEngine` + `CheckupEvaluator`，产出 P0/P1 硬伤 + 覆盖率（沿用 autopsy 的 coverageNode 口径：rulePool/executed/notRun/skipped，「没跑的规则」必须显式披露）。**scope 过滤在这一相生效**：`review` 模式文件列表先按 include/exclude 裁剪再进引擎（coverageNode 额外记 `scopeFilteredOut` 文件数）；`focus` 模式全量跑、出口处按 scope 分桶。同时产出 **triage 信号**供 ③ 用（候选池 = scope 内文件；`focus` 可把「scope 内文件直接调用到的圈外方法所在文件」作为上下文文件附带，只作上下文不单独送检）：
- 含 P0/P1 违规的文件
- 词法圈复杂度高的文件（CodeScanner 级别的正则统计，不引 JavaParser）
- `directCalls`/`routes` 密集的核心路径文件
- `check.llm` 已配提示词的规则候选文件（targetGlob 命中）

**③ LLM 语义深检（可选，默认关闭）**：
- **接口**：OpenAI-compatible chat/completions，三档配置（沿用 arsenal.json 覆盖模式）：
  ```
  默认  关闭
  覆盖  arsenal.json#project.llm { baseUrl, model }
  覆盖  env ARSENAL_LLM_BASE_URL / ARSENAL_LLM_MODEL / ARSENAL_LLM_API_KEY
  ```
  一个 client 通吃 DeepSeek / Gemini(兼容模式) / 本地 Ollama。key 只走环境变量，不落库、不进前端、不进 git。
- **喂法**：按文件分批（不是整仓塞入），每批一个代码窗口 + 项目上下文摘要（技术栈 facts 来自 ProjectScanner）。
- **输出契约**：扩展现有 `{verdict, lines, reason}` 为语义 finding：
  ```json
  { "category": "bug|边界|并发|安全|性能|可维护性",
    "severity": "MUST|SHOULD|MAY",
    "file": "…", "line": 0, "evidence": "…",
    "confidence": 0.0,
    "impact": "会出什么事，一句话说死",
    "recommendation": { "before": "…", "after": "…", "rationale": "…" } }
  ```
- **顺带补洞**：声明了 `check.llm` 的 43 条规则（实测：19 条 llm-only 无静态兜底、24 条 regex 优先路由仅在静态层判不出时落 LLM）从这里获得真判定 —— 这正是 README「未完成」里 **LLM 语义层 0/43** 的口径，本棒填第一块砖。未配置 key 时 `LintEngine` 占位保留（skipped + 原因），**且 LLM 判定只在 `/qa` 的 Job 上下文里启用，同步的 `/autopsy` 与 `/api/lint` 链路永不调 LLM**（它们是同步请求，分钟级调用会撞超时，也违背各自的既有承诺）。
- **降级**：未配置 key → ③ 整段跳过，报告显式标「语义深检未执行（原因：LLM 未配置）」，沿用三态披露纪律；④ 退化为规则 good 片段模板。

**④ 方案聚合**：static + semantic findings 合并 → 按「文件 + 类别」聚类去重（同一文件同一问题 LLM 可能报多次）→ 逐点生成优化方案 → 按 `confidence × severity` 排序。**语义 finding 与静态 finding 分档展示，永不混进 P0**（P0 即必改的可信度是 autopsy 立起来的，不能稀释）。测试建议：基于 routes/directCalls/无测试事实（CiScanner、`arsenal-cases` 判据）列「该补测试的核心路径」；LLM 模式给用例草案，离线模式只给清单。

**⑤ 报告 schema（qaReport v1）**：

```json
{ "schemaVersion": 1, "jobId": "…", "projectRef": "…",
  "scope": { …复用 autopsy… },
  "targetRange": { "mode": "full|review|focus", "include": [], "filesMatched": 42, "pctOfRepo": 18.0,
                    "outOfScopeSummary": { "p0": 3, "p1": 7 } },   // focus 模式只给计数；review 模式为 null（圈外根本没跑）
  "coverage": { …复用 autopsy coverageNode，另加 scopeFilteredOut… },
  "staticFindings": [],        // 复用 autopsy violationNode
  "semanticFindings": [],      // 见 ③ 契约
  "recommendations": [],       // { findingIds[], title, before, after, rationale, source: "rule:<id>"|"llm" }
  "testSuggestions": [],       // { target, reason, draftCases? }
  "skipped": [], "undecidability": [],
  "llmUsage": { "model": "…", "filesSent": [], "tokens": 0 } // 离线 = null
}
```

### 1.3 前端 `/qa` 四面板

| 面板 | 内容 | 与 autopsy 的关系 |
|---|---|---|
| A 硬伤清单 | P0/P1 + 证据 file:line，点跳源码位置 | 口径与 autopsy 面板 B 完全一致 |
| B 语义深检 | 规则之外的 bug/边界/并发发现，带 confidence 徽章；未执行时显示降级横幅 | 新 |
| C 优化方案 | 逐点 before/after 代码对照 + 依据 + 来源标注（哪条规则 / 哪次 LLM 判定） | 新，核心卖点 |
| D 测试建议 | 缺测试的核心路径清单 + 用例草案 | 新 |

复用 AutopsyLab 组件风格、`arsenal-api.ts` 封装模式、快照落盘机制（localStorage + `.data/` Node 侧）。

**范围选择器（贯穿输入与报告）**：输入卡上「整仓 / 圈定范围」切换；圈定范围时从 `GET /api/qa/tree` 拉目录树勾选（Maven 多模块顶层直接按模块勾），实时显示「已选 N 文件，约 M MB」。报告页顶部固定范围横幅（「3 个目录 / 42 个文件，占全仓 18% · 严格局部」），`focus` 模式在横幅里挂「圈外另有 3 P0 / 7 P1（折叠）」的展开入口。

## 2. 关键设计决策（怕以后忘了为什么这么定）

| 决策 | 理由 |
|---|---|
| LLM 做成**可选层**，默认关闭 | 这是第一个打破离线优先的功能，必须给不用外网的人留全功能降级路径（②④⑤离线全可跑） |
| OpenAI-compatible 单接口 | 一个 client 通吃 DeepSeek/Gemini/Ollama，不做多 provider 适配层的维护地狱 |
| **异步 Job 状态机**而非加长同步超时 | clone 60s + LLM 分钟级，同步必撞墙；且 Job 落盘天然就是历史记录 |
| triage 先做**简单启发式** | 选不准会白烧 token，但第一版不值得上 embedding；启发式清单在 1.2-②，误杀的代价只是少检几个文件 |
| 语义 finding **不进 P0**、必带 confidence | 混档 = 稀释 P0 可信度 = 用户不再信报告 |
| `llmUsage.filesSent` **必须记账并展示** | 隐私红线：用户要能看到「哪些代码片段被发出去了」。发送范围 = triage 选中的文件，白名单式披露 |
| 报告口径**复用 autopsy** coverageNode/violationNode | 两套口径会打架；「哪些规则没跑」的披露纪律只维护一处 |
| 局部检测给 **review/focus 两种语义**，默认 review | 「只检一部分」≠「只看一部分」：分层/调用闭包/技术栈是全局事实，`focus`（全量扫+聚焦呈现）避免「圈外代码调了圈内」被假阴性吞掉；`review` 留给严格局部场景。**模式在报告头部标注死，不让人猜圈外跑没跑** |
| Job/快照落 `.data/qa/`，不进 git | 沿用 `profile-store` 与 autopsy 的规矩：别的项目的资料不入库 |

## 3. 实现计划（4 棒）

依赖关系：`M1 → M2 → M3 → M4`；M1 可独立发布验收。

---

### 棒 M1 · S · 骨架 + 静态深度审查（**不需要 LLM**）

**做什么**
1. Job 状态机：内存队列 + 线程池 + 状态落盘 `.data/qa/jobs/<jobId>.json`（PENDING→…→DONE/FAILED，含各 phase 时间戳）
2. 四个端点：`POST /api/qa/submit`（含 `scope` 匹配器与 glob 规范化校验）、`GET /api/qa/jobs/{id}`、`GET /api/qa/reports/{id}`、`GET /api/qa/tree?projectId=`（目录树 + Maven 模块清单，本地路径即时可得，git 依赖工作副本缓存）（复用 SourceResolver + ProjectScanner + LintEngine + CheckupEvaluator 组装 qaReport，③ 整档标「未执行」）
3. **scope 过滤层**：glob 匹配器（include/exclude，工作副本内规范化）+ `review`（引擎入口裁剪）/ `focus`（引擎出口分桶）两种语义 + `outOfScopeSummary` 计数
4. 前端 `/qa`：输入卡（整仓/圈定范围切换 + 目录树勾选 + LLM 开关，此阶段置灰提示「需配置」）+ 进度条（5 phase）+ 报告范围横幅 + 面板 A/C（C 走规则 good 片段模板）/ D（仅清单）
5. 快照历史：`.data/qa/<projectId>/`，复用 autopsy-snapshot 模式；不同 scope 的报告并存可对比

**验收**：填本仓地址 → 出报告且与 `/autopsy` 同地址的 P0/P1 数一致（两条链路同源判据，数字打架就是 bug）；填慢网 git 地址 → 页面不卡死，进度条动，FAILED 有原因。**局部检测专项**：只勾一个子目录跑 `review` → 所有 findings 的 file 都在圈内、横幅显示正确占比、圈外明确标「未检查」；同范围跑 `focus` → 圈内明细一致，圈外只出计数；勾一个不在仓库根内的越界 glob（`../../etc`）→ 拒绝且报错可读。

---

### 棒 M2 · S · LLM 层（补 LLM 语义层 0/43 的第一个洞）

**做什么**
1. `LlmClient`：OpenAI-compatible、超时/重试/单次请求体积上限、日志不记 key 不记 prompt 全文
2. 配置三档（arsenal.json / env），前端加「LLM 已配置/未配置」状态位（`GET /api/qa/llm-status`，只回状态不回 key）
3. `LintEngine` 的 `hasLlm` 占位（reasonFor，约 :399）改为**条件启用**：Job 上下文 + key 已配置 → 走真判定，产出 `{verdict, lines, reason}`，报告里标注判定来源 = LLM；否则维持占位归 skipped。同步链路（`/autopsy`、`/api/lint`）行为不变
4. MCP/CLI 不做，留 P2

**验收**：配 key 后，挑一条 llm 规则的正/反样本各判一次（verdict 正确、带 lines 证据）；不配 key，M1 验收全过（降级不回归）。

---

### 棒 M3 · M · 语义深检

**做什么**
1. Triage 甄别器（1.2-② 四类信号，输出候选文件 + 每个入选理由）；候选池 = scope 内文件，未选中项（含 `scopeFilteredOut`）全部计入披露
2. 分批 prompt 管线：代码窗口 + 项目 facts 摘要 → 语义 finding JSON（契约见 1.2-③），解析失败重试一次后归 skipped（**不许静默丢**）
3. 面板 B 上线：confidence 徽章 + 「语义深检未执行」降级横幅
4. `llmUsage` 记账：model / filesSent / tokens，报告页可展开

**验收**：拿 bug-by-design 的 `qa-fixtures` 演示仓（本棒新建：埋 1 个边界、1 个并发、1 个空指针类 bug）跑深检，三个至少抓到两个且 file:line 对得上；抓不到不判死 —— 首版接受召回率偏低，**接受标准写进 fixtures 的 README**。

---

### 棒 M4 · M · 逐点优化方案 + 测试建议

**做什么**
1. 方案聚合器：findings 聚类去重 → 逐点 before/after 生成（LLM 模式生成真代码差异；离线模式规则 good 片段 + 上下文拼接）
2. 面板 C 升级：代码对照视图 + 来源标注（`rule:<id>` / `llm`）
