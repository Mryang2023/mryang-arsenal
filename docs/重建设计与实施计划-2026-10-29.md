# 杨先生的军火库 · 重建设计与实施计划

> 日期：2026-10-29
> 范围：产品定位、信息架构、核心工作流、产物与验收、技术架构、六周实施路线
> 依据：2026-10-29 对本仓与真实项目 `command-center-backend` 的实测。复现命令见附录 A。

---

## 0. 一页结论

**它现在的问题不是「功能少」，是「没有一条链路以交付物结束」。**

先看七个实测事实：

| # | 事实 | 实测结果 |
|---|---|---|
| 1 | 菜单规模 | 11 个一级入口 + 18 个二级入口（4 个装配台页 + 10 个步骤 + 4 个项目工坊页），至少 7 个与「把项目变合规」没有连接 |
| 2 | 导入真实项目 | 438 个文件、221 条问题、42/69 条规则执行、27 条跳过；报告只能看，不能出补丁、不能验证 |
| 3 | 生成脚手架 | 53 个文件，`mvn -DskipTests package` 能过；`mvn test` 2/2 失败（Testcontainers 要 Docker，`ApplicationTests` 要外部 MySQL） |
| 4 | 项目档案 | 真实项目打开后：0 张表、0 个 DDL 脚本、0 行章程；六视图的业务/产品部分大量 `TODO` |
| 5 | 规则可信度 | 69 条规则中，51 处阿里巴巴引用只有 1 处带版次、16 处连章节号都没有，27 处来源没有引文；43 条依赖 LLM，而 LLM 默认未配置 |
| 6 | 测试能力 | 后端 21,164 行 Java、0 个测试文件；站内「测试建议」只是文字，不是可运行的测试 |
| 7 | 验证链 | 2330 项断言、238 秒、4 条已知失败；验的是「站内数据自洽」，不是「用户能不能完成一件事」 |

**重建成什么：**

> 一个个人工程交付工作台：把一个代码仓库，从「不知道合不合规」，推进到「有报告、有补丁、有测试、有验收、可归档」。

**五个主菜单：** 工作台 / 项目 / 新建项目 / 规范库 / AI 护栏。设置收进右上角齿轮。

**一条主链路：**

```
接入 → 基线体检 → 问题清单 → 生成修复 → 沙箱验证 → 交付物
                                      ↘ 生成测试 ↗
```

**六类产物：** 体检报告、修复补丁、测试包、架构包、脚手架、AI 护栏包。

**三个阶段、六周：**

| 阶段 | 时间 | 目标 | 验收 |
|---|---|---|---|
| 0 | 第 1 周 | 导入 → 报告 → 下载，跑通一条链路 | 任意 Java 项目 10 分钟内出报告 |
| 1 | 第 2–3 周 | 问题 → 补丁 → 编译/复跑/测试验证 | 10 类问题可自动修复并验证 |
| 2 | 第 4–5 周 | 测试生成、脚手架执行门、AI 回验 | 生成测试红→绿；脚手架测试全绿 |
| 3 | 第 6 周 | 规则夹具、CI、清理与固化 | 69/69 可自动规则有夹具；0 个孤儿菜单 |

**你能立刻得到的四件事：**

1. 接手任何 Java/Spring Boot 项目，10 分钟内拿到一份带文件行号、规则出处、修复建议的体检报告。
2. 选中问题，生成可应用的补丁；在副本里编译、复跑、跑测试，验证通过再拿走。
3. 看到「哪些类没有测试」，生成 JUnit 用例，并拿到「修复前红、修复后绿」的证据。
4. 新项目从选型到可编译可测试的骨架，下载即用；AI 护栏包让 Cursor/Claude 按同一套规则写。

## 1. 现状：实测证据

### 1.1 我实际跑了什么

| 动作 | 命令/入口 | 结果 |
|---|---|---|
| 导入并质检真实项目 | `POST /api/qa/submit`（`command-center-backend`，438 文件） | 14 秒完成；221 条问题；42/69 规则执行；27 条跳过；0 条语义结论；26 条「测试建议」中 25 条明确 `not-run`、1 条无 `draftCases` |
| 查看项目档案 | `GET /api/projects/{id}/dossier` | `tables=0`、`scripts=0`、`charter.found=false` |
| 运行体检 | `POST /api/projects/{id}/checkup` | 同上：221 条问题 + 8 条观察项 |
| 编译生成物 | 解压 `export-standard.zip` 后 `mvn -DskipTests package` | 成功，53 个文件 |
| 跑生成物测试 | 同一目录 `mvn test` | 2 个测试类全错：`ApplicationTests` 缺数据源；`UserServiceTest` 缺 Docker |
| 检查后端测试 | `find arsenal-server/src/test` | 0 个文件 |
| 规则溯源统计 | 解析 `arsenal-rules/**/*.json` | 69 条；50 处阿里巴巴引用无版次；27 处来源无引文；43 条声明 `llm` |
| 菜单清点 | `src/components/Shell.tsx` + `stack/wizard.ts` + `projects/nav.ts` | 11 个一级、18 个二级 |

### 1.2 七个事实的展开

**事实 1：菜单是「模块目录」，不是「任务流程」。**

当前菜单：

```
概览 / 规则库 / 最佳实践案例库 / 场景案例库 / 装配台(4 页 10 步) /
项目工坊(项目管理·项目侦察·项目档案·质检台) / 图标库 / 出图服务 /
校验台 / 工程规范 / 导出中心
```

其中至少 7 个入口与「把一个项目变合规」没有连接：

| 入口 | 实际是什么 | 与主流程的关系 |
|---|---|---|
| 最佳实践案例库 | 5 条技术主线的静态代码切片 | 只能读，不能应用到项目 |
| 场景案例库 | 8 个独立模拟器（缓存、并发等） | 与当前项目无关 |
| 图标库 | 图标素材墙 | 与主流程无关 |
| 出图服务 | 依赖仓库外 `wrench-ai` 技能的独立服务 | 与项目体检割裂 |
| 校验台 | 粘贴一段代码的临时校验 | 结果不进入项目、不留档 |
| 工程规范 | 军火库自身的治理台 | 不是用户项目的规范 |
| 导出中心 | 规则导出 | 与项目、修复、验收不连接 |

**事实 2：导入项目只产生「读数」，不产生「可用的东西」。**

对 `command-center-backend` 的真实结果：

- 221 条问题，分布在 16 条规则；其中 `WEB-CTRL-002`（缺 `@Valid`）35 条、`REL-LOG-001`（System.out）34 条、`WEB-CTRL-005` 34 条。
- 至少 28 条来自 `.wb-tmp/` 与根目录 `SmokeCcgp.java` 这类临时文件——扫描没有排除它们。
- 27 条规则被跳过：19 条需要 LLM、5 条 AST 无检查器、3 条人工。页面披露了「跳过」，但没有给人工规则生成待办清单。
- 26 条「测试建议」里 25 条明确 `draftCases.status = not-run`，1 条连 `draftCases` 段都没有；内容是同一句话的变体：「命中 N 处且找不到同名测试」。不是可运行的测试。
- 没有「导出问题清单」、没有「生成补丁」、没有「修复后复跑」。

**事实 3：生成物能编译，但不能自证可运行。**

`export-standard.zip` 的真实测试结果：

```
Tests run: 2, Failures: 0, Errors: 2
- ApplicationTests.contextLoads：Failed to load ApplicationContext（MyBatis 需要 DataSource）
- UserServiceTest：Could not find a valid Docker environment（Testcontainers）
```

README 里写着「当前组合：可以跑起来」，但默认测试需要一个外部 MySQL 和一个 Docker；没有 `demo` 测试档，也没有「测试不通过就不许下载」的闸门。`verify:scaffold` 只检查文件在不在、import 有没有对应依赖，**从不编译、从不运行**。

**事实 4：项目档案只索引「你已经写好的文档」，不生成。**

- 它期待项目里已经有 `docs/db/`、DDL 脚本、开发章程；没有就显示 0。
- 对一个正常项目，档案页是空的——这正是「导入了本地项目，什么都生成不出来」的直接原因。
- 六视图对导入项目的草稿，业务/产品部分大量 `TODO`；这是诚实的，但产品没有把「待补清单」变成可执行任务。

**事实 5：规则本身没有受检。**

- 69 条规则，9 大类；35 条正则可执行、20 条声明 AST、43 条声明 LLM、22 条声明人工（有重叠）。
- 51 处「阿里巴巴Java开发手册」引用里，只有 1 处带版次（嵩山版/泰山版）；35 处有章节号，16 处连章节号都没有；27 处来源没有引文。69 条规则中只有 15 条的来源同时具备「版次 + 章节 + 引文」。
- 一条规则是否真的能抓到它声称的问题、误报率多少，没有任何夹具或实测证明。
- 结果：用户无法判断「这条规则对不对、凭什么、在我项目里算不算问题」。

**事实 6：没有测试能力。**

- 后端 0 个测试文件；21,164 行 Java 靠 2330 项前端脚本断言「间接保护」。
- `ReproAuthor` / `ReproRunner` 确实能生成并运行复现测试，但它要求 LLM，默认关闭；每次 job 最多 5 条。
- 生成脚手架只有冒烟测试和少量切片测试，且默认跑不起来。
- 所以「你自己的测试功能都没有」这句话，在默认配置下是准确的。

**事实 7：验证链测错了对象。**

2330 项断言守的是：生成物清单一致、导出产物逐字节一致、规则 schema、页面存在性、截图矩阵……这些有价值，但它们回答的是「站内数据有没有漂移」，不是「用户能不能完成一次体检→修复→验收」。一条链路 238 秒、4 条已知失败、13 条跳过，却没有任何一条断言在验证「生成的补丁能不能编译」「生成的测试是不是红的」。

### 1.3 根因：不是 bug，是设计

1. **以模块为中心建菜单。** 每个功能是一个「站点」，站点之间靠用户自己脑补关系。
2. **没有产物模型。** 页面只有「展示」，没有「下载/应用/归档」；QA 报告 900KB，却只能看。
3. **没有执行闭环。** 扫描、生成、修复都不进入沙箱，没人验证结果。
4. **规则自身未受检。** 规则是产品的地基，但地基没有出处校验、没有夹具、没有误报度量。
5. **LLM 是静默单点。** 43 条规则依赖它，默认没配；页面虽然披露「跳过」，但产品没有「没有 LLM 也能完成一次交付」的路径。
6. **验证链替代了产品验收。** 站内自洽的绿灯，掩盖了「用户拿不走东西」的红灯。

## 2. 重新定位

### 2.1 一句话

> 军火库不是「规范展示站」，是「个人工程交付工作台」。
> 它只对一件事负责：把一个仓库，从「不知道合不合规」，推进到「有报告、有补丁、有测试、有验收」。

### 2.2 主链路

```
┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
│ 接入     │ → │ 基线体检 │ → │ 问题清单 │ → │ 生成修复 │ → │ 沙箱验证 │ → 交付物
│ Project  │   │ Run      │   │ Finding  │   │ Patch    │   │ Verify   │   Artifact
└─────────┘   └─────────┘   └─────────┘   └─────────┘   └─────────┘
                                                │
                                                └→ 生成测试（红→绿）
```

两条支线：

- **新建项目**：选型 → 生成 → 沙箱构建/测试 → 下载。
- **AI 护栏**：导出规则包 → AI 写代码 → 回验 → 生成补丁/测试。

### 2.3 三个用户故事

**故事 A：接手一个项目（最重要的主线）**

1. 在「项目」里添加本地路径。
2. 点「体检」：得到健康分、覆盖率、Top 问题。
3. 在「问题」里按「可自动修复」筛选，选中 10 条。
4. 点「生成补丁」：看到 diff。
5. 点「在副本中验证」：编译通过、复跑命中减少、测试通过。
6. 下载补丁和报告，进自己的分支。

**故事 B：让 AI 写功能**

1. 在「AI 护栏」选择项目与规则集，下载 `.cursorrules` / `CLAUDE.md` / MCP 配置。
2. AI 写完代码，回到「项目 → 回验」，粘贴 diff 或指向 commit。
3. 得到「新增违规 N 条」，一键生成补丁与测试。
4. 验收报告进 PR。

**故事 C：开新项目**

1. 在「新建项目」选形态、技术栈、模块、环境、部署。
2. 右侧实时显示「可运行性 5/5、冲突 0、预计 53 个文件」。
3. 点「生成并在沙箱构建」：编译 + 测试（H2/demo，无 Docker）全绿才允许下载。
4. 下载 `all.zip`：代码、测试、Flyway、Dockerfile、Compose、CI、ARCHITECTURE.md、AI 护栏文件。

## 3. 新信息架构（菜单）

### 3.1 五个主菜单

| 菜单 | 回答的问题 | 输入 | 输出（交付物） | 验收 |
|---|---|---|---|---|
| **工作台** `/` | 我现在该做什么？ | 当前项目、最近 run | 下一步任务、最近交付物、全局健康度 | 打开 3 秒内知道下一步 |
| **项目** `/projects` | 这个项目现在什么状态？ | 仓库/快照 | run、问题、补丁、测试、报告 | 导入到报告 < 10 分钟 |
| **新建项目** `/new` | 新项目怎么起步？ | 选型 | 可编译可测试的 zip | 沙箱构建 + 测试全绿 |
| **规范库** `/rules` | 这条规矩凭什么？怎么用？ | 规则/代码 | 规则详情、试跑结果、夹具结果 | 每条规则有出处 + 验证 |
| **AI 护栏** `/guard` | 怎么让 AI 守规矩？ | 规则/项目 | prompt/cursorrules/CLAUDE.md/MCP | 客户端配置可用；回验有结果 |

设置（`/settings`）收进右上角齿轮：引擎、LLM、忽略规则、存储、任务并发。

### 3.2 新旧映射：哪些留下、哪些合并、哪些下线

| 旧入口 | 新去处 | 处理方式 | 理由 |
|---|---|---|---|
| 概览 | 工作台 | 重写 | 从「门户」变成「下一步」 |
| 规则库 | 规范库 → 规则 | 保留并增强 | 核心资产 |
| 最佳实践案例库 | 规范库 → 最佳实践 | 合并 | 是规则的「怎么做」补充 |
| 场景案例库 | 规范库 → 场景 | 合并 | 独立模拟器不进入主流程 |
| 装配台 | 新建项目 | 保留并加执行门 | 从 10 步压到 7 步 |
| 项目工坊 | 项目 | 合并为项目页签 | 四个页面本来就是一个项目的四个视角 |
| 图标库 | 新建项目 → UI 素材 | 移出主菜单 | 素材不是任务 |
| 出图服务 | 项目 → 交付物 → 架构图 | 合并；v1 用内置 SVG | 外部技能不适合当一级菜单 |
| 校验台 | 规范库 → 试跑 | 合并 | 一次性工具，结果应留档 |
| 工程规范 | `docs/governance/`（仓库内部） | 移出主菜单 | 它是军火库自己的章程，不是用户项目的规范 |
| 导出中心 | AI 护栏 | 合并 | 导出是护栏的一部分 |

**结果：主菜单从 11 个降到 5 个；每个菜单都对应主链路上的一段，或者一个跨切面能力。**

### 3.3 每个菜单你能干什么

#### 工作台

- 顶部：当前项目、健康分、最近一次 run、快照指纹。
- 「今天该做什么」三张卡：
  - 可自动修复的 N 条 → 去修复。
  - 缺测试的 N 个类 → 去生成测试。
  - 需要人工确认的 N 条 → 打开清单。
- 「最近交付物」：报告、补丁、测试包，带时间与状态。
- 「全局」：规则覆盖率、项目健康度趋势。
- 空态：只有一个 CTA——「导入第一个项目」。

#### 项目

`/projects`：项目列表。每行显示：名称、来源、快照、最近 run、健康分、状态（未体检/有阻塞/已交付）。

`/projects/[id]`：项目主页，六个页签：

| 页签 | 回答 | 主要输出 |
|---|---|---|
| 总览 | 整体怎么样？ | 健康分、五维分解、覆盖率披露、Top 5 问题 |
| 问题 | 有哪些问题？ | 可筛选清单、证据、规则出处、修复预览 |
| 修复 | 怎么改？ | 补丁、验证结果、下载 |
| 测试 | 有没有测试、缺什么？ | 现有测试结果、覆盖缺口、生成测试、红→绿证据 |
| 交付物 | 能拿走什么？ | 报告、架构包、API 文档、DDL、测试包、AI 包 |
| 设置 | 这个项目怎么检？ | 忽略路径、规则档、引擎、LLM 开关 |

项目主页线框：

```
┌ 项目 command-center-backend   快照 dir:550:9267701   [运行体检] ┐
│ 健康分 62 / 100   规范 48  架构 70  测试 20  交付 55  文档 30  │
│ 本次覆盖：42/69 自动执行 · 27 未验证（19 需 AI / 5 AST / 3 人工）│
├ 下一步 ───────────────────────────────────────────────────────┤
│ ① 修 12 个可自动修复的 P0            [生成补丁]                │
│ ② 为 8 个无测试的 Controller 补测试   [生成测试]                │
│ ③ 3 条需要人工确认的规则              [查看清单]                │
├ 最近交付物 ───────────────────────────────────────────────────┤
│ report-20261029.md · patch-0001.diff · tests-0003.zip          │
└───────────────────────────────────────────────────────────────┘
```

#### 新建项目

7 步，不是 10 步：

1. 形态（单体/分层/微服务）
2. 技术栈基底
3. 功能模块
4. 数据与连接（数据库/缓存/迁移）
5. 运行与部署（容器/CI/监控/日志）
6. 质量门（测试策略/覆盖率/静态检查）
7. 生成与验证

右侧常驻「可运行性」面板：

```
必需能力 5/5 已满足   冲突 0   预计 53 个文件
[生成并在沙箱构建]  →  编译 ✓  测试 ✓  [下载 all.zip]
```

生成物必须包含：

- 可编译的 `pom.xml` / `build.gradle`
- 单元测试 + 切片测试 + 冒烟测试（`demo` 档，H2，无 Docker）
- Flyway、Dockerfile、Compose、CI 配置
- `ARCHITECTURE.md`、`README.md`、风险报告
- `.cursorrules` / `CLAUDE.md`（可选，来自规则库）

#### 规范库

四个页签：

- **规则**：69 条，按分类/严重度/可执行层筛选。
- **最佳实践**：5 条技术主线的完整代码切片。
- **场景**：8 个场景的选型与代码。
- **试跑**：粘贴代码，跑正则 + AST，结果直接链到规则详情。

规则卡片必须显示：

```
WEB-CTRL-002  @RequestBody 必须加 @Valid
MUST · 可自动检出（AST） · 在你的项目命中 35 次
出处：阿里巴巴Java开发手册（嵩山版）§4 安全规约【强制】· 引文 …
为什么：缺 @Valid 时 DTO 约束静默失效
怎么验：bad.java / good.java 夹具已通过（2026-10-29）
```

「规则健康」页：溯源完整率、夹具通过率、最近实测误报样本。

#### AI 护栏

- **生成护栏包**：选择格式（prompt / cursorrules / CLAUDE.md / AGENTS.md / MCP）、严重度、分类、是否带示例/检查项。
- **安装状态**：检测当前仓库是否已有这些文件，显示「缺失/过期/版本一致」。
- **MCP**：展示配置片段、启动命令、工具清单、连接测试。
- **回验**：粘贴 AI 生成的 diff 或指向 commit，跑同一套规则，输出违规清单与补丁。
- **护栏覆盖率**：哪些规则能被哪个客户端执行；哪些只能人工。

#### 设置

- LLM：状态、模型、连接测试、预算上限；未配置时明确写「语义层不运行，报告只含静态结论」。
- 引擎：正则/AST/LLM/人工的开关与优先级。
- 忽略规则：`.gitignore`、build 目录、临时文件、生成代码。
- 存储：缓存根、保留天数、清理。
- 任务：并发、超时。

### 3.4 页面状态规范

每个页面必须能说清五种状态，不许把「没跑」说成「没问题」：

| 状态 | 文案要求 | 示例 |
|---|---|---|
| 空 | 告诉用户下一步 | 「还没有项目，先导入一个」 |
| 载入 | 说明在做什么 | 「正在摄取 438 个文件」 |
| 离线 | 说清是后端不在，不是故障 | 「后端 :3011 未启动，项目功能不可用」 |
| 未验证 | 说清为什么、缺什么 | 「19 条规则需要 AI，本次未运行」 |
| 已验证 | 给出证据与时间 | 「补丁在副本编译通过，复跑命中 12→0」 |

## 4. 核心工作流设计

### 4.1 接入（Project）

- 输入：本地路径或 https git 地址。
- 动作：复制到缓存、生成快照指纹、排除构建目录/临时目录/生成代码。
- 输出：项目条目、快照、可体检状态。
- 要求：
  - 源与缓存落点重叠必须拒绝（已有）。
  - 忽略规则可配置，默认排除 `.git`、`node_modules`、`target`、`dist`、`build`、`.wb-tmp`、`*.min.*`。
  - 保留原目录不变，所有写操作只在缓存副本。

### 4.2 基线体检（Run）

- 输入：项目、快照、规则档、引擎开关、范围。
- 动作：正则 → AST → 语义（可选）→ 人工清单。
- 输出：`run.json`、`findings.jsonl`、`coverage.json`。
- 要求：
  - 每个 finding 必须有：规则 ID、文件、行、列、证据片段、规则出处、执行层（regex/ast/llm/manual）。
  - 覆盖率必须披露：执行/跳过/不可判定，以及原因。
  - 同一规则在同一文件的重复命中要折叠，但保留计数。
  - 耗时目标：500 文件项目 < 60 秒（静态层）。

### 4.3 问题清单（Finding）

- 视图：按严重度 / 按规则 / 按文件。
- 每条显示：严重度、规则标题、文件:行、证据、为什么、出处、可执行层、是否可自动修复。
- 操作：选中、查看修复预览、加入修复批次、标记「人工已确认/忽略（带原因）」。
- 忽略必须落档：谁、何时、为什么，下次 run 不再报，但报告里保留「已忽略 N 条」。

### 4.4 生成修复（Patch）

两种修复器：

1. **确定性 codemod**（优先）：
   - 例：`System.out` → `log.info`、缺 `@Valid` 补注解、字段注入 → 构造器注入、空 catch 补日志、`@Override` 补齐、日志字符串拼接 → 占位符。
   - 每条修复器有 `bad.java` / `good.java` 夹具，CI 必须跑。
2. **LLM 修复**（可选）：
   - 只对语义规则；输出必须是 diff + 解释。
   - 必须通过「应用 → 编译 → 复跑 → 测试」才展示为「已验证」；否则标「未验证」。

补丁格式：

- 统一 diff（`--- a/...` / `+++ b/...`），可用 `git apply`。
- 每个补丁带 `manifest.json`：findingIds、规则版本、生成器版本、输入快照、哈希。
- 默认不写用户原目录；只下载或写入工作副本。

### 4.5 沙箱验证（Verify）

- 复制项目到工作副本。
- 应用补丁。
- 编译（Maven/Gradle 自动识别）。
- 复跑同一套规则：命中数必须下降，且不新增 P0。
- 跑相关测试：新增失败即拒绝。
- 输出 `verify.json`：

```json
{
  "apply": "ok",
  "compile": { "status": "ok", "command": "./mvnw -q -DskipTests compile", "ms": 18342 },
  "lint": { "before": 12, "after": 0, "newP0": 0 },
  "tests": { "status": "ok", "run": 37, "failed": 0, "skipped": 2 },
  "verdict": "verified"
}
```

### 4.6 测试包（Test）

这是当前完全缺失、也是最容易被误解的一块。分三层：

1. **现有测试执行**：在沙箱跑 `mvn test` / `gradle test`，解析 surefire，得到「哪些测试通过/失败/跳过」。
2. **覆盖缺口**：解析测试类与主类对应关系，列出没有测试的 Controller/Service；不伪造覆盖率。
3. **生成测试**：
   - 对缺测试的类，生成最小 JUnit 5 用例。
   - 每个生成测试必须证明「修复前红、修复后绿」；证明不了的不展示。
   - 输出测试源码 + 运行日志 + 结论。

没有 LLM 时，第 1、2 层仍然可用；第 3 层明确标「需要 AI」。

### 4.7 交付物（Artifact）

每次 run 结束，产物目录：

```
.data/projects/<id>/runs/<runId>/
├── run.json
├── findings.jsonl
├── coverage.json
├── report.md
├── report.html
├── patches/
│   ├── 0001-valid-annotation.diff
│   └── manifest.json
├── tests/
│   ├── UserControllerTest.java
│   └── run.log
├── verify.json
└── manifest.json
```

所有产物带哈希、规则集版本、引擎版本、快照指纹，可复现、可归档。

### 4.8 新建项目分支

复用现有装配台的数据与模板，但加三道门：

1. **能力门**：必需槽位未满足 → 禁止生成。
2. **编译门**：生成后在沙箱编译；失败显示日志，不显示「可下载」。
3. **测试门**：`demo` 档（H2，无 Docker）必须全绿；否则标「未验证」并列出失败。

### 4.9 AI 护栏分支

- 导出包带版本号与哈希；客户端配置检测。
- MCP 工具从「只读规则」扩展到「体检/补丁/测试」：
  - `arsenal_list_rules`
  - `arsenal_lint_file`
  - `arsenal_audit_project`
  - `arsenal_generate_patch`
  - `arsenal_generate_test`
- 回验：任何 AI 产出的 diff 都能跑同一套规则，结果写回项目 run。

### 5.1 六类产物

| 产物 | 内容 | 生成方式 | 验收门 |

## 6. 规则体系重建

### 6.1 溯源：从「一句引用」到「可核对的事实」

新增 `arsenal-rules/sources.json`：

```json
{
  "id": "alibaba-java-manual",
  "title": "阿里巴巴Java开发手册",
  "edition": "嵩山版",
  "year": 2020,
  "clause": "异常日志 · 日志规约【强制】",
  "url": "https://…",
  "accessedAt": "2026-10-29",
  "licenseNote": "引用关键句用于溯源，不复制全文"
}
```

规则改为引用 `sourceId + clause`，不再写自由文本。规则 lint 在构建期失败的条件：

- 引用不存在；
- 缺版次/条款/链接；
- 声明 `industry-standard` 但没有引文；
- 只有 `llm` 层但没有人工清单。

### 6.2 分层：每条规则必须说清「怎么验」

| 层 | 含义 | 要求 |
|---|---|---|
| regex | 正则可判定 | 必须给 pattern + targetGlob + expect |
| ast | 语法/符号可判定 | 必须注册检查器；没有就降为 llm/manual，不许假装 |
| llm | 语义判定 | 必须要求文件行号 + 引文；无行号视为无效 |
| manual | 人工判定 | 必须给可勾选清单，不是一句「人工过目」 |

目标：69 条规则全部有明确层；`llm` 不是默认兜底。

### 6.3 夹具：给规则本身写测试

`arsenal-rules/_fixtures/<ruleId>/`：

```
bad.java     # 必须命中，期望行号
good.java    # 必须不命中
meta.json    # 期望命中数、适用栈
```

CI 跑 `npm run verify:rules`：

- 每条自动规则在 bad 上命中数 == 期望；
- 在 good 上命中数 == 0；
- 人工规则必须有清单；
- 输出每条规则的「最近验证时间」。

### 6.4 规则健康页

- 溯源完整率（目标 100%）。
- 夹具通过率（目标 100%）。
- 最近一次在真实项目上的命中/误报抽样。
- 「这条规则在你的项目命中 N 次」——从项目 run 反查。

### 6.5 不做什么

- 不增加规则数量，先把 69 条做实。
- 不做多语言（v1 只 Java 17/21 + Spring Boot 3 + MySQL/PostgreSQL）。
- 不把「项目自主决策」伪装成行业标准；`project-decision` 必须显式标注。

## 7. 技术架构

### 7.1 领域模型

```
Project 1─n Snapshot 1─n Run 1─n Finding
Run 1─n Artifact
Run 1─n Patch 1─1 Verify
Run 1─n TestPlan 1─n GeneratedTest
```

关键原则：

- Run 是唯一执行单元；所有结果挂在 Run 上，不散落在页面状态里。
- Artifact 是唯一交付单元；没有 Artifact 的页面不算完成。
- Finding 只描述「哪里不对」，不描述「怎么改」；修复是 Patch。
- Verify 只描述「改完以后怎么样」；没有 Verify 的 Patch 标「未验证」。

### 7.2 存储布局

```
.data/
├── projects/
│   └── <projectId>/
│       ├── project.json
│       ├── snapshots/<fingerprint>/
│       └── runs/<runId>/
│           ├── run.json
│           ├── findings.jsonl
│           ├── coverage.json
│           ├── report.md
│           ├── patches/
│           ├── tests/
│           ├── verify.json
│           └── manifest.json
└── tmp/            # 沙箱工作副本，跑完即删
```

v1 用文件系统 + JSON/JSONL，不引入数据库；原子写（临时文件 + rename），避免半份报告。

### 7.3 API（v2）

```
POST   /api/v2/projects                     添加/摄取
GET    /api/v2/projects                     列表
GET    /api/v2/projects/{id}                详情 + 快照
POST   /api/v2/projects/{id}/runs           提交体检
GET    /api/v2/runs/{runId}                 状态/进度
GET    /api/v2/runs/{runId}/findings        问题（筛选/分页）
POST   /api/v2/runs/{runId}/patches         生成补丁
POST   /api/v2/patches/{id}/verify          沙箱验证
GET    /api/v2/runs/{runId}/tests           测试计划/结果
POST   /api/v2/runs/{runId}/tests/generate  生成测试
GET    /api/v2/runs/{runId}/artifacts       产物列表
GET    /api/v2/artifacts/{id}/download      下载
POST   /api/v2/scaffolds                    生成脚手架
POST   /api/v2/scaffolds/{id}/verify        构建+测试
GET    /api/v2/rules/{id}/provenance        出处
POST   /api/v2/rules/{id}/fixtures/run      夹具
```

保留 v1 端点，前端逐步迁移；旧页面重定向到新路由。

### 7.4 引擎

```java
interface Engine {
  String id();              // regex / ast / semantic / manual
  boolean deterministic();
  EngineResult run(RunContext ctx);
}

record EngineResult(
  List<Finding> findings,
  List<SkippedRule> skipped,
  Coverage coverage,
  Map<String, Object> metrics
) {}
```

- 引擎只产出 findings + coverage，绝不产出「通过」。
- 每个 finding 带 `evidence`（文件、行、列、片段）。
- 引擎版本写进 run manifest。

### 7.5 沙箱

统一 `SandboxService`：

- 复制项目到 `.data/tmp/<runId>/`。
- 应用 patch。
- 自动识别 Maven/Gradle；执行编译/测试。
- 超时、输出上限、进程强杀；不写用户原目录。
- 复用现有 `RunSandbox` / `ReproRunner` 的安全约束（不拼 shell、工作副本、超时）。

### 7.6 前端

- 保持 Next.js 静态站 + Spring Boot；规则库/AI 护栏可离线，项目功能需要后端。
- 项目页以 `runId` 为 URL 状态：`/projects/[id]/runs/[runId]`，可分享、可刷新。
- 去掉跨页 `activeProject` 隐式状态；项目 ID 从路由来。
- 复用现有 `AutopsyLab` / `QaLab` / `DossierConsole` 面板，先嵌入新页签，再逐步重构。

### 7.7 LLM 策略

- 配置：`ARSENAL_LLM_KEY` 环境变量；设置页只显示状态与模型，不回显 key。
- 未配置：语义层不运行，报告首页明示；43 条规则进入「未验证/人工清单」。
- 已配置：批量语义检测，要求行号 + 引文；无行号丢弃；预算上限；每次 run 记录 token 与费用。
- 生成测试/补丁：必须经过沙箱验证才展示为「已验证」。

### 7.8 验证与 CI

- 后端：JUnit 5，先覆盖 RunStore / ReportService / PatchService / VerifyService。
- 规则：`verify:rules` 跑全部夹具。
- 端到端：`npm run e2e:delivery` —— 导入 fixture → 体检 → 生成补丁 → 验证 → 断言产物。
- CI：GitHub Actions（或 GitLab CI），JDK 21 + Node 24；跑后端测试、前端 typecheck、规则夹具、e2e。
- 旧的 2330 项链保留，但降级为「站内一致性」；新增「产品验收」链，二者分开报告。

## 8. 实施路线

> 估算口径：一个人 + AI 协作，每周 20–25 小时。全职可压缩到 3–4 周。

### 阶段 0（第 1 周）：让一条链路闭环

目标：导入 → 报告 → 下载。

任务：

1. 新建 `src/app/projects/[id]/page.tsx`，六个页签；先嵌入现有 `AutopsyLab` / `QaLab` / `DossierConsole`。
2. 后端新增 `runs` 包：`RunStore`、`ArtifactStore`、`Manifest`。
3. `ReportService`：把现有 QA report + facts 渲染成 `report.md` / `report.html`。
4. 项目页加「下载报告」。
5. 重写 `Shell.tsx` 导航为 5 项；旧路由 301 重定向。
6. 扫描忽略 `.wb-tmp`、根目录临时脚本；忽略规则可配置。
7. 规则溯源 lint：缺版次/条款/引文的规则在构建期失败。
8. 后端加 10 个 JUnit 测试（RunStore/ReportService）。
9. `e2e:delivery`：fixture 项目导入 → 报告存在 → 断言包含文件行号与规则出处。

验收：

- 任意 Java 项目导入后 10 分钟内出报告。
- 报告可下载，含覆盖率披露与 Top 问题。

## 11. 风险与需要你拍板的事

### 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 补丁改坏用户代码 | 信任崩塌 | 只在副本应用；默认只下载；显式确认才写工作区 |
| 规则误报 | 报告不可信 | 夹具 + 真实项目抽样 + 一键「标记误报」 |
| LLM 成本/延迟 | 体验差 | 确定性优先；预算上限；语义层可关 |
| 范围膨胀 | 又变成模块陈列馆 | 锁定一条主链路、五个菜单；新功能必须挂在链路上 |
| 外部依赖（archify/wrench-ai） | 换机不可用 | v1 用内置 SVG；外部技能仅作增强 |
| 旧 2330 项链维护成本 | 拖慢迭代 | 降级为站内一致性；新增产品 e2e 作为主门 |

### 需要你拍板

1. **v1 范围**：只做 Java 17/21 + Spring Boot 3 + MySQL/PostgreSQL？建议是。多语言会稀释质量。
2. **LLM**：用现有 DeepSeek OpenAI 兼容端点？预算上限多少？没有 key 时接受「静态报告 + 人工清单」吗？
3. **写不写工作区**：默认只出补丁/压缩包，还是允许「一键应用到当前分支」？建议默认不写。
4. **军火库自身章程**：同意移到 `docs/governance/`、不再占产品菜单吗？
5. **出图**：同意 v1 用内置 SVG、外部 archify 作为可选增强吗？
6. **排期**：六周（每周 20–25 小时）是否可接受？如果只能全职投入，可压到 3–4 周。
