## 2. 新技术的立项门槛（先立规矩，再谈扩张）

三原则是「写不出 bad/good 示例的不收录」。案例库三层化后，门槛要写死成**可机检的条件**，否则 B-4 的 4 个空家族会被随手填进半成品：

| # | 门槛 | 谁检 |
|---|---|---|
| T-1 | ≥ 2 个场景，每个场景都要有 `when` + `signals[]`（≥2 条可核对信号）+ `notSuitable`（≥2 条） | `build_cookbook()` |
| T-2 | 每个场景 ≥ 1 套方案，方案必须含 `flow` / `files[]` / `checklist` / `pitfalls` | `build_cookbook()` |
| T-3 | **至少 1 个真接口实验**：`lab.kind=mock-endpoint` 的代码里必须有 `HttpServer`（不接受 sleep 假装 IO） | `build_cookbook()` + `sync-content.mjs` |
| T-4 | 关联 ≥ 3 条真实规则 ID（拼错即报错，不静默） | `build_cookbook()` |
| T-5 | `references` ≥ 2 条，且每条有 url 或 note | 已有 |
| T-6 | **方案代码过自己的引擎零 MUST/NEVER 违规**（见 C-2） | `project-check` 新增 |
| T-7 | 每个实验必须在真 JDK 21 上跑通过一次，实测数字写进 `lab.baseline`（见 C-8） | 人工 + 断言 |

> 门槛进了校验层之后，「已比较过但尚未立项」的对照技术（线程池 / 响应式 / CompletableFuture）就不是空话：差哪一条一目了然。

## 3. P1 · 兑现（建议本轮做完）

### C-1 给 AI 的出口：案例包

| 项 | 内容 |
|---|---|
| 问题 | B-1。这个库的目的是让 AI 照抄，但 AI 现在读不到它。 |
| 做法 | 新增 `blueprint-pack` 导出，**纯前端**（数据已在 `src/generated/cookbook.json`）。两种粒度：① 全量包（一条技术主线三层全量）；② 场景级片段（勾选场景 → 一段可直接粘给 AI 的上下文）。渲染器新文件 `src/lib/blueprint-export.ts`，挂到导出中心新增的一类格式里。 |
| 内容硬要求 | 必须含 **notSuitable 与 pitfalls**。只给代码不给边界，AI 会在错误场景照抄 —— 这正是「不划边界的范例比没有范例更糟」在数据出口上的翻版。代码用语言围栏包裹，保留 `signals[]`。 |
| 改动面 | 新 `src/lib/blueprint-export.ts` + `ExportStudio.tsx` 接一类格式；**不动事实源、不动校验链** |
| 验收 | 导出文本里每个场景的 `notSuitable` 条数与事实源一致（断言）；代码围栏闭合（断言）；pack 体积超阈值时提示「改用场景级片段」 |
| 风险 | 低（纯前端）。体积随主线增长会膨胀 → 一开始就做「场景级片段」粒度，别只做全量包 |
| 棒次 | 1 棒（新文件，零冲突） |

### C-2 案例代码自证

| 项 | 内容 |

## 4. P2 · 纵深（内容成本最高，一条一棒）

### C-4 第二条技术主线：线程池 `thread-pool`

| 项 | 内容 |
|---|---|
| 理由 | 虚拟线程的 `pickWhen` 里已经拿线程池当对照；做成独立主线后两方能**互证**（同一场景两套技术，各自给适用条件，而不是一边倒地夸虚拟线程）。这是目前性价比最高的一条主线。 |
| 做法 | 新建 `tools/content/thread_pool.py` 出 `TOPIC`，在 `build_cookbook()` 注册；按第 2 节门槛 T-1~T-7 齐备。建议场景：**CPU 密集与混合负载**（虚拟线程的明确禁区）、**有限并发的外部依赖**（池化反而更稳）。 |
| 改动面 | 新内容源 + `build-content.py` 注册 + sync + 家族计数；前端零改动（三层路由已通用） |
| 风险 | 工作量最大。实验必须真跑（JDK 21 fork 子进程），参数要调到位 —— 参考虚拟线程那次的教训：并发连接数本身会变成瓶颈，跑出反直觉结果时**先怀疑实验设计，不要改结论** |
| 棒次 | 1~2 棒，**不要和别的内容源挤一棒** |
