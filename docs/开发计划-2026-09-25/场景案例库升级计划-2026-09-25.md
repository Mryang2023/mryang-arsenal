## 2. P1 · 内容层（治「不是我的场景」+「调参是假动作」）

### C1-1 补 6 个 Java 后端日常场景

**目标**：让「我的问题在这里」从 2/10 变成 8/10。

| # | 场景 id | 一句话 | 建议驱动参数 | 预计切片 |
|---|---|---|---|---|
| 1 | `idempotent-write` | 幂等与重复提交：重复下单/重复支付/重试风暴下的重复写 | 调用来源 / 重复窗口 / 一致性要求 / 有无全局 ID / 幂等存储 | 6~8 |
| 2 | `slow-sql` | 慢 SQL 与索引失效：一个接口把数据库拖垮 | 数据量 / 查询模式 / 索引现状 / 是否允许改表 / 紧急度 | 6~8 |
| 3 | `export-timeout` | 大文件导出超时：几十万行导出把网关打穿 | 行数 / 并发导出数 / 格式 / 时限 / 内存上限 | 6~8 |
| 4 | `distributed-tx` | 分布式事务一致性：跨服务写，一半成功一半失败 | 参与方数 / 一致性级别 / 时延容忍 / 补偿能力 / 幂等 | 6~8 |
| 5 | `file-upload` | 文件上传：大文件/断点续传/病毒扫描/存储选型 | 文件大小 / 并发 / 校验强度 / 存储 / 是否秒传 | 6~8 |
| 6 | `authz-masking` | 越权与数据脱敏：横向越权、敏感字段泄漏 | 数据敏感度 / 角色层级 / 粒度 / 审计要求 / 性能容忍 | 6~8 |

**改动**：`tools/content/cases/<id>.py`（每个 ~450 行）+ `build-content.py` 注册 + `arsenal-cases/meta.json` order。
**硬要求**（照现有 8 个的规矩）：每场景 4~5 条症状（带 `params`）、必须声明 `recommended`、`notSuitableFor` ≥2、切片 `notSuitable` 必填、`relatedRules` 尽量挂真实规则 id。
**验收**：build 绿 + `verify:cases` 33/33 + 新场景首屏命中 ≥1 + 症状点进去不空。
**成本**：每场景约 1~1.5 小时（含 SQL + Java 代码），6 个 ≈ 一整晚。建议**先做 #1 幂等 和 #2 慢 SQL** 当样板，确认口径后再铺开。

### C1-2 参数虚胖治理（本轮性价比最高）

**目标**：让「调参数」这件事重新算数。

三条处置，按参数性质分：

| 类型 | 数量 | 处置 |
|---|---|---|
| 告警型（参与 `conflicts`） | 9 | **保留**，但前端必须标注。参数卡上加一行 `只影响矛盾告警 · 不改变命中切片`，并在滑块旁显示告警计数 |
| 真摆设（三处都不引用） | 2 | **二选一**：补进 `conflicts`/`notSuitableFor` 让它有用，或从 `drivers` 删掉。建议 `msi/growth` 补一条告警（增长预期高 + 全量解析 = 存储爆炸），`vt/lifespan` 补进 `notSuitableFor`（短命任务用线程池更划算） |
| 低敏感度（<35%） | 5 | **不动**，但在参数卡显示敏感度百分比（数据算出来写进 JSON），让用户知道哪个旋钮最有效 |

**新增构建期断言**（防回潮，写进 `build-content.py`）：
```
每个 driver 必须至少被 slices[].when / conflicts / notSuitableFor 之一引用，否则构建失败
```
注入验证：临时给某场景加一个孤儿 driver，必须红。

**改动**：`tools/build-content.py`（断言 + 计算 `sensitivity`）、`src/lib/case-types.ts`（`Driver.inert?: boolean` / `sensitivity?: number`）、`CaseLab.tsx` 的 `LevelAxis`。
**验收**：11 个零影响参数全部被标注或处置；断言注入测试真红；`verify:project` 计数同步。
