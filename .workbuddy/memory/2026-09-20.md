### Bug 1（主因）：导览点哪一章图都一模一样

`graphStories` 里预设章节 `focus = Object.keys(preset.picks)`，而**四个预设都声明了全部 17 个维度**
→ 每章 focus 都是 17/17 → `lit` 覆盖全场 → 没有一格被压暗 → 点哪一章图都不变。
实测：旧定义下 4 章的 focus 完全相同（去重后 1 种）。

**修**：焦点改成「与当前选择**不同**的槽位」，note 明说「相对当前选择要换掉 N 个槽位」；
当前选择即该预设时 focus 为空、note 说「当前选择就是这套预设」，渲染层 `lit` 为空时不再整片压暗。
修后各章：standard=0 / minimal=4 / cloud=5 / enterprise=9 / computed-risks=3 —— 5 章 5 种。

### Bug 2：角色透镜的重复 React key

透镜两列标题里嵌泳道名，A 与 B 被设成同一条泳道时标题撞 key →
React 会丢掉或重画一列，而**控制台只有一条 warning，面板看起来只是「少了一块」**。
A===B 是怎么来的：`pickSlot` 的透镜分支 `if (lensA === laneId) setLensB(laneId)` 会主动把两边设成同一条。

**修**：点方块 = 把 B 换成它所在泳道（已在比较里的不动）；两个下拉把对面占着的泳道 `disabled`；
三列与能力 chip 的 key 改成不依赖泳道名的稳定 key。

### 这次踩出来的三条规矩（值得长期记住）

1. **落位（place）必须按选项定，不能按维度定**。同一个「定时任务」维度，Spring @Scheduled 是进程内线程，XXL-Job 是独立进程；同一个「缓存」维度，Caffeine 进程内、Redis 起进程。按维度定会把进程内的东西画成一个不存在的部署单元——这是架构图里最容易被当真的一类错。
2. **落成 appTag 的选项，指向它的连线必须一起消失**（onCanvas 过滤）。否则图上会有一根连到空气里的线。
3. **画布文字按像素裁剪**（textW：CJK≈1em / ASCII≈0.55em），按字符数猜会压到端口徽章。分区标题悬浮在框外左上——节点正上方是连线标签带。连线标签放目标入口上方（向上的线放源端），多条线从源底边按 lane 均分出口。

另修：`build-content.py` 在 Windows 上用文本模式写 JSON → CRLF，整文件假变更污染 diff；已改 `newline='\n'`。

实测：308 项 verify 全绿 + tsc 干净；浏览器端到端过：渲染 / 集群切换（×2 徽章出现）/ 拖拽 / 改名 / 复制 PNG 进剪贴板。

## 选型 → Archify JSON IR 适配器（`src/lib/archify-ir.ts`）+ `verify:archify`

装完 Archify 之后接着做的是**接上去**：把装配台的选型数据翻译成它的中间表示，
拿它那九项构图检查当质量门。

**定位：一份模型，两个渲染器。** 输入只有 `buildTechArch()` 的产物 —— 适配器不碰
`picks`、不碰原始 JSON。它自己的 `CANVAS_LAYOUT` 是画布上手工调过的像素，这边要留
region 边框、框外标题带、正交折线标签的空隙，所以几何**重算一遍**。语义（谁连谁、
什么类型、带什么商标）必须来自同一份数据。手工拖动的 `edits.offsets` 不带过去 ——
那份图有自己的版式引擎，而正是那个引擎在管「标签会不会压线」。

### 结果

- 4 套预设 + **133 种节点层组合穷举**（2^7 + 预设 + 空画布）→ 全部 9/9、0 错 0 警，
  `--quality showcase` 最严档。最小标签净空 6px（门槛 4）、最小内部段 20px（门槛 16）。
- `verify:archify` 进 `npm run verify` 链，默认 12 例（4 预设 + 7 边界 + 空画布）19 项断言；
  穷举档走 `ARCHIFY_SWEEP=1`（约 70 秒）。**全套自检 308 → 327 项。**

### 逆向出来的三条硬规律（读它的 renderer 源码得来的，不是猜的）

1. **版式必须是左到右主干，不能照搬自研画布的自上而下分层。** 它的端点方向推断是
   `defaultFromSide` **先比两端中心的 x**、相等才比 y —— 竖排布局里跨层连线的两端中心
   几乎不可能对齐，于是每条都被判成"水平方向"，而它要求首末段必须水平。四套预设全灭。
   → 改成三列主干（客户端 → 应用 → 右列一排基础设施），分层信息交给 region 边框承担。
2. **同一个源分出去的多条连线，它自己的路由必然叠在一起。** 自动路由恒取
   `midX = (start.x + end.x) / 2` 作转折竖线 —— 同源扇出的每一条竖段都落在同一条 x 上，
   标签必然互压。→ **凡是跨列向前的连线一律显式写 `via`，竖段 x 由我们排车道。**
   `via` 一旦给了，它连端点方向都不再推断，几何正确性全归我们。
   （`automaticPortSpread` 对带 `via` 的连线直接 `continue`，别指望它帮忙。）
3. **回边（目标列在左）必须绕行。** 直连会横穿中间那一列的节点，那在它那边是硬失败。
   走「右导轨 → 顶部横轨 → 下沉进目标顶边」，`labelSegment: 2` 把标签挪到横轨上
   （默认骑竖向轨，右半边会探出画布 —— 包围盒只按组件与边框算，折点不进包围盒）。

### 两处必须算准的几何（都是实测撞出来的）

- **车道竖段长度 = 两个节点中心的高度差**，而它有一条 **16px 内部段下限**。
  天生居中的左列，应用进程中心很容易正好撞上右列某个节点的中心 → 竖段只有 8px。
  → 新增 `leftBlockShift()`：左两列整块纵向平移，取「离所有右列目标都 ≥20px 且挪得最少」
  的那个偏移。**挪版式而不是挪数据**。
- **标签默认骑在中间段上方 20px**（矩形上沿 = 中点 − 20，高 14）。车道越短，中点越贴近
  源节点中心线，标签就正好压在同一源扇出的那条横线上（实测差 1.5px，门槛 4px）。
  → `laneLabelDrop()` 逐个试偏移 0..60，取第一个同时避开「源扇出横线」与「前序车道入线横段」
  的值。**不能写死一个数**：写死 26 先修好短线，又把长线的标签推到前一条入线上（1.5px）。
- 标签遮罩宽度要按它自己的公式估：`max(30, 单位数 × 4.8 + 10)`，全角算 2 个单位。
  估错的后果是它报错指向我们的坐标。

### 只有扫组合才会露出来的坑

四套预设全过 ≠ 没问题。含「库 + 缓存 + 消息队列 + 注册中心 + 调度器」那套组合里，
缓存那条线的标签离数据库的入线只差 1.5px。**穷举 2^7 才碰到。** 这条经验已写进
`archify-check.ts` 的注释，穷举档保留成可选项。

### 环境坑（新增一条）

`.verify/archify-check.ts` 原先用 `fs.rmSync(tmpDir, {recursive:true})` 清临时目录 ——
穷举档 133 个文件时**被宿主机注入的删除守卫打死**：
`SAFE_DELETE_BULK_CONFIRM_REQUIRED {"count":194,"threshold":50,"scope":"turn"}`。
（和 MEMORY 里那条「rm 被守卫截断在约 9~10 个文件」是同一个守卫，只是这次守的是**单轮总数**。）
→ 改成**只建目录、按下标覆写、不做递归删除**。临时文件名是确定性的，上一轮多出来的读不到。

### 为什么必须有个后端

渲染器是技能里的 Node CLI（13.5k 行 ESM，读自己的 HTML 模板、自己算标签遮罩与折线净空），
浏览器跑不了；而 `arsenal-web` 是 `output: 'export'` 纯静态站、没有 API 路由
（此前**零网络请求**，已核实）。给用户列了四条路（独立小服务 / 塞进 arsenal-server /
构建期预渲染 / vendor 渲染器进前端），**他选了塞进 arsenal-server**。

### 后端（新增包 `com.arsenal.archify`）

- `ArchifyService`：写临时 spec → `ProcessBuilder` 跑 `deliver` → 翻译回结构体。
- `ArchifyController`：`GET /api/archify`（可用性）+ `POST /api/archify/deliver`
  （请求体**就是 IR 本身**，不套壳 —— 页面上复制到的那份 JSON 原样 POST 过来）。
- `ArchifyUnavailableException` 四码：NOT_INSTALLED / NODE_MISSING / TIMEOUT / EXEC_FAILED。
- 全局异常出口加两条：503 / 504（超时）分流 + `HttpMessageNotReadableException`→400
  （原先会落 500，**方向是反的**：500 说服务端坏了，实际是调用方发了坏数据）。

**用 `deliver` 而不是 `render`** —— 前者一次给图 + JSON 收据
（`checksPassed` / 两类 sha256 / 字节数），省一次进程。

### 版本协议（实测出来的，别猜）

- 成功：退出码 0，stdout 是 JSON（`specification.sha256` / `artifact.sha256` / `validation.*`）。
- 失败：退出码 **1**，**stdout 也是 JSON**（`error` + `diagnostics[]`），stderr 是给人看的日志。
- **stdout 与 stderr 必须分开**：合并后 JSON 就解析不了。且重定向到**文件**而不是管道 ——
  顺带没有管道缓冲死锁，也绕开 Windows 控制台代码页把中文糊掉。

### 安全（这是「收 JSON + 起子进程」的接口，出事概率最高那类）

1. **不走 shell**：`ProcessBuilder` 传数组，没有 `sh -c`。
2. **拒收对象形态的 `brand`** —— 逆源码得到的关键事实：对方的渲染器**只在**
   `brand: {url, sha256}`（「钉住抓取」形态）时才**真的发网络请求**（它自己有 SSRF 防护，
   但那是它的防线）。我们的适配器只产出内置 id（字符串），对象形态零收益纯风险
   → 递归**整棵树**拒收（只看 components 的话，哪天 schema 多认一处就静默失守）。
3. 显式 `pb.environment().remove("WRENCH_AI_BRAND_ALLOW_PRIVATE")` —— 挡掉从另一侧的绕过。
4. 超时 `waitFor` + `destroyForcibly`；临时目录 `finally` 清。
5. **请求内容校验放在环境检查之前** —— 于是「坏请求」的判定与机器装没装技能无关，
   既可测、也不会因为环境变化而少一道防线。

### 探针：`arsenal-server/.verify/ArchifyProbe.java` + `scripts/archify-probe.sh`

仿 `parity-probe.sh`：绕过 Spring 直接构造服务。**IR 由调用方传入**（同 ParityProbe 那条教训）。
三类断言：

- 正例：出图 9/9 · `artifactShaMatches`（**证明按 UTF-8 读回是逐字节无损的**）· 产物像 HTML 文档。
- **环境类（不看本机装没装，每次都跑）**：模拟技能缺失 → 如实报 NOT_INSTALLED 且说明里
  带怎么补、deliver 抛异常；node 配置写错 → 能回落到 PATH；quality 写错 → 起服务当场失败。
  这一类只测「本机能出图」是**永远测不到**的，而它恰恰是别人机器上最常见的情况。
- 护栏：非对象拒收 · 对象 brand 拒收 · 坏几何**如实回诊断而不是抛异常** · 临时目录残留 0。

### 前端：`src/lib/arsenal-api.ts`（全站第一处网络请求）

四态分开——checking / ready / unavailable / offline。**「没起服务」和「没装技能」
要用户做的事完全不同**，糊成一句「不可用」等于没说。出图通道那一行按四态给四句话。
生成后页内 iframe 预览（`srcDoc` + `sandbox="allow-scripts"`，不给同源权限）+ 新标签 +
下载 HTML + 收据行（N/N 项检查 · 字节 · 耗时 · 指纹前 8 位）。IR 变过就标「这张是旧图」。
**后端不在时按钮灰掉、其余四个出口照常可用** —— 没打破「脱离服务器活着」这条原则。

### 环境坑（两条新的）

1. **`curl` 是 Windows 原生程序，`-o` / `-D` 也是路径**，不只是 `--data-binary @file`。

## 23:00+ 自审：出图功能的遗漏（`function-review-2026-09-20.md`）

用户要求「检查刚写的功能有没有遗漏」。全量读源码 + 实跑取证，落成评审文档。

**P1-1 护栏全在「解析之后」+ 监听 `0.0.0.0` + 无并发闸门。**
这是军火库**第一个「收 JSON 就在机器上起子进程」的接口**（此前全部只读），风险模型变了而闸门没加。
- `netstat`：`0.0.0.0:3011`（`application.yml` 只写 port 没写 address）→ 局域网任何机器可 POST；
  CORS 只拦浏览器，`curl` 不看 `Allow-Origin`，那道 403 对非浏览器客户端等于零。
- 24 并发 → 峰值 6 个渲染进程（受本机 CPU 限制）；12 并发时 node.exe 合计 1377 MB vs 基线 1171 MB
  → **单渲染进程约 40 MB**；代码里无信号量/队列/限流，唯一闸门是 Tomcat 线程池 200。
- 24 MB 请求体被**完整收下 → 完整解析成一棵树 → 重新序列化**，才被 1 MB 护栏拒
  （回「IR 太大（24003625 字节…）」）→ `maxSpecBytes` 挡的是「喂给渲染器的字节」，
  不是「收下的字节」。单字符串 >20 MB 会被 **Jackson 自己的 `maxStringLength`** 挡成

  `Semaphore(2)` 满载 429。**别把 `IllegalArgumentException` 那道挪走**，它是对的，只是位置靠后。

## 代码审查（`code-review-2026-09-20.md`）· 同日晚

对 Archify 那套做了**代码级** review（区别于上午的 `function-review-2026-09-20.md`：那份审功能与约定，
这份审错误映射 / 并发与资源 / 类型边界 / 死代码 / 注释与实现是否一致）。全部结论都实跑取证。

### 三条 P1（前两条是新的，第三条与上午重复但换了角度）

**P1-1 · `GlobalExceptionHandler` 的兜底把 Spring 自己的 4xx 全吃成 500。** 实测 6 例：
`Content-Type: text/plain` → 500（应 415）· 不带 Content-Type → 500 · `DELETE /api/archify/deliver` → 500（应 405）
· `POST /api/rules` → 500（应 405）· `GET /api/nope` → 500（应 404）· `GET /no-such-page` → 500（应 404）。
根因：`@ExceptionHandler(Exception.class)` 在 `ExceptionHandlerExceptionResolver` 里**先于**
`DefaultHandlerExceptionResolver` 命中，而 advice 没继承 `ResponseEntityExceptionHandler`
→ `HttpMediaTypeNotSupportedException` / `HttpRequestMethodNotSupportedException` / `NoResourceFoundException`
全落进兜底 + `log.error` 带堆栈。
反讽：类注释专门为 `HttpMessageNotReadableException` 写了「不接住它会变成 500，而 500 意味着服务端坏了
—— 排查方向完全是反的」，结果为同类的另一个兄弟（Content-Type 错）漏在外面。**406 碰巧是对的。**
⚠️ 这一层**当前一条自检断言都没有**，所以它能一次错 5 种。修：继承 `ResponseEntityExceptionHandler`
或逐类加 handler + 补 5 条 HTTP 断言。

**P1-2 · 分区不在 `CANVAS_ZONES` 里的节点被静默丢掉，自检看不见。** tsx 探针实测：10 个节点进
`buildArchifyIr` → 9 个组件出，`archifyIrIssues` 报 **0 处**。链条：`groupZones` 只遍历 `CANVAS_ZONES`
→ 该节点不进任何组 → `layoutColumns` 不给槽位 → 组件循环 `if (!p) continue` 静默跳过。自检只看 IR，
那时节点已经没了，所以**永远报不出来**。
两处注释与实现相反：`archifyTypeOf` 说「真走到兜底说明有人加了新维度却忘了声明分区归属」——
这类节点走不到那个兜底；`columnOf` 说「找不到分区时归到右列（最保守）」，代码 `if (index <= 0) return 0`
—— `findIndex` 找不到返回 **-1**，`-1 <= 0` → 返回 **0（左列）**，注释与代码相反，而且是死代码。
**这不是纸上的问题**：项目正在做「加维度」（结构层 2 条规则缺口就是），忘了声明分区 → 图上少一块、
零提示，而这张图是发给客户的。修 10 行：断言每个 model 节点都拿到槽位，缺的把 id 交出去。

**P1-3 · 前端硬编码 `75_000` 与后端可配的超时脱钩。** 注释说「后端超时的 1.25 倍」（60×1.25），
但 `application.yml` 的 `timeout-seconds` 可配，且 `probe()` **已经把它如实返回**（前端类型也声明了）
—— 就是没人用。调到 120 时前端 75s 先掐断，后端那句「先手工跑一遍 render 看它停在哪」永远送不到。

### 两条「查过、不是问题」（记下来免得下次重复怀疑）
1. **可编辑文字经 IR 进对方渲染器不构成注入。** 构造 6 处载荷（`</text><img onerror>`、

### 两条新踩到的环境坑
- **`node`（Windows 原生程序）读不了 Git Bash 的 `/c/...` 路径** —— 与 curl 同族：

  解法：所有传给 node 的路径过 `cygpath -m`。

  `Error: Bad substitution`。改用 Write 工具落文件，或脚本里用字符串拼接不要模板串。
- `wrench-ai deliver` / `render` **都过校验门**，所以"用超长 label 造注入样本"会被构图检查挡在门外
  —— 想拿产物只能先让版式合法，或者去读渲染器源码。
