## 部署产物自审（用户："对代码进行自检"）—— 查出 7 个真 bug，全是「不报错但产物跑不起来」

### P0

1. **Helm `service.yaml` 根本没被模板化**：原来是 `service(ctx).replace(/^name: .*$/m, ...)`，

   必挂 not found。Gradle 分支写 `RUN gradle`，而 temurin JDK 镜像里没有 gradle。

## 09:40 收尾排查 —— 三件「数字对不上」的事

用户问「接下来还需要做什么」，先实测了一遍当前状态，查出三件：

**① 运行中的后端会静默停在陈旧规则集（真问题，未修）**
3011 上那个进程只提供 **62 条**（`reliability: 9`），而事实源是 **69 条**（`reliability: 16`）。
`/api/stats` 一脸正常地报 `total 62 / mustClass 50/50 / budgetUsedPct 100`，
`/api/rules` 同样 62 条 —— **没有任何异常迹象**。这正是 RuleLoader 注释自己警告的场景
（"你会以为自己在被 62 条规则保护，实际只有 59 条，而且永远发现不了"），
但它只防「启动时少读」，不防「运行中事实源变了」。
查出原因：该进程是**加 K8S 规则之前启动的**，RuleLoader 启动时一次性加载进内存索引。
重启后立刻恢复 69 条。**结论：没有任何校验覆盖 HTTP 层**（见 ③），
「改了规则忘了重启后端」会长期骗人。→ 待补一条「活服务体检」断言。

**② `SERVER__PORT` 环境变量污染（已修 run.sh）**
启动失败报 `Port 3743 was already in use`，但 `application.yml` 写的是 3011。
根因：托管环境注入了 `SERVER__PORT=3743` / `SERVER__HOST=127.0.0.1`——
**双下划线是 Spring 的层级分隔写法**，relaxed binding 认成 `server.port`，
优先级高于 application.yml，于是应用去抢宿主的端口。
修法：run.sh 用 `--server.port=${ARSENAL_PORT:-3011}`（命令行参数优先级最高），
换端口走 `ARSENAL_PORT`，不要改 yml。另注意：`bash run.sh > log &` + 主脚本退出
会把子进程带走（日志只留两行），后台启动必须让 task 持有进程。

**③ parity 的「68 条」是设计行为，不是 bug（虚惊）**
`parity-probe.sh` 编的是独立 `ParityProbe`，**直读 rulesDir**，完全不经过 HTTP 后端。
68 = 69 − 1 条 MAY（探针按 severity CSV 过滤，调用方传的 `MUST,NEVER,SHOULD`）。
所以 parity 测的是「同一份数据被两套代码编译」，**不测运行中的服务**——
