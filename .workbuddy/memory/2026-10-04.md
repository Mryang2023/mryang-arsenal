### 三个工具的设计取舍

- **`list_exceptions` 是这套机制里最容易被省掉、也最有用的一个**。
  它的存在意义：AI 在「觉得自己要违反某条条款」时**先看有没有现成豁免**，
  而不是直接申请新的。不查就申请是台账膨胀的头号原因。
- 服务端**不做合格性判断**，只读取与格式化。合格性由构建期那道闸负责（已过）。
  混用会出现「构建期说合格、运行期报违规」而无人知道原因。
- 服务端**不自己取 `new Date()`** —— 例外是否到期靠日期，自己取就意味着
  同一份代码两次调用结论可能不同。`today` 由调用方传。

### 导出：三个函数 + 一条硬规矩

`buildCharterMarkdown` / `buildCharterCI` / `charterDeliverableFiles`。
**CI 片段里绝不写死判负口径** —— 例外到期判不判负是 `policy.overdueException`
决定的，而 policy 在**用户自己的章程文件**里。片段写死等于越权。

自检**分两种**：断言层验「某一层自己对自己」，最容易出问题的恰恰是**层与层之间**。

### 结论：产品 0 bug，但**自检脚本自己错了 3 处**（这一条比结果更值钱）

| 我以为红了 | 真因 |
|---|---|
| 页面全说「生效中」而校验器说「已到期」 | **我的夹具传错了对象** —— policy 覆盖传了 `d`（带例外），页面函数传了 `overdue`（exceptions 为空）。判据本身是对的（单独复现：`level=error`、逾期 275 天） |
| 每条用例都报 `OVERRIDE_RULE_NOT_FOUND` | 我传 `knownRuleIds: new Set()`（**空集**）。真数据里 `COL-GIT-002` 存在，sync 也通过 |
| 未来条款「校验器不放行」 | 校验器**说得对** —— 条款生效于 2099 而章程批准于 2026-10-03，命中 `RATIFIED_AFTER_EFFECTIVE`（另一条判据）。我的判据写得太笼统（`errors.length === 0`），应该写「除这一条外没有别的」 |

> **教训：「红 → 一定是产品有问题」这个惯性本身就是错的。**
> 第三版自检的三个红全部属于「夹具把上下文造错了」或「判据写得太粗」，
> 而前两版我差点照着去改产品代码 —— 那会把对的判据改错。

### 25 项跨层自检在验什么（断言层验不到的部分）

| 跨层项 | 验的是 |
|---|---|
| 快照 vs 事实源 | 条款 id 集合、policy 四项逐项一致（改了 JSON 忘 sync 会分叉） |
| **冻结线三处一致** | 未来条款：校验器**放行**（合法、只是没到日子）／纯函数层**排除**出规则池（挡住 PR 门）／`today` 为空时仍排除（保守侧） |
| **例外处置三档 × 两方一致** | `overdueException` 的 error/warn/ignore 三个取值，校验器的 err/warn 与页面徽标的 error/warn/ok **逐档比对** |
| **孤儿两档 × 两方一致** | `orphanBlocks` 的 warn/error 同样逐档比对 |
| MUST 配额三口径 | separate / shared（50+1=51）/ **读不到时**（校验器报「无法判定」+ 页面显示「无法计算」，都不许静默或显示 0%） |

| 五道闸门 + 反证 | 逐条注入各命中自己的判据；**反证：合规的例外 0 诊断** |

其中「冻结线」与「例外处置」这两组是最值钱的 —— 它们是**同一份数据的两种算法**
