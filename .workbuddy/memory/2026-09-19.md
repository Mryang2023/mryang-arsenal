## 启动链路实测 + 两个真 bug（mryang：「我这个项目怎么启动」）

没照抄 README，而是把前后端**真跑了一遍**，结果挖出两个实测 bug。

### 后端

`bash scripts/run.sh` 直接挂：`[FAIL] java not found under: C:/Users/Administrator/.jdks/ms-17.0.18/bin`。
**根因**：`run.sh` 写死 JDK 路径，而本机只有 `.jdks/{corretto-1.8.0_422, corretto-17.0.12, corretto-21.0.4}`。
更能说明问题的是 `_cp.sh` 第 6 行的注释 —— 「两个脚本各写一份的结果就是哪天换 JDK 只改了一处，
另一处静默用旧路径，正是本项目在防的那类漂移」—— `run.sh` 恰好就是那份没跟上的。
**修法**：`run.sh` 改为 `source "$HERE/_cp.sh"` 复用 JDK 定位（删掉本地 `to_win` 与硬编码）、
保留自己那份含 tomcat 的运行时 DEPS 列表（`_cp.sh` 刻意只含编译期依赖）。
修后无需任何环境变量：`SERVER_ARGS="--server.port=3011" bash scripts/run.sh` → 11s 起来。

### 第二个坑（非代码 bug，是脚本语义坑）

`SKIP_COMPILE=1` 不只是跳过 javac，它把 `cp -r src/main/resources/. target/classes/` **一起**跳过了
（那行在同一个 `if` 块里）。现象是 Spring 启动报
`Could not resolve placeholder 'arsenal.rules-dir'` —— 看着像 `application.yml` 写错，
实则 `target/classes/` 里只有 `com`，配置文件压根没进去。

而且 `compile-check.sh` **只做静态校验、从不复制资源**，所以「先 compile-check 再 SKIP_COMPILE=1 启动」
这条最自然的路径**必然踩坑**，不是边角情况。
**修法**：把资源复制移出 `SKIP_COMPILE` 守卫（`mkdir -p target/classes` 也一起移出），
变量名的语义收回「只跳过编译」。
修后实测：路径 A（compile-check → SKIP_COMPILE=1 启动）2s 成功、路径 B（全新 target 直接 run.sh）3s 成功
且 `target/classes` 含 `application.yml`。README 的警告块已同步改写成说明而非劝退。
