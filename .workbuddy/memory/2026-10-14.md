### ③ 代码扫描层链内崩溃 —— 根因找到了，不是并发干扰

**真根因：`spawnSync('bash', ['--version'])` 在本 harness 是瞬时 EBUSY。**
实测四份：npm run / 全链里 3 次返回 EBUSY，1 次真跑通 137/137。
老写法只看 `status === 0`，于是 EBUSY 被写成「bash 不可用」，
后果是**整层 N 项记成「未执行」而实测数取自档案声明值** —— 一句假话套着另一句假话。

修法（`probeBash()` / `gitProbe`）：
- EBUSY / EAGAIN / EPERM **重试 3 次**；
- 重试后仍被拒就**照实说是被拒**，不再写「bash 不可用」「沙箱限制」这种推断；
- 文案里点明「这不是环境不具备，是这一层一次都没能起跑」。

效果：链内代码扫描**首次拿到成绩**（33 通过 / 139 未测 / **0 失败**，此前是 `?` 无状态文件）。

## 傍晚：三件一起开完（`5b7e607`）

### 1. flaky 判定（补 C1 的洞）

`ReproVerdict.stabilityOf(redCount, attempts)` —— **纯函数**，四档：
`stable / flaky / absent / insufficient`。最少 3 次样本才给结论，
**宁可不给也不拿 1/1 说「稳定复现」**。

**最重要的决定：偶发复现仍然是实锤。**
若因为「不稳定」降级成待确认，那正是并发/时序类缺陷的下场 ——
它们天生低复现率，于是永远进不了实锤档，于是永远没人修。
稳定性只影响「你有多急」，不影响「它是不是真的」。

### 2. C4 审查员委员会（`CommitteeJudge.java`）

安全 / 性能 / 并发三路**真并行**（三个 future 同时发，串行只是把墙钟 ×3），
交叉验证按「文件:行 + 归一化标题」当同一问题的键。

- **孤证 ≠ 误报**：只有 1 个审查员报的是**置信标注**，不删、不判负 ——
  与「语义 finding 必带 confidence、不进 P0」同一条纪律。
- **归一化只剥空白与句末标点，不归一措辞**：措辞不同恰恰是不同审查员各自写的证据；
  揉成同一个词的话，「共识」就从需要论证的数字变成恒等于分组数的数字。
- **成本 ×3 的闸门先于功能上线**：`llmUsage` 拆成 `perJudgeer` 三份账 +
  `costNote` 写明倍数 + 某位没跑成时如实标 `not-run-budget`。
  一个审查员超时不拖死整批（`f.get(8, MINUTES)` 单独兜），另外两位结论照样有效。
- ⚠ **踩过一个顺序坑**：`autopsy.inspect` 内部会 close 掉 source（git 模式工作副本用完即焚），
  委员会排在它之后就只能读空目录。已挪到 inspect 之前 —— 与复现实锤同一纪律。

### 3. C2 改造工坊（`RefactorWorkshop.java`）

计划书那句边界决定了一切：**全自动改造是危险机器，首版是「人踩油门、机器干活」**。
所以**没有「一键改造」入口**，会话是三段、每段要人确认：

```
PLAN   选目标 → 逐点方案（哪些能自动、哪些只出主意）   ← 一个字节都不写
APPLY  确认后只机械应用「可自动」的点 + 存原文供回滚
VERIFY 改造前后各跑一次审查 → 数字对照，不达标不许「交付」
```

**「可自动」判据（唯一定义处 `judgeAuto`）**：有 before/after 正例 +
before 在目标文件里逐字节找得到 + **出现且只出现一次**。
第三条最容易忘：同一片段出现三次时，「自动替换」要么只改第一处（改一半）、
要么全改（改超了）—— 两种都是「看起来改成功了」的假绿，所以直接判不可自动。
应用前**再核一次**（计划与应用之间文件可能被别人动过）。

回滚凭据落 `target/arsenal-refactor-undo.json`（原文），**不用 git checkout** ——
那会连带抹掉别人未提交的改动。VERIFY 的门槛是数字：两次报告缺一侧 = `not-run`，不是达标。
「交付」也只产出 diff 文本 + 前后对照，**不 commit、不 push**。

配置：`arsenal.qa.committee.max-batches-per-job` / `.parallelism`、
`arsenal.qa.refactor.max-per-session`。
