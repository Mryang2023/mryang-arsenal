# 夜跑章程 v1.0

> 立章：2026-09-22
> 依据：首次夜跑（2026-09-21 23:20 → 09-22 07:52，五棒接力）的实际结果与第 5 棒巡检报告。
> 适用范围：任何项目的「夜间无人值守开发」。

---

## 零、它管什么

管三件事：

1. **排期** —— 一个窗口装得下多少任务，怎么算，装不下怎么砍。
2. **单棒作业** —— 一棒怎么干才算干完（三段式 + 收尾）。
3. **接力与终检** —— 多棒怎么不互相踩，最后一棒怎么兜底。

不管：任务内容本身（那是方案的事）、用哪个模型（用户自己选）。

---

## 一、三条第一原则

### 1.1 时间窗是硬约束，不是「尽量做完」

夜间窗口是有边界的资源。窗口外的每分钟都在扣积分；窗口内做不完的代价不是「少做一点」，
而是**留下半成品 + 欠账**。

**首次夜跑的实证**：4 个按"一整晚 9 小时"设计的方案被塞进一个窗口，每棒只有约 2 小时。
结果四棒全部只做到地基 —— 图标没位图、装配台没 UI、案例只有 2/6、扫描出不了图。
**没有一棒失败，但四件事都没完成。**

→ 推论：排期必须**倒着算**。先按体量算出需要多少时间，再看窗口装得下几棒。顺序不能反。

### 1.2 一棒三段，缺一不可

**一棒 = 开发 → 自检补漏 → Code Review。**

这不是"可选的最后两步"，这是**交付的定义**。没跑过自检和 review 的产出，不算这一棒做完了。

理由：夜间无人值守，第二天你看到的只有一份报告。若没有内置的质量门禁，
你拿到的可能是"看起来完成、实际是半成品"的东西 —— 而你要到几天后真正用到时才发现。

两段的侧重必须分清，否则会重复劳动：

| 段 | 对准什么 | 回答什么问题 |
|---|---|---|
| 自检补漏 | **方案**（要求） | 该做的都做了吗？有没有静默失败？ |
| Code Review | **代码**（实现） | 写得住吗？有隐患吗？和项目一致吗？ |

### 1.3 诚实优先于好看

- 未做完的写进清单，具体到**文件 / 阶段 / 断言编号**。
- 不许写"部分未完成""基本完成"这类无法核对的话。
- 不许为了报告好看而修改结论、把"没做"写成"做了"、删掉挂红的断言。
- **首次夜跑的增值点恰恰在此**：四棒零虚报，终检抽查 6 条"未做完"条条属实。
  这份诚实比多做两个功能值钱。

## 二、三段式细则

### 2.1 预算分配

| 段 | 占比 | 说明 |
|---|---|---|
| 开发 | 60% | 按方案的「MVP 与可裁剪」，先做闭环再做扩展 |
| 自检补漏 | 20% | 对**方案验收标准**逐条核对 |
| Code Review | 20% | 对**本次改动的代码**按五个维度扫 |

**收尾另算，约 20 分钟**（全量验证 / 数字同步 / git commit / 清理 / README / memory / 状态文件）。
排期时不能把它漏掉 —— 它不是"可选的最后一步"，是交付的一部分。

### 2.2 第一段 · 开发

- 开工先按预算砍范围。**这是开工第一件事，不是可选项。**
  方案原文往往按"一整晚"写，砍到预算内是正常操作，不是偷懒。
  砍完把范围写进 `0N-running.json`，收工时对照它交账。
- 有前置依赖的，先查依赖产物是否存在。缺失就**降级**并如实记录，**不许硬造**。
  > 首次夜跑第 4 棒的正面案例：发现前棒没做到 `CanvasTheme` 的 `doc/slide/blueprint` 三态，
  > 按规程拒绝硬造，降级为"不产出部署图 SVG"并写进剩余工作量。这是对的做法。
- 阶段化推进（数据 → 引擎 → 产物 → 页面 → 验证），每阶段做完立刻验收。

### 2.3 第二段 · 自检补漏（完整性）

**目标：找出"看起来完成、实际没完成"的地方。**

必做五件事：

1. **验收对照** —— 把方案的「分阶段实施 / 验收标准」逐条拉成表，标 ✅ / ⚠️ 部分 / ❌ 未做。
   **对照的是方案原文，不是自己的印象。**
2. **存在性核验** —— 声称新建的文件，`ls` / `grep` 逐个确认真的在。
3. **反着验** —— 至少挑 **2 处**本次新写的闸门或断言，**故意注入错误**，
   确认真会报错 / 变红，然后还原。
   > 一条从没红过的断言，和摆设没有区别。
   > 首次夜跑终检只来得及验 2 组，剩余 8 组（闸门 ⑥⑦、断言【11】【15】、cases 25 项、scan 恶意输入 7 项）
   > 至今**未被证伪** —— 它们"看起来是对的"，但没人知道是不是真的在工作。
4. **静默失败排查** —— 找"空跑通过"的检查。
   例：体积断言在文件数为 0 时"通过"；取到 0 条数据的校验报"0 条全部合法"。
   任何"断言通过但样本量为 0"都必须点名。
5. **引用核实** —— 方案里引用的 id / 路径 / 依赖 / 接口，**去仓库里查是否真实存在**。
   > 首次夜跑第 3 棒的实战：方案示例里的规则 id `DATA-IDX-002` 根本不存在
   > （真实的是 `DATA-SQL-001..004`），照抄就错。

**未完成项先补** —— 自检段的预算本来就是留给补漏的。补不完的写进清单，具体到条目。

### 2.4 第三段 · Code Review（质量）

**目标：对本次改动的代码做严肃审查。** 只审本次改动范围，不审全仓。

五个维度：

| 维度 | 查什么 |
|---|---|
| **正确性** | 边界值、空值、并发、错误路径、类型、异步时序 |
| **安全** | 注入、路径逃逸、敏感信息硬编码、权限、对外部输入的信任 |
| **性能** | 循环内 IO、N+1、无界集合、重复计算、不必要的同步 |
| **可维护性** | 重复代码、魔法数、命名、死代码、**残留调试代码** |
| **一致性** | 与项目既有范式 / 类型体系是否一致；有没有留下"功能等价但形态不同"的平行通道 |

**每条问题必须给三样**：`[P0/P1/P2] 文件:行 —— 问题 → 根因 → 处置`。
处置只有两种：**当场修掉** / **列入剩余工作量清单**。

- **P0 与便宜的 P1 → 当场修**，修完重跑验证。
- 其余 → 进清单，并写明为什么没修（时间不够 / 需要设计决策 / 影响面大）。

**诚实边界**：不许把 P2 包装成 P1 凑数，也不许漏报。
审查结论没人看没关系，误导使用者才有事。

### 2.5 段间门禁

| 关卡 | 规则 |
|---|---|
| 开发 → 自检 | 代码能编译 / 能构建通过。**带编译不过的代码进自检毫无意义。** |
| 自检 → Review | 无未修的 P0 完整性缺陷（漏做的要么补上，要么明确记录）。 |
| Review → 收尾 | 无未修的 P0 代码缺陷。 |

> 门禁的意义：**不许带着已知的重病往下走。** 轻问题可以记账前行，重问题不行。

## 三、体量评估与排期

### 3.1 档位表

| 档 | 开发净时长 | 典型特征 |
|---|---|---|
| **S** | ≤45 min | 单点改动：一处配置、一个函数、一条断言 |
| **M** | 45–90 min | 一个模块：一个 resolver、一段生成器、一个组件 |
| **L** | 90–150 min | 一条链路：跨 2–3 个文件打通一个功能 |
| **XL** | 150–240 min | 新事实源 + 生成器 + 闸门 + resolver + 验证层；或新页面 + 后端接口 |
| **XXL** | >240 min | 多个 XL 的组合 —— **必须拆，不许整棒排** |

判定依据看方案里的：分几个阶段、新建几个文件、涉及几个模块、有没有新页面 / 新数据源 / 新验证层。

### 3.2 预算公式

```
可用窗口 = 硬停时刻 − 开工时刻              （23:00 → 07:55 = 535 min）
扣除项   = 终检棒（40 min）+ 交接余量（3 min × 棒数）+ 启动缓冲
单棒预算 = (可用窗口 − 扣除项) / 棒数
准入条件 = 单棒预算 ≥ 体量 × 1.5 + 20        （自检 + Review 占 1/3，收尾约 20 min）
```

实算（窗口 535 min）：

| 棒数 | 单棒预算 | 能装的体量 | 判断 |
|---|---|---|---|
| 1 | ~490 min | 2×XL 或 1 个拆分后的 XXL | 宽敞 |
| 2 | ~245 min | 各 1×L | **舒适区** |
| 3 | ~160 min | 各 1×M～L | 偏紧 |
| 4 | ~120 min | 各 1×S～M | ⚠️ **装 XL 必然是半成品** |

**硬规则**：`单棒预算 < 体量 × 1.5 + 20` → **不许排**。

> 首次夜跑违反的正是这条：4 个 XL 各需约 `240 × 1.5 + 20 = 380 min` 的单棒预算，
> 实际只给了约 120 min —— 不到所需的 1/3。结果可预测：四线全停在"地基"。

### 3.3 排不下怎么办（四策，按优先级）

1. **降级** —— 只排每条的 P0 核心（闭环那一步），明确声明"今晚目标是骨架 / 闭环，不是完整交付"。
2. **分夜** —— 排到后面几晚。夜间免费窗口通常有较长有效期，欠账不必一夜还清。
3. **合并** —— 同类任务合成一棒（例：几条都是"给现有页面加一个数据源"）。
4. **砍** —— 明确告诉用户"今晚放 N 个，剩余排到明晚"，并说清取舍理由。

**绝不做第五种：硬塞。**

### 3.4 排期表样例

| 棒 | 任务 | 方案 | 体量 | 开工 | 交棒硬线 | 单棒预算 | 开发预算 |
|---|---|---|---|---|---|---|---|
| 1 | … | plan-1 | L | 23:20 | 02:15 | 175 | 105 |
| 2 | … | plan-2 | L | 接棒（兜底 02:18） | 05:15 | 175 | 105 |
| 3 | … | — | — | 06:00 | 07:40 | 100 | — |

> 终检棒若棒数 ≤2 可由最后一棒兼任，但职责必须写进 prompt；棒数 ≥3 则独立成棒。

## 四、接力协议

### 4.1 为什么必须串行

多棒常要改**同一批文件**（同步脚本、README、验证数字、共享类型）。
两棒并行 = 互相踩烂，且事后**无法归因**是谁改坏的。

- 串行的代价：晚开工。
- 并行的代价：静默损坏。

后者贵得多。

### 4.2 状态目录

每棒在 `<项目>/.workbuddy/night-chain/` 留状态文件：

| 文件 | 谁写 | 内容 |
|---|---|---|
| `0N-running.json` | 第 N 棒开工 | 棒次、任务、开工时刻、计划交棒、**本棒砍定后的范围** |
| `0N-done.json` | 第 N 棒收尾 | 见 `briefing-templates.md` 的 schema |
| `0N-blocked.json` | 第 N 棒等不到前棒 | 等了多久、前棒缺什么、读到了哪些状态文件 |
| `REVIEW.md` | 终检棒 | 逐棒核对 + 差异清单 + 补了什么 + 剩余工作量 |

终检棒收尾时清掉一次性文件，只留 `0N-done.json` 与 `REVIEW.md`。

### 4.3 开工 / 收尾 / 交棒

**开工（在读方案之前先做完）**

1. 读状态目录，先搞清现在到第几棒了。
2. **等前棒**：`<N-1>-done.json` 不存在 → **不许开工，不许碰仓库任何文件**；
   每 60 秒查一次，最多等到本棒硬线。
   等不到 → 写 `<N>-blocked.json`，**跳过本棒**，如实留给终检棒。
3. 建 `<N>-running.json`。
4. 第一棒不需要等待。

**收尾** —— 见第五节（顺序不能反）。

**交棒**：把下一棒的 `scheduledAt` 改成「现在 + 3 分钟」。
若预计超时，先把下一棒推到你预计结束时间 +3 分钟；但整体不要让终检棒晚于硬线。

## 五、收尾清单（每棒必做，顺序不能反）

1. **跑全量验证** —— 不是只跑自己改的那一层。
   > 首次夜跑的坑：第 3 棒漏跑 parity/archify（环境守卫拦截），第 4 棒漏跑 6 层（时间到），
   > 都把这句"我没跑过，按前一棒基线应该是绿的"留给下一棒。
   > **没跑过就不能说它是绿的。**
2. **同步所有派生数字** —— 项目里凡是"同一个数字写在多处"的，全部改齐，并复跑一次确认生效。
3. **git commit** —— 本棒产出必须在收工前形成一次提交。
   > 首次夜跑的坑：8 小时的产出，**一夜没有版本快照**。中途任何一棒改坏了，
   > 都无法回滚到"棒间状态" —— 只能整夜回滚或者硬着头皮往前。
   - message 用规范格式（`feat(scope): 说明` / `fix(scope): 说明`），让历史可读。
   - 提交前确认没有夹带调试产物。
4. **清理调试产物** —— 临时脚本、备份、日志，`_*` 前缀的，全删。
   > 首次夜跑遗留了 `_tmp-link.ts` / `_tmp-theme.ts` / `WalkDiag.java` 三件。
5. **README / memory 日志** —— 追加本棒记录到项目的 memory 日志。
6. **回滚判断** —— 若构建或验证比开工前更红且无法修复，
   **回滚到开工前状态**并在报告里说明回滚了什么。
   留一个坏状态，比少做一个功能严重得多。
7. **写 `<N>-done.json`** —— 含三段式各段产出（schema 见 `briefing-templates.md`）。

## 六、终检棒

**唯一不写新功能的一棒。产出是「真相」+ 收拾摊子。**

- 棒数 ≥ 3：必须独立成棒。
- 棒数 ≤ 2：可由最后一棒兼任，但职责要明确写进 prompt。

职责：

1. **独立验证，不许只信状态文件** —— 每一项"声称做完的"自己动手验一遍：
   全量构建、全量验证、文件存在性、闸门是否真会中断、断言是否真会变红、
   页面是否真挂上了导航、数字是否真同步、memory 是否真写了、**git 是否真提交了**。
2. **反着验补课** —— 优先验那些**从未红过**的检查。各棒自述"我验过"的，抽查即可。
3. **差异清单** —— 逐棒列出：它说做了 vs 实际。**逐条点名**说做了实际没做的。
4. **补漏**（按此优先级）：
   仓库不可运行 > 验证挂红 > 数字不同步 > 文档缺失 > 状态文件缺失。
   **不补**任何需要 30 分钟以上的新功能。
5. **产出 `REVIEW.md`**：逐棒核对 + 差异清单 + 补了什么 + 剩余工作量
   （**按离闭环的距离**排 P0/P1/P2，这份清单就是下一晚的输入）。
6. **硬停** —— 到硬线无条件停止动手。窗口外每分钟都在扣积分。

## 七、给用户的三个动作（编排者必须交代）

1. **手动选模型** —— 创建接口没有 model 字段，模型只能在客户端界面逐条选。
   不选就会用默认模型跑，整夜按默认倍率扣积分。
2. **电脑不关机 + 客户端保持登录** —— 定时任务在本机客户端执行，关机即不执行、不补跑。
   「允许锁屏运行」建议设 **"熄屏后继续运行"**（别设屏幕常亮 —— 跑满 9 小时没必要亮着）。
3. **今晚的取舍** —— 哪几条进了今晚、哪几条排到后面、为什么这么砍。

## 附录 A · 已知环境坑

- **长任务的删除计数**：某些沙箱守卫会在单次会话内累计删除操作达阈值后拦截构建的清理步骤。
  症状：编译 / 类型检查都过，只在清理产物目录时抛错。
  **判定为环境问题而非代码问题**；换个新会话即可复现正常。
  写报告时要说明"是哪一层被拦"，别让读者误以为代码坏了。
- **改文件前先备份**：某些环境会把 `node -e` / 脚本重跑一次。
  改文件前 `cp` 备份、改完 `diff` 验证，是低成本的保险。
- **取退出码**：别用管道后的 `PIPESTATUS` 之类间接方式。直接 `cmd; echo $?`。
  首次夜跑差点因此误判"闸门失效但退出 0"。
- **heredoc 的变量展开**：往文件追加含 `${...}` 的内容时，heredoc 会抢先展开。
  可靠做法是用写文件工具，或先写临时文件再 `cat >>` 追加。
- **子任务并行写法**：多个子 agent 并行写同族模块时，让每个模块导出 `*_EXTRA` 由生成器合并，
  避免多份编辑撞同一文件。首次夜跑第 2 棒用此法完成五个数据模块，零编辑丢失。

## 附录 B · 章程的自我修订

每次夜跑后，若发现章程有遗漏或错误（新的环境坑、排期公式偏差、模板缺字段），
**当次就改**，不要攒着。章程的价值在于每跑一次都更准一点。
