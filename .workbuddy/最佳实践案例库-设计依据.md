## 一、结论

「蓝本」的正式叫法是 **最佳实践案例库（Cookbook / Reference Implementation）**，
本质是**一案例一目录、独立可跑、配 README**。

「蓝本」原意是建筑或印刷用的底稿，引申为「后续所有东西都照着它抄的原始范本」。
软件工程里的近义词与侧重：

| 中文 | 英文 | 侧重 |
|---|---|---|
| 蓝本 | Blueprint / Reference | 权威范本，照着抄 |
| 脚手架 | Scaffold / Boilerplate | 一键生成项目骨架 |
| 模板工程 | Template Project | 新建项目时复制 |
| 最佳实践仓库 | Best Practices Repo | 收集正确写法 |
| 代码大全 | Cookbook / Recipes | 按场景查代码 |
| 参考实现 | Reference Implementation | 权威实现，可对照 |

## 二、每个案例必须包含的 README 七段

这是本次落地的核心规范。对话里定的原文顺序：

1. **什么时候用** —— 2~5 个具体场景，不要写「当需要的时候」
2. **不适合** —— 1~3 个反例，避免被误用
3. **核心示例** —— 文件清单与各自说明
4. **关键点 / 原理** —— 说清为什么这么写，而不是只贴代码
5. **坑** —— 每条要能复现，给出错误写法 vs 正确写法
6. **性能对比**（如适用）—— 有数据给数据，没数据给结论
7. **参考资料** —— JEP、官方文档、权威文章

**落到军火库的映射：**

| README 七段 | 军火库字段 | 状态 |
|---|---|---|
| 什么时候用 | `scenario` | 已有 |
| 不适合 | `notSuitable` | **本次新增** |
| 核心示例 | `files[]` + `flow[]` | 已有 |
| 关键点 / 原理 | `files[].highlights[]`（编号备注） | 已有，且用片段锚点定位 |
| 坑 | `pitfalls` | 已有 |
| 性能对比 | `performance` | **本次新增** |
| 参考资料 | `references` | **本次新增** |

另外军火库特有的 `checklist`（提交前验收清单）与 `relatedRules`（关联规则）
在对话里没有，属于本项目自己的增强，予以保留。

## 三、对话里提到但本次**未做**的事

这些是「案例库作为一个独立 Java 仓库」的建议，与军火库「Web 端内容资产」的定位不同，
本次刻意没做，留作后续决策：

- 多模块 Maven 工程骨架 + 一键生成脚本 `init-best-practices.sh`
- 每个案例独立 `pom.xml`、独立 `mvn test`
- `CONTRIBUTING.md`（案例贡献规范）
- 07 大类目录结构（01-web / 02-concurrency / 03-data / …）
- 001 号样板案例：虚拟线程在 Spring Boot 里怎么用

**判断依据：** 军火库的案例是「Web 端可查可抄的内容资产」，
数据集在 `arsenal-cookbook/*.json`，由 `tools/content/*.py` 生成；
而对话里那套是「能 clone 下来跑的 Java 仓库」。两者可以并存，
但如果要做后者，应该是**第二个仓库**，而不是塞进 `arsenal-web`。

## 四、对话里的三个关键判断

1. **它不是「可运行的大项目」，而是「可复制的小案例集合」。**
   一案例一目录、互不依赖、每个配 README。
2. **别追求大而全。** 覆盖 100 个场景但每个都很浅，不如 20 个场景每个都很透。
3. **README 比代码重要。** 半年后你不会记得为什么这么写。
